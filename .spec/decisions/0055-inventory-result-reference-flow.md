# 0055-背包结果写入参考流程边界

- 日期：2026-07-16
- 状态：已采纳
- 背景：
  - 本轮继续按 `0046/0050` 的纠偏口径审计正式结果写入链，不再把 `GameManager.InventorySystem` 直读或 `TryGetSystem<T>()` 当成问题本身。
  - 2DRPGEngine 同职责库存流程中，命令、箱子、怪物奖励、制作产出和商店交易都直接写入 `GameManager.InventorySystem`；它的重点是“库存系统是结果真相源”，不是“必须安全查询系统”。
  - 2DRPGEngine 的制作流程是 `CanCraft -> 成功提示 -> Craft`，`Craft` 直接扣钱、扣材料、写产物；该流程依赖参考工程较宽松的库存写入和单背包前提。
  - 2DRPGEngine 的商店卖出流程也直接从唯一玩家背包删除物品后给钱；该写法在参考工程成立，因为商店背包 UI 的来源就是同一个全局玩家背包，没有多 owner 背包切换面。
  - FantasyWord 的多 owner 背包是当前项目的合理增强，但旧 `InventorySystem.AddToBag/RemoveFromBag` 会在空物品或非正数量时静默返回，可能让命令、箱子首次初始化、制作产出或击杀奖励表现为执行成功但没有写入库存。
  - FantasyWord 已把库存写入坏配置升级为可定位异常；如果制作仍在成功提示后才执行坏配方写入，就会出现“已经提示成功但扣款/扣料/给产物中途失败”的退步。
  - 2DRPGEngine 的商店买入流程先扣钱再把物品写入唯一玩家背包；参考工程没有“当前交易 owner 解析失败”的失败面。FantasyWord 新增多 owner 后，买入必须先确认当前交易 owner 有效，否则会先扣钱，再在写入物品时丢失目标。
  - FantasyWord 商店 UI 当前按 `GameCommandContext` 解析交易背包 owner；沿用参考工程“删除后无条件加钱”的表面流程，会在当前 owner 物品已不存在或 owner 已切换时形成“物品没删掉但钱增加”的失败面。
  - 2DRPGEngine 的背包 UI 只显示唯一玩家背包，打开菜单时没有“当前控制角色或目标 owner 解析失败但不能误退默认队伍背包”的失败面；FantasyWord 的多 owner 菜单上下文已经故意把失败解析保持为无效 owner，因此显示层必须把无效 owner 表达为空背包，而不是继续读库存系统抛异常或回退默认队伍背包。
  - 2DRPGEngine 的消耗型物品效果在效果成功后直接从唯一玩家背包扣物品；FantasyWord 继承该流程后新增了多 owner 和可失效 UI，若仍先应用效果、播放成功提示，再忽略扣除失败，就可能出现“治疗/学技能/开任务已经生效，但来源背包没有扣物品”的退步。
  - 2DRPGEngine 的装备穿脱在唯一玩家背包内成立：卸下装备后直接把装备放回同一个全局背包。FantasyWord 新增角色/队伍/尸体等多 owner 背包后，卸下装备必须先确认回包 owner 有效，否则会先改变角色装备状态，再在回包时暴露无效 owner，形成半完成状态。
  - 2DRPGEngine 的装备附加能力直接使用装备资产里的能力引用，`Hero.Equip/Unequip` 在改变装备字典时同步加/移除能力，没有单独的能力来源身份失败面。FantasyWord 把装备附加能力迁到 Formal GAS 编码后，还要用装备在 `DatabaseRegistry` 里的稳定引用作为能力来源；如果槽位已经改变后才发现来源无法创建，就会出现“装备状态已变，但附加能力没有正确加/移除”的半完成状态。
- 决策：
  - `InventorySystem.AddToBag(...)` 和 `RemoveFromBag(...)` 必须暴露无效物品或无效数量配置，不能把坏配置当成成功 no-op。
  - 制作仍沿用参考的 `CanCraft -> Craft` 主流程，但 `Recipe` 必须在可制作判定和容量计算前验证产物、材料和额外产物配置；`CraftingStation.Craft(...)` 必须在扣钱、扣材料或添加产物前重新确认配方有效且当前 owner 仍可制作。
  - 玩家交互尝试仍可返回失败：拾取物在物品或数量无效时不拾取，UI 转移请求通过 `InventoryTransferResult` 返回失败，商店/制作 UI 仍由菜单流程给玩家反馈。
  - 商店买入继续沿用参考的直接库存写入流程，但 FantasyWord 必须在扣钱前确认当前交易 owner 有效，避免钱款结果先落地、物品结果落不到任何背包。
  - 商店卖出不是新建交易系统；它继续直接写 `InventorySystem`，但 FantasyWord 必须先确认当前交易 owner 的物品删除成功，成功后才加钱、播放交易音效并刷新 UI。
  - 背包菜单显示层可以使用非抛错查询；当菜单上下文无法解析角色、背包 owner 无效或库存系统尚未就绪时，`UIInventoryBag` 必须清空槽位并停止显示，不得读默认队伍背包、不得把视图失败升级成正式库存写入。
  - 消耗型物品效果必须在执行效果前确认来源 owner 仍有该物品；效果成功后必须先完成扣除，再播放成功音效和成功提示。若扣除失败，应暴露结果链错误，不得把成功反馈发给玩家。
  - 卸下装备仍沿用参考的“装备系统负责穿脱，库存系统负责回包”职责划分，但 FantasyWord 必须在调用角色装备状态变更前验证目标背包 owner。无效 owner 是当前项目配置/身份错误，不得先卸下装备再让回包失败。
  - 装备附加 Formal GAS 能力继续由角色装备系统随装备穿脱同步加/移除，但 FantasyWord 必须在改变装备槽位前先准备好装备能力来源。带附加能力的装备如果没有有效装备资产或未登记到 `DatabaseRegistry`，必须直接暴露配置错误，不得记录错误后继续穿脱。
  - 宝箱首次初始化属于正式结果写入链；掉落条目缺物品或数量非法时必须抛出可定位异常，不得跳过该条目后继续把宝箱标记为已打开。
  - 本决策不改变 `GameManager.InventorySystem` 作为参考衍生库存真相源的地位，也不新增第二套库存 owner。
- 影响：
  - `AddOrRemoveItem`、击杀奖励、制作产出、箱子掉落初始化和商店买入在遇到坏物品配置时会暴露配置错误。
  - 坏配方会在制作写入前暴露配置错误，不会先播放成功提示、先扣钱或先扣材料；正常配方仍直接写入 `InventorySystem`。
  - 商店买入遇到无效交易 owner 时会在扣钱前报错，不会出现“钱少了但物品没进包”的半完成状态。
  - 商店卖出失败时只反馈并刷新 UI，不写入金钱；这是当前项目多 owner 背包对参考单背包流程的必要适配，不是访问形式重构。
  - 当前控制角色不存在或 UI 请求早于系统就绪时，背包界面显示为空；这保留了“不能误读默认队伍背包”的项目约束。
  - 消耗型物品如果已经不在来源背包，会给出“已没有该物品”的反馈，不执行效果；如果效果成功后扣除失败，会抛出可定位错误，避免假成功。
  - 卸下装备遇到无效目标 owner 时会在角色装备状态改变前报错，避免装备已从角色身上消失但没有回到任何背包。
  - 带附加 Formal GAS 能力的装备若缺少数据库登记，会在装备槽位改变前报错；没有附加能力的普通装备不受影响。
  - `ExecuteTransfer` 的可失败交互语义保持不变；它仍先验证请求，再调用库存写入方法。
  - `ItemPickable` / `MoneyPickable` 这类触发器交互仍可失败，不被升级成正式结果异常。
- 替代关系：
  - 本决策是 `0050-参考流程审计结论纠偏边界` 在库存结果链上的落地案例；它不是“单例更好”或“Try 查询更差”的结论。
