# 项目目录与入口

## 适用范围

- 本文只负责说明 `FantasyWord` 的目录职责、正式入口和待整理目录。
- 旧恢复任务目录不自动成为当前正式目录合同。

## 当前工程根目录

- `Assets/`
- `Packages/`
- `ProjectSettings/`
- `docs/`
- `.codex/`
- `scripts/`
- `AIBridgeCache/`
- `docs/archive/archived-recovery/`
- `Tools/`

## 当前正式入口

- AI 主入口：`AGENTS.md`
- 文档入口：`.spec/knowledge/features/project/文档索引.md`
- 包配置：`Packages/manifest.json`
- Unity 版本：`ProjectSettings/ProjectVersion.txt`
- 输入配置：`Assets/InputSystem_Actions.inputactions`。当前已回到与 `2DRPGEngine/Mythril2D/Demo/Settings/PlayerInputActions.inputactions` 对齐的 `Gameplay / UI / None` 动作图，不再沿用旧 `Player / UI` 资产形状。

- 启动配置现态：`Assets/GameData/GameCore/GameConfig.asset` 已接入新 `GameManager`。

## Assets 目录判定

- `Assets/Scripts/Presentation/EquipmentSystem`：当前正式装备/换装表现业务目录，承载运行时渲染、编辑器工具与 Shader；不保留独立业务程序集或命名空间，旧测试面板兼容占位已从正式树移除。
- `Assets/GameData/EquipmentSystem`：当前装备/换装相关 ScriptableObject 数据，已从旧 `Assets/Data` 迁入并保留 `.meta`。
- `Assets/GameData/GameCore/Modules`：旧五大默认模块资产目录当前不存在；不得重新创建为正式目录合同。
- `Assets/GameData/Combat/Definitions`：旧 EX-GAS 项目侧候选样例资产目录当前不存在；正式 EX-GAS 接入前需重新建参考矩阵。
- `Assets/GameData/Presentation/Audio`：旧 BroAudio 项目侧候选样例资产目录当前不存在；正式表现/音频接入前需重新建参考矩阵。
- `Assets/GameData/Items/Equipment`：旧 EquipmentSystem 项目侧样例资产目录当前不存在；当前装备候选数据以 `Assets/GameData/EquipmentSystem` 为准。
- `Assets/Scenes/SampleScene.unity`：当前已按 `2DRPGEngine` 参考把宿主对象命名统一为 `Game Manager`，并挂 `FantasyWord.GameCore.GameManager`；不再挂旧 `FantasyWordBootstrapper` 和 `FantasyWordModuleInstaller`。场景内也已按 `2DRPGEngine` 参考补齐正式系统闭包与必要子树，包括 `Input / Inventory / Dialogue / Audio / Player / UI / Game State / Journal / Map / Game Flag / Persistence / Transition / Save`。旧 `Notification System` 场景对象已退场。当前正式裁决是“单一 `GameManager` 组件宿主 + 场景级系统对象平铺”，不是“一个总 prefab 把所有系统收成子节点”；`2DRPGEngine` 和 `TopDownEngine` 的本机场景复核都不支持后者作为默认最佳实践。玩家实体不再由 `PlayerSystem` 动态生成，正式场景直接预摆 `玩家角色`，并由 `PlayerSystem.m_playerInstance` 序列化绑定场景内 `Hero`；缺少该引用时必须按配置错误报错并中断，不允许运行时搜索、自动新建或自动替代。
- `Assets/Scenes/ClickMoveTest.unity`：目标中的基础点击移动/WASD 切换验证场景，设计口径仍是沿用 `SampleScene` 的 `Game Manager + 平铺系统对象 + 预摆 玩家角色`，并且只应用于现有 `Movable / PlayerController / IPlayerInputTarget` 闭包验证，不允许新增同职责测试控制器。
  但当前静态门禁已确认该场景和 `.meta` 尚未被 git 跟踪，因此它现在不能继续被当成“已纳入正式版本控制的验证场景真相”来引用或验收。
- `Assets/Scenes/EquipmentSystemDemo.unity`：EquipmentSystem 独立 smoke 场景；用于承载换装表现宿主，不和正式启动场景混放。
- `Assets/ThirdParty/MiniFantasyUV`：MiniFantasy UV 资源/来源链证据，默认先作为正式换装资源追溯入口保留。
- `Assets/Art`、`Assets/Minifantasy_NPCs_Assets`、`Assets/ArtRes`：MiniFantasy 与当前像素素材主来源，重整前先保留。
- `Assets/Art/MINIFANTASY - Crafting and Professions I/Scenes`、`Assets/Art/MINIFANTASY Creatures - Super Low Res 2D Pixel Art by Krishna Palacio/Scenes`：MiniFantasy 素材包自带 demo 场景，当前作为来源证据和接线参考保留原目录结构，不等于正式玩法场景入口，但未经用户允许不得移出。
- `Assets/Plugins`：第三方插件落点，当前包含 GAS、YokiFrame、DOTween、TopDownEngine、BroAudio 项目级配置资源及若干已导入插件；导入且能编译的插件默认可以按自身职责使用，且同职责优先用插件原能力，不在项目侧重造一套。完整清单和正式 owner 边界以 `.spec/knowledge/features/project/第三方插件接入清单.md` 为准。UniTask 当前落点是 `Packages/com.cysharp.unitask`，不是 `Assets/Plugins/UniTask`。
- `Assets/Database`、`Assets/Prefabs`：旧 RPG 业务数据库和业务 Prefab，当前已恢复到 `Assets` 正式入口；它们是否继续迁移、重构或替换，要按新项目业务矩阵逐项决策，不能先归档后再考古。
- 当前正式玩家资产命名已收口到中文：`Assets/Prefabs/Entities/Characters/Heroes/玩家角色.prefab`、`Assets/Database/Characters/Heroes/玩家角色配置.asset`、`Assets/Sprite Libraries/Characters/玩家角色精灵库.spriteLib`。第三方原始素材仍保留原来源目录，不等于正式玩家继续沿用旧占位名。
- `Assets/Editor/GameCore`：当前已接入与 `2DRPGEngine` 对齐的轻量编辑器工具，包含 `SceneUtil` 和检查点/引用 PropertyDrawer；只服务已迁入的 GameCore 最小闭包。
  当前人类可见的 Unity `场景/*` 菜单的单一真相源是 `Assets/Scenes` 下的 `.unity` 文件；`场景/刷新场景菜单` 只扫描该目录并生成菜单。`EditorBuildSettings` / Build Settings 只负责构建配置，不参与编辑器场景菜单列表裁决。
- `Assets/Editor/com.IvanMurzak`：旧 UnityMCP 安装器已删除，不作为正式编辑器工具入口。
- `Assets/Resources/Unity-MCP-ConnectionConfig.json`：旧 UnityMCP 配置若再次生成，说明当前 Unity Editor 仍有旧插件会话残留；应删除并刷新包解析。
- `Assets/_Recovery`：旧 Unity 恢复场景已删除；历史线索只保留在 `docs/archive/archived-recovery/`。
- `Assets/Scripts/test`：项目侧临时验证、试验性脚本和未进入正式边界的试做代码目录；自动化测试仍放 `Assets/Tests`。若为空，不保留空目录占位。
- `Assets/Resources`：若为空，不保留空目录占位；需要正式入口时再按规范创建。

## 目录裁决

`Editor` 和 `GameCore` 的放法不是沿用现状，而是按 `设计模式 / 软件工程 / 易用` 的正式裁决。若需要更直接的胜负理由，先看 `框架三项判分矩阵.md`，这里再把结论落到目录边界：

| 目录决策 | 正式动作 | 设计模式理由 | 软件工程理由 | 易用理由 | 不选什么 |
| --- | --- | --- | --- | --- | --- |
| `Assets/Scripts/GameCore/Runtime` | 保留为正式 runtime 总根 | 在世界层、角色层、表现层都尚未形成独立真相源前，`GameCore` 承担的是“RPG 世界规则真相 + 吸收后的动作/工具正式入口”这段连续职责；先拆顶层目录只会制造伪分层 | 先把序列化、Prefab 接线、场景宿主、系统入口和门禁集中在一个稳定根上，能减少迁移期的状态分叉、漏改和错误归因 | 维护者只需要记住“地基 runtime 去 `GameCore/Runtime`”，不必先猜哪些目录已经是正式产品层 | 不选“为了看起来更像最终产品结构，先拆成 `World/Characters/Combat/Presentation/...` 多个顶层目录” |
| `Assets/Editor/GameCore` | 保留为只服务 `GameCore` 的编辑器根 | 编辑器工具服务运行时资产、检查器、验证器和 AIBridge 恢复入口，不是玩法系统本身 | 直接服从 Unity `Editor` 编译边界，天然阻断编辑器代码误进运行时程序集、玩家构建和序列化引用闭包 | 对 Unity 使用者来说，找 PropertyDrawer、EditorWindow、验证器时入口最直观 | 不选“运行时和编辑器脚本按功能混放，只靠 asmdef 或命名约定区分” |
| `Assets/Plugins/TopDownEngine` 与 `Assets/Plugins/YokiFrame` | 保留第三方来源边界，项目侧只吸收胜出的模式、正式入口和工具入口 | 第三方框架的职责是提供参考实现或工具能力，不是伪装成项目自有模块 | 保留来源结构更利于升级、对照、问题归因和门禁，也能防止把第三方 manager 误当项目正式入口 | 开发者能立刻分清“第三方原件在哪”“项目正式真相在哪” | 不选“把第三方源码剪碎并回项目目录，或额外包一层兼容目录” |
| `Assets/Scripts/World`、`Assets/Scripts/Characters`、`Assets/Scripts/Items`、`Assets/Scripts/Combat`、`Assets/Scripts/Presentation` | 只保留为未来晋升目标，不提前迁正式闭包 | 只有当系统已脱离参考直拷闭包、形成 FantasyWord 自己的独立真相源时，这些目录才有真实职责 | 现在提前晋升会扩大引用闭包和回归面，并重新制造“地基代码”和“产品层代码”的边界混乱 | 认知负担最低的规则是：未形成独立真相源的代码继续留 `GameCore` | 不选“先建一套好看的产品目录，再把仍受同步/parity 门禁约束的代码搬过去” |

- 这里的“合理”不是抽象结论，可以直接对照参考源码目录看：

| 参考目录 | 当前目录 | 正式动作 | 理由 |
| --- | --- | --- | --- |
| `C:/Gamedev/Unity/Engine/2DRPGEngine/Assets/Mythril2D/Core/Runtime/Scripts/*` | `Assets/Scripts/GameCore/Runtime/*` | 保留同一 runtime 总根 | 这部分是 `2DRPGEngine` 的世界规则与运行时宿主闭包。当前项目还没有把这些职责拆成 FantasyWord 自己的独立真相源，所以不应提前散拆。 |
| `C:/Gamedev/Unity/Engine/2DRPGEngine/Assets/Mythril2D/Core/Editor/Scripts/*` | `Assets/Editor/GameCore/*` | 保留同一 editor 支撑根 | 这部分是 Inspector、PropertyDrawer、EditorWindow、Playtest 支撑，不是玩法系统；按 Unity `Editor` 边界分开才是正确职责。 |
| `ReferenceSources/TopDownEngine/Assets/TopDownEngine/Common/Scripts/Characters/*`、`MMFeedbacks/*` | `Assets/Scripts/GameCore/Runtime/Combat/*`、`Presentation/*`、`Animation/*` 的正式吸收点 | 只吸收胜出的动作模式，不照抄目录当项目总根 | `TopDownEngine` 在动作能力、武器、命中、反馈上更强，但它强的是模块，不是“Common 目录本身适合作项目根”。 |
| `ReferenceSources/TopDownEngine/Assets/TopDownEngine/Common/Scripts/Managers/*`、`GUI/*`、`ScriptsInputSystem/*` | 不进入项目正式总根；只保留为参考源或第三方来源边界 | 冻结为非正式宿主 | 这些目录会把 `LevelManager/InputManager/GUIManager` 一起带入项目生命周期，违反单一真相源。 |
| `Assets/Plugins/YokiFrame/Core/Runtime/PoolKit/*`、`Tools/SaveKit/*`、`InputKit/*`、`UIKit/*` | 项目运行时只保留调用点，例如 `SaveSystem`、`InputSystem`、`FloatingTextPool` 等 | 直接用工具，不复制第二份实现 | `YokiFrame` 赢的是工具层。项目只该保留使用点，不该再自造一层同职责工具目录。 |

- `Assets/Scripts/GameCore/Runtime` 与 `Assets/Editor/GameCore` 的分离是正式裁决，不是临时摆放。它先服从 Unity 自己的 `Editor` 编译边界，再与 `2DRPGEngine/Assets/Mythril2D/Core/Runtime/Scripts` / `Core/Editor/Scripts` 的参考分层保持一致；后者是佐证，不是理由本身。
- `GameCore` 仍是项目地基的单一正式闭包。只要某段代码还同时承担 RPG 世界规则真相、场景/Prefab 正式接线入口，或仍未脱离“吸收后的统一运行时宿主”这一职责，就不要为了“更像最终产品目录”把它提前拆散到多个顶层模块。
- `Assets/Editor/GameCore` 只放服务 `GameCore` 的编辑器工具、PropertyDrawer、验证器、AIBridge 编辑器恢复入口和文档窗口；它们不是玩法系统，不应混回 `Assets/Scripts/GameCore/Runtime`。
- `Assets/Plugins/TopDownEngine` 与 `Assets/Plugins/YokiFrame` 保留来源边界。项目侧只能吸收胜出的系统模式、正式入口和工具调用点，不把第三方源码剪碎并回项目自定义目录。
- `Assets/Plugins/TopDownEngine` 里的 demo 图片、Tile、Prefab、场景、音频和 UI 资源只属于参考工程随带资源，不是 FantasyWord 正式美术来源；正式美术以 MiniFantasy 为基线。
- `Assets/Scripts/World`、`Assets/Scripts/Characters`、`Assets/Scripts/Items`、`Assets/Scripts/Combat`、`Assets/Scripts/Presentation` 目前只是未来产品层级的目标目录，不代表现在就该把 `GameCore` 里的现有闭包提前迁过去。
- 顶层产品目录何时可以建立，判断标准不是“目录好不好看”，而是：这个系统是否已经脱离参考直拷闭包、形成 FantasyWord 自己的独立真相源、并且继续保留在 `GameCore` 里反而会混淆职责。没有这三个条件，就继续留在 `GameCore`。

## 目标目录合同草案

- `Assets/Scripts/GameCore`：当前正式地基闭包。凡是仍直接承载 `2DRPGEngine` RPG 世界规则真相，或只是吸收 TopDown/Yoki 优势但还没有独立成项目自有模块的代码，都继续留这里。
- `Assets/Scripts/Characters`：玩家、NPC、怪物和可交互角色的项目自有顶层目录。只有当对应代码不再只是 `GameCore` 地基的一部分，而是 FantasyWord 已独立成形的角色层真相时，才从 `GameCore` 晋升出来。
- `Assets/Scripts/World`：地图、区域、采集点、场景对象和世界交互的项目自有顶层目录。只有当区域/Cell、队伍、派系、AI 日程、经济或局部模拟等世界层能力真的进入正式实现时才建立；当前不得为了占位先拆目录。
- `Assets/Scripts/Items`：未来正式物品、装备、背包、掉落和制作闭包预留目录；当前不要把候选代码继续放进来制造误解。
- `Assets/Scripts/Combat`：俯视角战斗、伤害、技能、状态效果的项目自有顶层目录；仅在战斗层已不再只是 `GameCore` 地基吸收项时建立。
- `Assets/Scripts/Presentation`：角色表现、动画、相机、视觉反馈的项目自有顶层目录；当前许多表现能力仍是地基吸收项，未必要急着迁出 `GameCore`。
- `Assets/Scripts/GameCore/Runtime/Resources`：Chris 资源层吸收落点，负责 Addressables 运行时加载、句柄释放、软地址引用和外部 catalog 加载；不替代 `DatabaseRegistry` 的玩法数据真相。
- `Assets/Scripts/GameCore/Runtime/Mods`：Chris Mod 层吸收落点，负责本地 `Mods` 目录扫描、zip 解包、启停状态、API 版本校验和加载启用 Mod 的外部 catalog；完整数据合同、脚本沙箱和创意工坊不在当前目录合同内。
- `Assets/Scripts/Networking`：当前不建立；FishNet 是后续联机阶段有限人数主机权威合作的首选评估框架，不能为了预留而堆空壳。只有联机专项正式立项、验收入口明确并确认不会污染单机核心时，才允许创建具体网络适配目录。
- `Assets/Scripts/Mods`：当前不建立顶层空壳；已进入正式范围的本地 Mod 加载能力落在 `GameCore/Runtime/Mods`。只有当 Mod 形成独立产品层真相，例如内容编辑器、发布工作流、脚本沙箱或创意工坊适配，才考虑晋升为顶层目录。
- `Assets/Scripts/test`：临时验证、试验脚本和待定代码，不算正式模块目录。
- `Assets/GameData`：ScriptableObject、配置、数据库资产和可 diff 设计数据。
- `Assets/GameData` 后续要兼容“官方内置内容包 + 外部 Mod 内容包”的思路；新增正式数据时应保留稳定 ID、来源归属和版本迁移空间，不能只按当前场景样例硬编码。
- `Assets/Prefabs`：正式 Prefab；当前为空或未建立时不要用旧 RPG Prefab 顶替。
- `Assets/Scenes`：正式场景和测试场景。
- `Assets/Editor`：正式编辑器工具。
- `Assets/Tests`：Unity Test Framework 测试。
- `Assets/ThirdParty` 或 `Assets/Plugins`：第三方插件、外部框架和需要保留来源结构的资源。
- `scripts`：只放不启动 Unity 的仓库维护脚本；涉及 Library 恢复、Unity 进程或资产导入的脚本必须先单独确认。

## 待整理原则

- 目录重整前，先确认当前引用和 `.meta`/GUID 关系。
- 可移动资源优先用 Unity/AssetDatabase 或保留 `.meta` 的文件级迁移方式。
- 第三方插件、第三方素材包和参考工程原始内容默认保留原目录结构；未经用户明确允许，不得为了“看起来更整齐”强制并入项目自定义目录。
- `scripts/Sync-2DRPGFoundation.ps1`、`Test-FoundationReferenceParity.ps1` 和 patched 台账是迁移期执行门禁，不是目录裁决的根本理由；它们只负责证明当前执行没有偏离既定裁决。
- 只要某个运行时闭包还受 `scripts/Sync-2DRPGFoundation.ps1`、`Test-FoundationReferenceParity.ps1` 和已登记 patched 台账共同约束，就默认继续留在 `Assets/Scripts/GameCore/Runtime`，不要提前拆到新的顶层产品目录。
- 只有当某个系统已经形成 FantasyWord 自己的独立真相源，并且继续留在 `GameCore` 反而会误导职责时，才允许把它晋升到 `Assets/Scripts/World`、`Characters`、`Combat`、`Presentation` 等项目顶层目录。
- 若 `GameCore` 中同职责正式闭包已经存在，例如当前 `Movable + IController/AController/PlayerController` 玩家控制器闭包，不得再在 `Assets/Scripts/test` 或测试场景中另起一套并行控制器来证明“先能跑”；只有在参考缺口已被证据锁定、且无法直接在现有正式闭包上对齐时，才允许先补流程理由文档，再由用户决定是否保留临时试做代码。该文档默认写到当前活跃 `openspec/changes/<change-id>/parallel-trial-rationale-<topic>.md`。
