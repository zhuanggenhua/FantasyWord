# 框架代码现态矩阵

> 用途：把 `GameCore` 当前正式运行时代码与框架裁决逐项对照。
> 这份文档只回答“代码现在到底收口到哪了”，不重新决定谁该赢。
> 胜负理由仍以 `框架最终裁决.md`、`框架三项判分矩阵.md`、`三方框架系统对照.md` 为准。

## 读取规则

- 这里只看 `Assets/Scripts/GameCore/Runtime` 和 `Assets/Editor/GameCore` 的正式代码现态。
- 搜索命中分两类：
  - `真实运行时依赖`：会进入正式代码行为。
  - `注释/Inspector 说明`：只用来解释吸收来源，不代表直接依赖第三方 manager。
- 这里的“已成立”表示代码现态已经支持对应裁决，不代表整条玩法链已经全部完成。

## 一页结论

- `2DRPGEngine` 作为世界规则真相源，这一点代码现态已经成立。
- `TopDownEngine` 作为动作表现层胜者，这一点代码现态已经成立到“核心闭包已吸收”，但更多表现接线仍未完全收口。
- `YokiFrame` 作为工具层胜者，这一点代码现态已经成立到“对象池、SaveKit、InputKit 已切入，正式菜单运行时也已收口到 `UIManager + UIKitMenuPanelBase + UIKit`”，但部分共享构件、非菜单 utility panel 和资源命名仍可能继续收口。
- 当前代码现态没有证据表明 `TopDownEngine` manager、`InputManager`、`GUIManager` 或 `LevelManager` 已被正式升格进 `GameCore`。
- `GameManager.Player` 静态快捷别名已从正式运行时代码移除，玩家长期真相入口只保留 `PlayerSystem.PlayerInstance`。

## 边界证明

### `TopDownEngine` manager 没有进正式运行时

当前命中的 `InputManager / LevelManager / GUIManager` 只有 4 处，而且全部是注释或 Tooltip：

- `Entities/Movable.cs`
- `Game/Systems/InputSystem.cs`
- `Game/Systems/MapSystem.cs`
- `Maps/MapInfo.cs`

它们的作用是说明“吸收了什么思路、没有接入什么 manager”，不是运行时依赖。

### `MoreMountains` 当前只剩一个正式反馈闭包

当前 `using MoreMountains` / `MoreMountains.` 在正式运行时代码里只命中：

- `Presentation/GameplayFeedbackSet.cs`

这说明当前不是把 TopDown/MoreMountains 生态直接散落接进业务代码，而是收口到一个正式表现闭包。

## 残留项说明

### `FloatingTextPool` 仍然存在，但它已不是旧对象池

`UI/FloatingTexts/FloatingTextPool.cs` 名字还保留着“Pool”，容易误读成旧池残留，但从代码语义看，它现在只负责：

- 浮字排队
- 播放节流
- 向 `GameObjectPoolService` 租还实例

它不再维护独立池实现，也不再和 `GameObjectPoolService` 并列竞争对象池真相。

因此当前应把它理解为：

- `浮字播放队列服务`

而不是：

- `第二套对象池`

## 当前仍未证明的部分

- 当前代码还没有证明开放世界模拟层已经形成正式实现。
- 当前代码还没有证明点击移动、自动靠近、实例宿主、出生点分流这些一级缺口已经被补齐。
- 当前代码已经证明“正式菜单运行时”这条 UI 主线已迁到 `UIKit`，并收口为 `UIManager + UIKitMenuPanelBase + UIKit`；但共享构件目录、非菜单 utility panel 与部分资源命名仍不是最终收口状态。
