# 2D移动与场景组织现态速查表

> 用途：把当前这条线压成一页可执行现态。
> 只回答三件事：本机已经证实了什么、本机已经明确排除了什么、下一步还应该找什么。

## 一句话现态

- 这 4 个一级缺口只描述 `2D 移动与场景组织` 当前还缺什么正式参考。
- 它们不等于开放世界模拟层的长期缺口；后者仍是另一层尚未开工的架构任务。

- 当前正式缺口仍是 **4 个一级框架缺口**：
  1. 单机/本地 2D 导航 Provider
  2. 2D 点击移动执行闭包
  3. 单机/本地场景实例宿主参考
  4. 单机/本地出生点分流宿主参考
- 依赖它们展开的 **3 个二级缺口** 仍只登记：
  1. 控制对象与世界穿越目标统一
  2. 超距后自动靠近再施法/交互
  3. 传送入口条件
- 当前不新增并行运行时代码；现有 `Movable / PlayerController / IPlayerInputTarget` 闭包里已经存在当前基础点击移动链路，但它只代表“点地后按当前 2D 直线移动闭包靠近”，不代表完整 2D 寻路 Provider 已经补齐，也不构成继续进入实现态的批准。

## 场景宿主现态证据

这部分只回答一个问题：参考项目的场景宿主到底是不是“一个 `GameManager` prefab，子节点挂所有系统”。

| 来源 | 本机看到的场景形状 | 玩家放置方式 | 对当前项目的意义 |
| --- | --- | --- | --- |
| `FantasyWord/Assets/Scenes/SampleScene.unity` | `Game Manager`、`Input System`、`Inventory System`、`Journal System`、`Save System`、`Game State System`、`Game Flag System`、`Map System`、`Dialogue System`、`Player System`、`Persistence System`、`Audio System`、`Transition System`、`UI System` 都是场景根对象；旧 `Notification System` 已退场 | `玩家角色` 玩家 prefab 直接预摆在场景里，并由 `PlayerSystem.m_playerInstance` 序列化绑定场景内 `Hero`；缺少该序列化引用时必须按配置错误报错并中断 | 当前正式场景已经是“单一生命周期宿主 + 场景级系统对象平铺 + 玩家实体预摆”，不是缺正式宿主，也不再沿用运行时生成玩家 |
| `FantasyWord/Assets/Scenes/ClickMoveTest.unity` | 当前目标中的候选验证场景，设计口径沿用 `SampleScene` 的 `Game Manager + 平铺系统对象 + 预摆 玩家角色`，但不再与正式场景并列描述 | `玩家角色` 同样预摆在场景里，主要用于现有 `Movable / PlayerController / IPlayerInputTarget` 闭包的候选验证 | 它只能证明当前候选验证链路长什么样；不能再拿来充当正式场景真相 |
| `2DRPGEngine/Assets/Mythril2D/Demo/Scenes/M2DEngine.unity` | 有单独的 `Game Manager` 根对象；`Input/Inventory/Journal/Notification/Save/Game State/Game Flag/Map/Dialogue/Player/Persistence/Audio/Transition/UI` 也是各自独立根对象 | `Player System.m_dummyPlayerPrefab` 负责运行时生成玩家 | 这是当前项目最直接的场景宿主参考；它支持“宿主对象 + 平铺系统”，不支持“单一总 prefab 收全部系统”。但玩家生成方式已被当前项目裁决替换为场景预摆 |
| `TopDownEngine/.../Demos/Minimal2D/MinimalScene2D.unity` | 根对象是 `GameManager`、`SoundManager`、相机 prefab 根 `Minimal2DCameras --------------------------------------------------------` 和 `Level`；`Level` 下再挂 `LevelManager` 等对象 | `LevelManager.PlayerPrefabs + InitialSpawnPoint` 负责运行时生成玩家 | 它同样不是单一总 prefab；它证明“场景有正式宿主和出生点，但玩家仍可运行时生成” |
| `uMMORPG/.../Scenes/World.unity` | 只有一张 `World.unity` 主场景，旁边挂着 `NavMesh-Environment.asset`、`NavMesh-Dungeon.asset`；根对象是 `NetworkManager`、`Environment`、`Main Camera`、`Minimap Camera`、`Directional Light`、`EventSystem`、多个 `Portal/Respawn` 与 UI 根对象混放 | MMO 单场景入口，不是当前单机玩家宿主样板 | 它只能作为负证据：说明 `uMMORPG` 的产品型单大场景组织不应拿来替换当前 `Game Manager + 平铺系统对象 + 预摆玩家角色` 裁决 |
| `RTS Starter Kit/Assets/Scenes/SampleScene.unity` | 当前只看到 `Main Camera`、`Directional Light`、`Global Volume` 三个根对象 | 不是单角色 RPG 的运行时宿主样板 | 这条参考更适合拿命令链、订单队列和选择逻辑，不适合拿来裁决当前单角色场景宿主结构 |

补充：

- `ClickMoveTest.unity` 现在按场景自身配置直进验证；是否黑屏、是否显示 UI，不再通过 `EditorPlayModeOverride`、marker 或 playtest snapshot 偷换启动链。
- 但它当前仍只是候选验证场景，不与 `SampleScene` 共享“正式场景”口径。

当前正式结论已经固定：

- 本机参考里没有证据支持“一个 `GameManager` prefab，子节点挂所有系统”是默认更优做法。
- 当前项目的场景宿主应继续沿用 `2DRPGEngine` 这条线：一个正式 `GameManager` 宿主对象，外加场景级系统对象平铺。
- 当前命名已经收口到参考的 `Game Manager`；这只是命名对齐，不是把整个系统层级改成单一总 prefab。

## 本机已融合到现有正式闭包

这些不是把 `uMMORPG` 的同职责实现重复搬进来，而是把能脱离 Mirror、3D NavMesh 和 MMORPG 业务的源码规则，作为合同/规则/健壮性补强融合进当前已有 `GameCore` 正式闭包：

| 已融合/补强项 | 来源证据 | 当前项目落点 |
| --- | --- | --- |
| 移动重置、传送落点修正、出生点合法性检查、最近合法落点合同 | `uMMORPG Movement.cs` | `Movable.cs` |
| `Navigate(destination, stoppingDistance)` 的停止半径合同 | `uMMORPG Movement.cs` | `Movable.cs` |
| 手动方向输入先取消旧导航路径 | `uMMORPG PlayerNavMeshMovement.MoveWASD()` | `Movable.SetMovementDirection(...)` |
| 失效保存位置回退到正式出生点 | `uMMORPG Database.CharacterLoad()` | `MapSystem.LoadDataBlock(...)` |
| 子碰撞体回溯正式玩家实体 | `uMMORPG Portal.cs` | `Teleporter.OnTriggerStay2D(...)` |

### 融合内容说清楚

这里的“融合/补强”不是把 `uMMORPG` 的导航系统、传送系统或副本系统整套搬进来，也不是并行保留第二套实现；它只代表现有正式闭包采纳了几条已经有源码证据支撑的规则：

- `Movable` 已融合/补强：移动重置、传送落点修正、出生点合法性检查、最近合法落点、停止半径到达判定、直接方向输入取消旧移动命令。
- `MapSystem` 已融合/补强：读档恢复当前地图时，若保存位置已对当前 2D 碰撞闭包失效，回退到正式出生点。
- `Teleporter` 已融合/补强：传送入口从子碰撞体向父级回溯正式玩家实体。
- 未吸收：`NavMeshMovement / RegularNavMeshMovement / PlayerNavMeshMovement.MoveClick()` 的完整导航实现，因为它们强绑 `NavMeshAgent`、Mirror 同步、本地相机和 3D 射线。

### 和总框架吸收清单的关系

本节只说 `uMMORPG` 在 `2D 移动与场景组织` 里已经融合到现有闭包的合同/规则/健壮性补强，不是整个地基总表，也不代表重复搬了一套 `uMMORPG` 实现。

完整框架里已经进入正式代码的还包括：

- `2DRPGEngine` 的世界规则地基：`GameManager + AGameSystem`、数据库、地图、检查点、传送、存档、持久化、背包、任务、角色和控制器闭包。
- `TopDownEngine` 的动作表现层：移动手感参数、能力权限与阻断、武器执行状态机、命中窗口、击退/短暂无敌、拾取/交互/受击/死亡反馈，以及地图边界、默认出生点、检查点顺序、重生延迟和相机目标样板。
- `YokiFrame` 的工具层：`GameObjectPoolService` 对象池、`SaveKit` 文件槽位/版本/头部元数据、`InputKit` 重绑定和冲突查询。

这些融合项的权威入口仍是 `.spec/knowledge/features/project/三方框架系统对照.md`、`.spec/knowledge/features/project/框架代码现态矩阵.md` 和 `openspec/changes/define-fantasyword-foundation-framework/framework-completion-audit.md`；本表只负责压缩 `2D 移动与场景组织` 这条线的参考缺口。

## 本机仍保留为 A 级证据，但不能直接实现

这些源码点仍是当前最值钱的本地证据源，但作用是**证明边界和规则**，不是直接搬完整实现：

| A级证据源 | 命中缺口 | 现在能证明什么 | 现在还不能做什么 |
| --- | --- | --- | --- |
| `uMMORPG Movement.cs` | 2D 导航 Provider | 移动/导航/传送/出生点合法性应拆开；`CanNavigate / Navigate / IsValidSpawnPoint / NearestValidDestination / stoppingDistance` 是值得保留的职责合同 | 不能直接当单机/本地 2D 导航 Provider 实现，因为具体实现落在 `NavMeshMovement` 的 `NavMeshAgent` 体系里 |
| `uMMORPG PlayerNavMeshMovement.cs` | 点击移动执行闭包 | 最近合法落点、WASD 取消旧路径是成熟规则 | 不能直接当 2D 点击移动正式闭包 |
| `uMMORPG Instance.cs` | 场景实例宿主参考 | 实例宿主至少要显式承载入口、归属、边界、实例内出生点、清理策略 | 不能直接当当前单机实例宿主实现 |
| `uMMORPG NetworkManagerMMO.GetStartPositionFor(...) + NetworkStartPositionForClass.cs` | 出生点分流宿主参考 | 分流应归正式宿主，专用入口缺失时要回退默认入口 | 不能直接当当前项目出生点分流实现 |

## 关于 `uMMORPG` 的当前正式口径

`uMMORPG Remastered - MMORPG Engine [2.41]` 现在已经固定成下面这句：

- 它只算 **2D 移动与场景组织的局部源码证据源**
- 它**不是**当前项目的联机实现基线
- 它**也不是**开放世界模拟层基线

它现在会让人误以为“像开放世界/MMO”，主要是因为本机源码里确实能看到：

- `PartySystem / GuildSystem / SafeZone / Instance / Portal`

但这和“已经形成开放世界模拟宿主闭包”不是一回事。

当前证据是：

- 能明确看到：`PartySystem / GuildSystem / SafeZone`
- 进一步能确认：`SafeZone` 本体只是 BoxCollider gizmo 标记，运行时真正保存的是 `Entity.inSafeZone` 这类局部布尔状态；玩家复活写在 `Player.UpdateServer_DEAD()`，怪物复活写在 `Monster` 自己的状态机里，没有统一 `Respawn` 宿主
- `MovementSystems` 目录也已经扫到边界：`NavMeshMovement.cs / RegularNavMeshMovement.cs` 继续只算 `NavMesh + Mirror` 负证据，`PlayerCharacterControllerMovement.cs + CharacterController2k.cs` 继续只算 `Mirror + 3D CharacterController` 负证据；真正还保留局部移动参考价值的，只剩 `Movement.cs` 与 `PlayerNavMeshMovement.cs`
- 没发现：`World / Cell / Faction / Economy / Base / Settlement / Region / Schedule` 这类开放世界模拟宿主闭包

所以它最多只能补：

- 移动合同
- 点击移动规则证据
- 实例宿主职责证据
- 出生点分流职责证据

它补不了当前项目真正缺的开放世界模拟层。

## 现在最该外找什么

优先顺序已经固定：

1. 单机/本地 2D 导航 Provider
2. 2D 点击移动执行闭包
3. 单机/本地场景实例宿主参考
4. 单机/本地出生点分流宿主参考

原因：

- 前两个一级缺口，本机参考池已经扫到当前边界；
- 后两个虽然有局部职责证据，但还没有可直接搬的单机/本地正式闭包；
- 点击移动、自动靠近、控制组穿越都会先卡在前两个一级缺口上。

补充：

- 对 `uMMORPG` 来说，当前已经不需要再反复翻 `MovementSystems` 目录；它的目录级裁决已经固定。
- 后续若没有新的 `uMMORPG` 文件进入视野，优先去补外部新参考，而不是回头重审这批 `NavMesh / CharacterController / Mirror` 运动实现。
