# 框架与运行时入口

## 适用范围

- 本文定义 `FantasyWord` 的运行时目录、框架级能力和正式边界。
- 本项目是俯视角开放世界像素游戏，不沿用 `dark-corridor` 的横版平台动作运行时合同。
- 当前阶段的正式框架变更以 `openspec/changes/define-fantasyword-foundation-framework/` 为主入口；该 change 已改为以 `2DRPGEngine` 的 `GameManager + AGameSystem` 作为最小可信基线，旧 `Bootstrapper/RuntimeContext/ModuleInstaller/EventBus` 方案不得继续作为完成状态。
- 按 `Skyrim + Kenshi` 目标复核后，`GameManager + AGameSystem` 只能视为启动宿主和 RPG 基线，不是完整开放世界架构。后续必须补 FantasyWord 自己的开放世界模拟层。
- 本文若提到 `2D 移动与场景组织` 的 4 个一级缺口，它们只描述那条线当前缺什么正式参考，不代表开放世界模拟层也被同一组缺口覆盖。

## 正式运行时方向

- 当前正式方向是单机优先核心；有限人数主机权威合作是确定目标，但当前不接入网络框架。
- 核心规则放在项目侧 C#、ScriptableObject 和可审计数据中。
- 场景、Prefab、Animator、Tilemap 和 UI 只承载初始引用、视觉表现和编辑辅助。
- 输入、世界事件、存档状态和表现层要能拆开，这是单机可维护性、长期扩展、Mod 兼容和确定联机目标共同要求；当前不创建网络空框架，也不保留联机占位层。
- Mod 支持是长期必须目标。运行时地基必须保留可扩展内容边界：数据项使用稳定 ID 或数据库引用，资源引用通过可替换的资源键/数据库入口收束，存档字段要考虑版本迁移和缺失内容回退；当前已吸收 Chris 的最小本地 Mod 加载器和资源 catalog 加载能力，但外部脚本沙箱、创意工坊接入和完整 Mod 数据合同仍未裁决。
- 新增开放世界系统不得继续扩张 `GameManager.*` 静态快捷入口。`GameManager` 保留启动和系统生命周期职责；区域、队伍、派系、AI 日程、经济和局部模拟要通过明确 Module Interface 进入正式代码。
- 新增游戏内卡牌/类昆特牌局内模式不得复用开放世界运行时作为牌局真相。它是本游戏的一部分，可以依赖玩家长期数据、存档/背包、奖励出口、资源、音频、UI 服务和 Mod 内容表；但单局牌库、手牌、弃牌、场面、回合、分数、效果栈和模式输入应由独立 `ModeRuntime` 或同级宿主持有。
- 单例不是默认架构答案。`GameManager.Instance` 当前只允许作为项目启动锚点；领域状态、开放世界状态、牌局状态和 UI 栈状态不得继续因为访问方便而扩张到全局单例。
- 当前不是先装大框架的阶段。Unity Behavior、GOAP/Utility AI、DOTS/Entities 只作为候选参考；工作区虽已导入 `Assets/Plugins/AStar 2D Grid Pathfinding` 本地候选源码，但它当前也只按局部参考保留。无论是否已在仓库里，都必须先有对应功能和验收场景，才能升格成正式依赖或落到项目运行时闭包。

## 裁决入口

- 运行时框架的胜负判断先看 `框架三项判分矩阵.md`，再看 `三方框架系统对照.md` 的长解释。
- 本文负责把裁决落到“运行时边界和入口职责”，不是再用一遍“当前仓库里已经有什么”倒推结论。
- 因此下面的 `GameCore`、`Editor`、`Plugins`、`World/Characters/...` 边界，都是三项裁决的结果；现态只用于证明执行有没有偏离，不反过来充当理由。

## 目录边界

- `Assets/Scripts/GameCore`：游戏启动、系统生命周期、配置、后续 Database/Map/Persistence 等成熟闭包落点。
- `Assets/Scripts/Characters`：只有角色闭包进入正式范围后才创建或恢复；玩家身份、角色数据和存档语义优先对齐 `2DRPGEngine` 的 `Hero/CharacterBase/CharacterSheet`，移动和能力组件执行优先吸收 `TopDownEngine` 的 `CharacterAbility/CharacterMovement/TopDownController2D` 模式。
- `Assets/Scripts/World`：只有地图、区域/Cell、采集点、交互对象、队伍、派系、AI 日程、经济/生产和世界状态进入正式范围后才创建或恢复；地图/传送参考面优先对齐 `MapSystem/MapInfo/Teleporter/IInteraction`，开放世界模拟参考面优先对齐 Skyrim 的 Cell/Worldspace、Quest Alias/Radiant Story、AI Package 思路和 Kenshi 的队伍/派系/基地/局部模拟目标。
- `Assets/Scripts/Items`：预留给未来正式物品、装备、背包、掉落和制作闭包；当前正式项目里还没有这条目录下的正式实现。
- `Assets/Scripts/Combat`：伤害、技能、状态效果、命中、目标选择和 EX-GAS 专项接入；RPG 规则和数据引用优先对齐 `2DRPGEngine` ability/effect，武器执行、命中区域、受击反馈和无敌帧优先吸收 `TopDownEngine` 的 Weapon/Health/DamageOnTouch 模式；EX-GAS 正式接入前必须先建专项矩阵，且不预留项目侧 `Combat/EXGAS` 第二收口目录。
- `Assets/Scripts/Presentation`：动画、角色表现、相机、视觉反馈、音效触发和表现层适配；正式音频/表现闭包需重新建 BroAudio/表现层参考矩阵。
- `Assets/Scripts/Networking`：当前不创建；FishNet 是后续联机阶段有限人数主机权威合作的首选评估框架，不能为了预留而堆网络空目录、网络上下文或网络模块资产。
- `Assets/GameData`：项目侧 ScriptableObject、配置、数据库和可 diff 设计数据。
- `Assets/Editor`：人工可理解、低误点风险的正式编辑器工具。
- `Assets/Tests`：Unity Test Framework 测试和验证夹具。

## 现态证据

下面这节只记录“仓库现在已经施工到哪里”，不作为选择框架的理由。

- `Assets/Scripts/GameCore` / `Assets/Editor/GameCore`：自 `2026-06-12` 起已按 `2DRPGEngine` 同职责源码整段进入当前工程，当前判断口径是“地基闭包是否成立”，不再停留在只看 `GameManager + AGameSystem + GameConfig` 最小闭包。
- `GameCore` 当前已经包含 `Database`、`Save/Persistence`、`Maps`、`Commands`、`Interactions`、`Entities`、`Controllers`、`PlayerSystem`、`InventorySystem`、`JournalSystem`、`Teleporter`、`Combat`、`Quest`、`UI` 与 `Events` 等参考目录闭包；这些闭包存在是正式现态。
- `Assets/Scenes/SampleScene.unity` 当前已按 `2DRPGEngine` 参考场景补齐正式运行时系统闭包：`Game Manager`、`Input / Inventory / Dialogue / Audio / Player / UI / Game State / Journal / Map / Game Flag / Persistence / Transition / Save` 系统对象，以及 `Transition` 的屏幕淡入淡出 UI 子树与 `AudioSystem` 的 4 个音频通道子对象。旧 `Notification System` 场景对象已退场。
- 上述闭包存在，不等于对应玩法链已经接线完成。真实可跑仍要分别补玩家 Prefab、场景、组件、数据库资产、输入、UI 和测试证据。
- 上述闭包也不等于已经具备 Skyrim/Kenshi 级开放世界能力。`2026-06-17` 已再次确认：当前并没有需要“live runtime 角色注册表”的真实调用者，因此 `CharacterRegistrySystem` 已被整块撤回，不再为未来控制组和世界层先留项目级系统闭包；区域/Cell 模型、队伍控制、派系关系、AI 日程、经济/基地生产、世界事件与任务动态绑定、导航 Provider，以及区域内外模拟降级仍然缺失。
- 玩家控制器的当前正式入口是 `Assets/Scripts/GameCore/Runtime/Entities/Movable.cs` 与 `Assets/Scripts/GameCore/Runtime/Controllers/PlayerController.cs`；后续对齐参考、补手感或补验证都应回到这组正式闭包上做，不得再在 `Assets/Scripts/test` 或测试场景里另起一套同职责控制器。
- 玩家实体的当前正式入口是场景内预摆 `玩家角色` prefab，并由 `PlayerSystem.m_playerInstance` 序列化绑定场景内 `Hero`；缺少该序列化引用时必须按配置错误报错并中断，不允许运行时搜索、自动新建或自动替代。`PlayerSystem` 只负责玩家实体真相、当前输入目标和存档登记，不再负责运行时生成默认玩家。
- 当前正式输入资产继续以 `Assets/InputSystem_Actions.inputactions` 为入口，动作图已回到 `2DRPGEngine` 参考的 `Gameplay / UI / None` 形状；`PlayerInput` 也已回到 `SampleScene` 的正式 `Input System` 对象上，且 `UI` 预制体继续指向同一输入真相源。完整点击寻路仍缺 2D 导航 Provider，但当前基础点击移动可以复用现有 `Movable.MoveTo(...)` 直线移动闭包实施；不得把它误报为完整导航/寻路控制器已完成。
- 点击移动、WASD 和摇杆切换不是单独控制器小功能；它会碰到能力阻断、当前控制对象/控制组、导航 Provider、反馈触发点和动画朝向。实施前必须先按 `.spec/knowledge/features/project/三方框架系统对照.md` 的 TopDown 融合优先顺序确认动作地基，不得绕过正式闭包另起同职责测试控制器。
- 3C 一致性不是“角色能动 + 场景能看见”。玩家 Character、Camera、Control 必须同轮回到正式闭包裁决：角色/控制继续以 `PlayerSystem + PlayerController + Movable` 为真相，相机必须以 `PlayerCameraRig + CinemachineBrain + CinemachineCamera` 作为正式表现闭包，默认跟随当前控制角色；`MapInfo` 只提供相机目标覆盖和地图边界配置，不直接驱动 Cinemachine，也不允许用一次性修复脚本在 PlayMode 隐式补相机。
- 若本轮讨论的是 2D 导航、点击移动、场景实例宿主、出生点分流或它们的派生问题，先看 `.spec/knowledge/features/project/2D移动与场景组织找参考清单.md` 做快速筛选，再回到 `.spec/knowledge/features/project/2D移动与场景组织缺口矩阵.md` 锁定一级/二级缺口。当前这 4 个一级框架缺口未补齐前，不得把控制组穿越、超距自动靠近或入口条件直接写进运行时。

## 输入、世界与表现边界

- 输入层只产生玩家意图，不直接修改世界状态。
- 世界层消费意图、交互和事件，推进可保存的状态。进入队伍控制后，输入目标必须是当前控制对象或控制组，不得继续硬绑 `GameManager.Player`。
- 表现层只订阅状态和事件，负责 Animator、Sprite、音效、特效和相机反馈。
- 交互、战斗、采集、制作和背包不得把核心规则写死在 UI 回调或单个场景实例里。
- 跨模块协作不得再恢复旧自造事件总线；事件派发机制正式选择 Yoki `EventKit.Type`。旧 `NotificationSystem` 已删除，项目事件统一通过 `GameRuntimeEvents + EventKit.Type` 分发。
- 游戏内卡牌自走棋模式不得把开放世界的当前地图、当前控制角色、移动输入或菜单栈当成自己的运行时前提。它可以读取玩家长期收藏和奖励出口，也可以使用项目级资源、音频和 UI 服务；但牌局状态必须能独立创建、结算、保存或丢弃。
- 开放世界模拟事件不得默认塞进任何项目级大总线。每类事件必须先确认拥有者、保存语义、区域内外处理方式和测试入口；否则只能继续定位或写设计，不得实施。
- 世界与交互协作后续优先对齐 `2DRPGEngine` 的 `MapSystem + IInteraction/ICommand`，并吸收 `TopDownEngine` 的关卡边界、出生点和重生样板。
- 区域、Cell、派系、AI 日程、队伍和经济生产不由 `MapSystem` 承担。`MapSystem` 继续负责当前地图、检查点、传送和场景加载；开放世界长期状态由后续世界运行时内核承担。
- 物品协作后续优先对齐 `2DRPGEngine` 的 `InventorySystem + Item/Equipment/ItemEffect`；`TopDownEngine` InventoryEngine 只作为拾取、掉落和槽位交互样板，不替换 RPG 背包真相。
- 战斗协作后续按分层处理：RPG 规则和状态优先对齐 `2DRPGEngine` ability/effect，武器执行和受击表现优先吸收 `TopDownEngine`，EX-GAS 是否替换规则层需专项矩阵决定。
- 表现和音频协作当前正式边界是 `Assets/Scripts/GameCore/Runtime/Audio` 与 `Assets/Scripts/GameCore/Runtime/Database/Audio`；后续扩展仍要沿这条边界继续，不再由 `PresentationModuleAsset` 先行定义。

## Mod 支持边界

- Mod 支持是正式长期目标，不是可选方向。
- 当前已创建 `GameCore/Runtime/Mods` 作为最小本地 Mod 加载地基；它只负责目录扫描、解包、启停状态、版本校验和外部 Addressables catalog 加载，不代表脚本热更、创意工坊、完整数据合并和安全沙箱已经完成。
- Addressables 已进入 Mod 资源 catalog 加载路径，但官方玩法数据主轴仍是 `DatabaseRegistry` 和项目稳定 ID；资源包格式、依赖解析、平台限制和验证流程还需要专项裁决。
- 新增正式内容数据时，默认提供稳定 ID、来源归属、版本字段或迁移策略；删除或改名数据时要考虑旧存档和外部内容的缺失回退。
- 新增资源引用时，优先走数据库条目、资源键或项目侧资源服务，避免把场景对象、Prefab 路径或第三方资源 API 直接写进玩法规则。
- 新增可扩展规则时，优先把官方内容也当作“内置内容包”处理，保证后续外部内容能复用同一入口，而不是为 Mod 另开第二套逻辑。

## 单机优先与有限联机边界

- 当前不绑定 FishNet、NGO、Mirror 或其它网络框架。
- 不创建 `Networking` 空目录、网络 SDK 抽象、网络模块资产或联机上下文容器。
- FishNet 是后续联机阶段有限人数主机权威合作的首选评估框架：房主世界是真相，访客可拥有完整角色操作权，但不拥有世界所有权。
- 输入来源、控制权、阵营、对象归属、世界状态和表现事件仍要分层清楚；这是单机复杂系统、Mod 兼容和确定联机目标共同需要的维护边界。
- 具体联机、Mod 一致性和卡牌局内对战边界见 `.spec/knowledge/features/project/联机与Mod边界.md`。

## 禁止误用

- 不把素材包 demo 脚本、demo 场景或旧恢复 Prefab 当作正式运行时入口。
- 不把 `dark-corridor` 的横版玩家控制器、横版相机、横版测试场景迁入正式框架。
- 不为空目录堆架构；只有能力进入正式范围时才创建对应目录和代码。
- 不让玩法代码散落直接依赖第三方插件 API；必须由正式拥有者闭包统一接入，不能额外再包一层假统一 facade。
