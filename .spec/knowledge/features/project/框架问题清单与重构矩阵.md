# 框架问题清单与重构矩阵

> 用途：把当前框架地基里的职责重复、单例边界和后续重构顺序说清楚。
> 本文不定义具体玩法内容；背包、任务、对话、属性、能力、装备、卡组、牌局属于领域框架模块，具体物品、具体卡牌、具体任务链、具体菜单流程才是业务内容。

## 当前结论

- 单例不是本项目的默认架构答案。`GameManager.Instance` 只能暂作 Unity 场景里的启动锚点和系统收集器，不能继续扩张为开放世界、牌局、UI 栈、角色属性或长期收藏的唯一真相。
- 当前 `GameManager + AGameSystem` 比 TopDown 的多 manager 链更可控，但它不是完整开放世界地基。继承自 2DRPGEngine 的 RPG 基线快捷入口可以保留；真正的问题是新增开放世界、牌局、UI 栈等新领域状态若继续以“全局可取”为理由挂到 `GameManager.XxxSystem`，会制造错误 owner。
- TopDown 不适合作总框架。它的 `GameManager/LevelManager/InputManager/GUIManager` 互相调用，适合吸收动作执行、重生、关卡边界、反馈触发点，不适合接管本项目生命周期、输入、UI 或存档真相。
- 背包、任务、对话、属性、能力不是业务垃圾。它们应保留为领域框架模块；要剔除的是具体内容、具体 UI 流程、重复真相和跨职责捷径。
- 类似昆特牌但自走棋模式的集换式卡牌玩法是本游戏的一部分，不是外部小游戏；它需要游戏内模式宿主。卡牌收藏、卡组、奖励可以接长期存档/背包；单局棋盘、自动战斗回合、单位状态、模式输入不能挂在开放世界运行时或 `GameManager.XxxSystem` 静态入口上。
- 事件派发机制正式选择 Yoki `EventKit`。旧 `NotificationSystem` 已从正式运行时、测试和场景退场；项目事件当前统一走 GameCore 强类型领域事件 + Yoki `EventKit.Type` 派发，后续不得恢复旧调用面。

## 现态证据

| 对象 | 当前事实 | 判断 |
| --- | --- | --- |
| `GameManager` | 公开继承自 2DRPGEngine 基线的 `XxxSystem` 静态快捷入口，内部用 `Dictionary<Type, AGameSystem>` 收集系统 | 可作为当前 RPG 基线启动宿主；不因“单例形式”默认收缩，但不得新增开放世界/牌局等新领域入口 |
| `AGameSystem` | 只有初始化、启动、停止、地图加载、存档加载回调 | 适合现阶段统一生命周期，不适合承载项目级/世界级/模式级所有权 |
| 已删除的 `NotificationSystem` | 曾同时包含战斗、物品、能力、任务、地图、存档、UI 菜单、音频请求事件 | 这是最典型的大总线反例；当前已删除，后续只允许继续精炼强类型事件边界 |
| Yoki `EventKit` | 提供 `Type/Enum/String` 三类事件中心，`String` 已标记废弃；`TypeEvent` 支持强类型载荷、自动注销 token、编辑器监控 | 机制层优于 `NotificationSystem` 的巨大 `UnityEvent` 字段表；正式派发机制选它 |
| `PlayerSystem` | 已把 `PlayerInstance` 和 `currentInputTarget/currentControlledCharacter` 分开 | 方向正确；后续命令、交互、UI 应逐步从唯一主角改读正式控制目标 |
| `InventorySystem` | 背包和货币为长期真相，默认装备入口读取当前控制角色并解析 `CharacterEquipment` | 系统本身保留；装备/使用目标边界继续保持角色级显式解析 |
| `Stats/currentStats` | 当前只保留为快照 DTO、UI/事件载荷、启动缓冲或批量计算输入；属性真相已切到角色实体级 ASC + `FormalGameplayAttributeSet` | 不得重新持有生命、法力、攻击、防御等属性真相，也不得与 EX-GAS 并行结算 |
| `GAS` | 插件已接入，`GameCore` 已正式引用 `AbilitySystemComponent`，并已作为属性/能力规则正式方向 | 当前问题不再是“能不能接 GAS”，而是怎样把旧规则残留直接替掉且不制造第二真相 |
| TopDown managers | `GameManager/LevelManager/InputManager/GUIManager` 是多单例链，并处理点数、生命、暂停、角色列表、移动端 UI | 不接管总框架，只吸收局部成熟执行模式 |

## 重复职责裁决

| 职责 | 保留一边 | 剔除或暂不接入一边 | 理由 |
| --- | --- | --- | --- |
| 项目启动宿主 | 当前 `GameManager` 最小保留 | TopDown `GameManager`、Yoki `SingletonKit` 接管玩法生命周期 | Unity 需要场景根，但玩法状态不能靠工具或动作框架单例表达 |
| 系统生命周期 | 当前 `AGameSystem` 暂保 | 再造 `FoundationSupport/RuntimeContext/ModuleInstaller` | 旧自造链路不赢任何一层，会制造第二地基 |
| 开放世界状态 | 后续 `WorldRuntime` 或同级世界内核 | `MapSystem` 或 `GameManager` 直接承担区域、派系、经济、AI 日程 | 地图加载和开放世界长期模拟不是同一职责 |
| 模式状态 | 后续 `ModeRuntime` | `GameManager.XxxSystem` 静态挂开放世界模式或牌局模式 | 开放世界、卡牌自走棋、主菜单、剧情演出有不同输入和状态保存边界 |
| 卡牌自走棋牌局 | 独立牌局模式宿主 | 复用开放世界当前地图、当前角色、移动输入、菜单栈作为牌局真相 | 牌局是可创建、可结算、可丢弃的局部状态 |
| 长期卡牌收藏/卡组 | 存档/背包同级长期数据模块 | 单局牌局持有长期收藏真相 | 收藏和单局战斗生命周期不同 |
| 属性 | 角色实体级 ASC + `FormalGameplayAttributeSet` 是正式真相 | `Stats/currentStats` 长期并行持有同一数值 | 生命、法力、攻击、防御只允许走一套正式 GAS 读写链 |
| 能力/效果 | 规则真相收口到 EX-GAS；项目侧只保留技能入口、执行壳和表现入口 | 旧 `Ability/Effect/Stats` 继续长期拥有同职责规则 | EX-GAS 已胜出规则层；当前只允许继续替旧残留，不允许再摇摆 |
| 输入 | `GameCore InputSystem` 保语义 | TopDown `InputManager`、Yoki `InputKit` 接管玩法输入 | 输入意图属于模式和控制目标，重绑定工具不等于输入真相 |
| UI | 当前正式宿主已切到 `UIManager + UIKitMenuPanelBase + UIKit` 原生 stack | 让 `AUIMenu/UIMenuManager`、adapter、wrapper 或第二宿主回潮 | UI 已经完成宿主替换，后续只允许继续清理旧资源和共享构件，不允许再回到包装兼容层 |
| 事件派发机制 | Yoki `EventKit.Type` | 恢复 `NotificationSystem` 或其它项目级大总线 | Yoki 已提供强类型派发、注销 token、编辑器监控；正式派发机制当前只留这一套 |
| 领域事件定义 | `GameCore` 强类型事件结构 | Yoki 插件里定义项目玩法事件，或恢复把所有事件塞进 `NotificationSystem` | 插件只提供工具机制；游戏领域语言必须留在项目侧 |

## 单例使用规则

| 用法 | 裁决 | 说明 |
| --- | --- | --- |
| 项目启动根 | 暂时允许 | `GameManager.Instance` 可以是场景 composition root，但只能负责发现和启动系统 |
| 工具缓存、对象池、资源句柄 | 允许 | Yoki 的对象池、资源工具这类纯工具适合全局访问 |
| 当前世界、当前牌局、当前 UI 栈 | 禁止默认单例 | 它们会随存档、模式或场景切换而变化 |
| 玩家长期数据 | 不直接挂全局单例 | 应由存档/玩家档案/世界运行时明确拥有 |
| 领域系统快捷访问 | 参考基线保留，禁止新增 | 现有 `GameManager.XxxSystem` 是 2DRPGEngine 同职责流程的一部分；通过原因是参考基线成立，不是单例形式优越；新增领域必须先证明 owner |

## 重构顺序

| 顺序 | 动作 | 不做什么 |
| --- | --- | --- |
| 1 | 守门禁：禁止新增 `GameManager.XxxSystem`，禁止旧 `Stats/IEffect` 与 EX-GAS 双真相回潮，禁止接 TopDown manager 链 | 不先大拆现有调用面 |
| 2 | 建立 `ProjectRoot / WorldRuntime / ModeRuntime / Entity` 所有权术语和落点 | 不建空 `WorldSystem` 或空 `CardSystem` 伪架构 |
| 3 | 维持 `NotificationSystem` 退场后的正式事件结构：新增事件一律定义为 GameCore 领域事件结构，并用 Yoki `EventKit.Type` 派发 | 不恢复万能事件总线，也不在 Yoki 插件里写项目玩法事件 |
| 4 | 处理 `PlayerSystem.PlayerInstance` 调用点：命令、交互、UI 分清“唯一玩家 Hero”和“当前控制目标” | 不用查找替换硬改所有调用 |
| 5 | 继续清理会让 `Stats/currentStats` 重新拥有属性真相的调用点 | 不让两套属性系统同时显示、存档或结算 |
| 6 | 设计卡牌自走棋模式宿主 | 不复用开放世界运行时或菜单栈当牌局真相 |

## 可以直接改的门禁

- `GameCore` 不得新增 `GameManager.XxxSystem` 静态快捷入口。
- `GameCore` 不得再把旧 `Stats/IEffect` 与 EX-GAS 并行长期运行，也不得新增包装层把两套规则真相继续绑在一起。
- `GameCore` 不得直接引用 TopDown 的 `GameManager/LevelManager/InputManager/GUIManager` 作为正式运行时依赖。
- `GameCore` 不得引入 TopDown `InventoryEngine` 作为背包真相。
- `NotificationSystem` 不得回归；静态门禁当前直接禁止旧通知中心文件、测试、场景对象和调用面，新增事件必须是 GameCore 强类型事件结构，并通过 Yoki `EventKit.Type` 派发。
- 新增开放世界或卡牌模式能力前，必须先说明它属于 `ProjectRoot`、`WorldRuntime`、`ModeRuntime` 还是 `Entity/Component`。

## 下一步判定标准

- 若一个东西表达“长期保存的玩家/世界事实”，优先问它属于哪个存档块或世界运行时。
- 若一个东西表达“当前这一局/这一段模式的状态”，优先放入 `ModeRuntime`，不要挂到全局单例。
- 若一个东西表达“游戏内卡牌自走棋”，它仍然可以依赖玩家档案、背包奖励、资源、音频和 UI 服务；分层只是在隔离单局牌局状态和输入上下文，不是在把它做成另一个游戏。
- 若一个东西只是工具能力，优先用 YokiFrame 已有实现，不再复制项目侧薄工具。
- 若一个东西只是事件派发机制，优先用 Yoki `EventKit.Type`；GameCore 只定义事件类型和领域含义。
- 若 TopDown 在动作执行上更好，直接吸收执行模式；但若它需要带入 manager、输入、GUI 或生命真相，则只取局部模式，不取宿主。
- 若 GAS 在属性/效果/标签/叠层规则上胜出，应替换当前对应职责；如果不替换，就不得并行成为第二真相。
