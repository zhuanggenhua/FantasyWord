# 文档索引

> 本索引用于回答两个问题：现在有哪些正式文档；遇到某类任务时先读哪几篇。

## 适用范围

- `.spec/knowledge/features/project` 是项目 AI 的长期渐进式披露入口，职责接近 skill：负责长期规则、任务路由、正式入口、职责边界、参考矩阵和可复用验收方法。
- `.spec/knowledge/features/project` 不是当轮工作台、临时草稿区、证据堆、搜索记录、交接记录或任务流水账；不能因为“后续可能有用”就把所有文件放进根目录。
- 当前迁移阶段的临时结论不能写进旧 `task_plan.md`、`findings.md`、`progress.md`；这些文件只作为旧恢复历史参考。
- 正式规格和阶段性 change 进入 `openspec/`；`.spec/knowledge/features/project` 不承载本轮任务快照。

## 文档分层规则

- 长期规则、任务路由、正式职责边界、工具入口、可复用验收方法：可以放在 `.spec/knowledge/features/project/` 根目录。
- 具体 bug 复盘、误判路径和验收记录：放在 `.spec/knowledge/features/project/bugs/`，根目录只保留 `Bug排查索引.md`。
- proposal、change、阶段拆分、阶段验收标准、一次性执行计划：放在 `openspec/`，不要复制到 `.spec/knowledge/features/project/` 根目录。
- 旧恢复记录、过期阶段日志、历史证据、已完成交接：放在 `docs/archive/`。
- 临时源码摘录、搜索过程、候选参考清单、当轮待办和交接草稿：默认不得进入 `.spec/knowledge/features/project/` 根目录；只有整理成长期可复用的职责矩阵、入口索引或规范后，才允许迁入。

## 新增文档门禁

新增或保留 `.spec/knowledge/features/project/` 根目录文档前，必须能明确回答：

1. 它的长期职责是什么。
2. 哪类任务会触发读取它。
3. 它替代、约束或补充了哪个已有入口。

如果三项答不清，就不要放入 `.spec/knowledge/features/project/` 根目录；优先落到 `openspec/`、`docs/archive/`、`.spec/knowledge/features/project/bugs/` 或具体专项目录。

## 当前整理判断

- `文档类型速查` 只列正式入口和仍需路由的长期文档，不再代表 `.spec/knowledge/features/project/` 根目录所有文件都合格。
- 已经混入根目录的阶段台账、源码摘录、参考搜索记录和提交模板，后续应按 `文档分层规则` 分批迁出或合并；迁出前不得继续把它们当成默认必读入口。
- 做具体任务时先按 `任务触发建议` 读取对应入口；不要从根目录文件数量倒推“全都要读”。

## 待迁出或合并材料

以下文件目前仍在 `.spec/knowledge/features/project/` 根目录，但它们更像阶段取证、搜索过程或提交模板，不应继续当作长期默认入口：

- `一级缺口取证清单.md`：阶段取证清单，后续应并入对应 `openspec` change 或迁到专项取证目录。
- `一级缺口候选优先级台账.md`：候选源阶段排序，后续应并入参考接入 change 或归档。
- `一级缺口源码摘录台账.md`：源码摘录证据堆，后续应迁到 `docs/archive/` 或对应 change 的证据目录。
- `2D移动与场景组织外部参考搜索指引.md`：外部搜索过程指引，后续应并入 `2D移动与场景组织找参考清单.md` 的长期筛选规则，或迁出为专项任务资料。
- `2D移动与场景组织外部参考提交模板.md`：一次性提交模板，后续应迁到专项 intake 文档或 `openspec` change。
- `foundation-reference-audit.md`：地基迁移纠偏审计，若不再承担长期规则，应迁到对应 archived change 或 `docs/archive/`。
- `foundation-template-guide.md`：地基模板迁移说明，若继续复用，应转成正式工具入口；否则迁到 `docs/archive/`。

迁出前，后续任务只能把这些文件当作补充证据，不得把它们列为默认必读入口。

## 任务触发建议

- 看新游戏目标、旧用户故事是否继承、单机优先定位和确定联机边界：读 `项目定位与迁移边界.md`。
- 看 FishNet、主机权威、访客控制角色、Mod 联机一致性或类昆特牌局内对战：读 `联机与Mod边界.md`。
- 看文件应该放哪、哪些废弃目录只是历史遗留：读 `项目目录与入口.md`。
- 改 `Packages/manifest.json`、ProjectSettings、Input System、URP、场景或 Prefab：读 `Unity工程通用规范.md`。
- 定义俯视角运行时目录、GameCore、输入、世界、表现和单机运行时边界：读 `框架与运行时入口.md`。
- 接入 EX-GAS、设计技能/状态/战斗边界：读 `Unity架构与GAS规范.md`。
- 需要判断技能系统某个职责到底参考谁、当前哪些已能定为正式真相、哪些还不能：读 `技能系统职责裁决矩阵.md`。
- 需要复刻当前普攻 `20001 Attack` 的 GAS 配置、时间轴、伤害、Cue、输入和角色装配流程：读 `普攻GAS配置复刻流程.md`。
- 写 spec、proposal、change、阶段任务或验收标准：读 `openspec/AGENTS.md`。
- 替换 UnityMCP、接入 AIBridge、迁移第三方插件：读 `参考源映射.md` 和 `Unity工程通用规范.md`。
- 核对当前已接入插件、UPM 包、参考源边界和待决插件任务：读 `第三方插件接入清单.md`。
- 只想先看最终结论，不想自己拼长表：先读 `框架最终裁决.md`。
- 对照 `2DRPGEngine`、`TopDownEngine`、`YokiFrame`，判断同职责系统谁是真相源、谁只作工具或参考：读 `三方框架系统对照.md`。
- 需要最直接地看“为什么这个系统选这边，不选另一边”，并把判断压回 `设计模式 / 软件工程 / 易用` 三项：读 `框架三项判分矩阵.md`。
- 需要直接回答“这个模块到底该替换、融合还是冻结，以及正式落点在哪”：读 `框架正式动作清单.md`。
- 需要继续分析“GameSystem 到处都是、单例是否合适、开放世界和卡牌小游戏怎么分真相所有权、哪些能直接改”：读 `框架问题清单与重构矩阵.md`。
- 需要判断“系统是不是框架、哪些职责重复、单例是否合适、开放世界和卡牌小游戏怎么分宿主”：读 `框架职责所有权矩阵.md`。
- 需要一页版地看“该替换什么、该融合什么、现在什么不能硬做”：读 `框架决策速查表.md`。
- 需要执行顺序版地看“先做什么、后做什么、什么被一级缺口卡住”：读 `框架实施阶段表.md`。
- 对照 Chris，判断哪些模块已经直接搬入、哪些只能局部吸收、哪些会制造第二套宿主：读 `Chris框架吸收清单.md`。
- 如果你现在只想先搞清楚“4 个一级缺口”和“开放世界模拟层未开工”是不是一回事：先读 `框架决策速查表.md`，再读 `框架与运行时入口.md`。
- 看 2D 移动、点击移动、实例宿主、出生点分流当前到底还缺什么正式参考：读 `2D移动与场景组织缺口矩阵.md`。
- 想一页看完“本机已证实 / 已排除 / 需要外找什么”：读 `2D移动与场景组织现态速查表.md`。

- 旧 `FantasyWorld` 恢复记录、乱码调查、换装测试主线和 MiniFantasy UV 验证只保留为历史证据。
- 如果历史记录仍有参考价值，应迁入 `docs/archive/` 或在新文档中以“历史参考”明确标注。
- 不能把历史文档中的 `Next:`、`进行中`、`Phase`、`待继续` 直接当成当前会话任务。
