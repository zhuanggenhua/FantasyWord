# 参考与复用来源映射

## 适用范围

- 本文定义哪些来源可以参考、复用、复制、导入或安装，以及触发哪些门禁。
- 参考不是灵感；当来源被用来决定正式职责、命名、API、Inspector、序列化、运行逻辑、资产组织或验收口径时，必须形成参考记录。

## 2DRPGEngine / TopDownEngine / YokiFrame 分工裁决

- 三方裁决必须按 `设计模式 / 软件工程 / 易用` 三项判断，不能用“当前已经接入谁”当理由；详细表见 `.spec/knowledge/features/project/三方框架系统对照.md`。
- `uMMORPG` 不参与这张三方胜负表；它当前只负责补 `2D 移动与场景组织` 的局部源码证据，不能被误升格成第四个总框架候选。
- 按 `Skyrim + Kenshi + 博德之门 + ToME4` 目标复核后，三方分工还必须加上第四层：FantasyWord 自己的开放世界模拟层和复合角色系统。2DRPG/TopDown/Yoki 都不能完整承担区域/Cell、队伍、派系、AI 日程、经济/生产、局部模拟、多角色私有库存、复杂状态突变和长期可扩展构筑。
- `2DRPGEngine` 负责 RPG 世界规则层：游戏启动、系统生命周期、数据库、存档语义、地图、命令、交互、对话、任务、物品、角色数据和 RPG 规则闭包。它胜出的原因是数据和存档语义集中，适合维护单一世界状态。
- `TopDownEngine` 负责俯视角动作表现层：角色能力组件、移动手感、武器状态机、命中/受击、无敌帧、击退、相机、反馈、AI 战斗样板、拾取/掉落、交互区、关卡边界、出生点和 2D 地牢样板。这里不是“仅观察”，但也不是整体接管；当后续要做点击移动、WASD、摇杆、战斗手感、AI 战斗、交互样板或反馈时，默认先复核 `.spec/knowledge/features/project/三方框架系统对照.md` 的 TopDown 全系统横向复核和融合优先顺序，再在 GameCore 正式闭包上实施。3C 相关需求必须把 `Character / Camera / Control` 作为同一闭包裁决：控制器吸收 TopDown 移动手感时，相机也必须同步复核 TopDown 的 Cinemachine 跟随、相机目标和边界样板；不得只补普通 `Main Camera` 当作完成。
- 相机参考不能按“哪边也有虚拟相机”来无脑选边，必须拆成三项分别比对：跟随目标真相源、边界真相源、切换/重置触发方式。TopDown 主要提供的是镜头拓扑和事件语义，2DRPG 主要提供的是地图真相源；当前项目的正式落点必须把这三项来源写清楚，再决定是整套替换、局部吸收还是仅观察。
- `YokiFrame` 负责工具层：对象池、资源句柄、场景加载工具、存档文件底层、输入重绑定、UI 缓存、日志、本地化和通用编辑器工具。它不承载 RPG 世界规则，但应替换项目侧重复工具实现。
- 开放世界模拟层只在具体能力进入正式范围时，才由 FantasyWord 项目侧定义正式宿主与接口；候选参考只能辅助局部实现，不能替代世界状态真相源。
- 两个成熟框架同职责冲突时只能选一个真相源，不做双轨兼容。默认裁决是：RPG 数据语义选 `2DRPGEngine`；俯视角动作执行选 `TopDownEngine`；通用底层工具选 `YokiFrame`。
- 融合不是包一层。融合后的正式调用点只能落在当前项目正式入口或第三方插件稳定工具入口；不得新增 `Compatibility`、`Adapter`、`FoundationSupport`、镜像包装层或第二套同职责入口。
- 允许存在的桥接只有两类：第三方插件 API 被项目正式拥有者闭包消费时的最小接入点，以及 AIBridge 这类编辑器自动化桥。它们必须服务明确外部依赖，不得变成玩法系统之间的缓冲层。
- 新项目不需要兼容层。旧 `Bootstrapper / RuntimeContext / ModuleInstaller / EventBus`、旧 `FoundationSupport` 等入口都不得恢复；若以后发现为了迁移旧资产而需要兜底，也必须先登记原因、对象和退出条件。

## 参考记录最小格式

当外部来源决定正式功能设计、命名、API、Inspector、序列化、运行逻辑、资产组织或验收口径时，必须至少形成一行参考采用记录；不得只把链接、源码摘录或阶段性 `openspec` 记录当作正式参考留档。最小记录项如下：

- 模块名
- 主参考来源路径或 URL
- 参考有什么：它真实提供的职责、行为、数据、工具或流程。
- 吸收什么：本项目准备采用的职责、规则、语义或局部做法。
- 为什么吸收：它比当前实现或其它候选具体好在哪里。
- 不吸收什么：明确不照搬的源码、框架、产品假设、参数、入口或运行方式。
- 为什么不吸收：原因必须归类为 `同类更好`、`职责不匹配`、`产品/引擎不匹配`、`质量不足`、`证据不足`、`许可/依赖风险` 或 `当前已有正式 owner`。
- 使用方式：`整套替换`、`局部吸收`、`仅观察`、`产品目标参考`、`负证据`
- 当前项目落点
- 一句话结论：它在这个职责上最终是什么地位。

Skyrim/Kenshi/博德之门/ToME4 目标参考最小记录还要额外写清：

- 它对应的现实能力：例如区域/Cell、队伍、派系、AI 日程、动态任务、基地生产、局部模拟、多角色背包、战术控制、复杂状态、奇特能力或构筑扩展。
- 当前项目真相源：哪个 FantasyWord Module 负责保存和推进状态。
- 候选参考的使用方式：设计目标、局部实现参考、工具包候选、或仅产品目标参考。
- 不采用范围：明确哪些部分不照搬，避免把产品目标误读成整套框架接入。

只有当同一模块存在多来源冲突、长期偏离、难以验收，或后续明显会反复争论时，才升级为专项参考矩阵。专项矩阵必须比最小记录多写清：同类候选谁更好、为什么更好、正式 owner 是谁、验证入口是什么。

## 参考采用规则

- “多方面参考、各取所需”的正式含义固定为：**先切职责，再为每个职责单独择优**；不是把多个来源的优点同时摊进同一条正式链路。
- “多方面参考”不等于“每次都把所有参考一起纳入方案”。默认只让**当前职责直接相关**的候选进入比较；与当前职责无关、或已经在别的职责上定过 owner 的参考，不得为了显得全面再强行入场。
- 默认裁决步骤必须按顺序执行：
  1. 先写清当前在比的是哪一个职责，例如：规则真相、作者输入源、可视化编辑、运行时执行宿主、表现触发、存档真相。
  2. 再列出该职责的候选来源。
  3. 对同一职责只选一个正式 owner，并写一句“为什么它比其它候选更适合当前项目”。
  4. 其它来源只能降级为 `仅观察`、`局部证据` 或 `待迁移候选`。
  5. 若后续同一职责出现更优来源，默认迁移并清退旧 owner，而不是把新旧两边都留下。
- “各取所需”里的“需”指的是**职责缺口**，不是“我喜欢这个来源里的某个局部体验”。
- 只要两个来源正在竞争同一份作者数据、同一份运行时解释权、同一份技能时间轴、同一份命中框数据或同一份规则结算入口，就已经属于同一职责竞争，不能再叫“多参考融合”。
- 一个来源只在某个局部职责上更强时，只吸收那一小段；不得顺势把它扩写成整套主轴，也不得为了“吸收它的优点”再复制出第二份正式数据。
- 判断“是否值得吸收”时，必须回到可证明收益：作者效率、可视化、调试性、稳定性、迁移成本、扩展性。若收益说不清，只是概念上看起来更高级，默认不吸收。
- 判断“是否只是混编”时，用一个简单标准：如果策划或程序需要同时维护两份同职责配置、两种同职责编辑入口、或两套同职责运行时理解方式，那就不是“各取所需”，而是双轨。
- 架构设计必须参考先行。凡是会新增正式架构层级、资产模型、运行时解释器、编辑器主流程或同职责真相源的设计，必须先登记主流公开参考、本地成熟源码参考或当前项目已有正式闭包证据；没有参考时只能登记为候选或待验证问题，不得写成正式方案。
- 单个技能、单个菜单、单个特效或单个测试场景不能倒推总体架构。火球、陨石、基础攻击、背刺这类案例只能用于验证某个参考模型是否覆盖需求，不能凭它们直接发明顶层系统。
- 只有在某个参考对当前实现形成**明确整体优势**，并且可以以相对完整闭包搬运时，才走 `整套替换`；这时优先替换，不保留旧实现拼接成双轨。
- 如果参考不是全方面更好，但某一段能力有**明确单点价值**，才走 `局部吸收`；吸收前先明确边界，不为了“多参考融合”而融合。
- 多方面参考不等于“全都要”。默认动作必须先把系统按职责切片，再为每个职责分别裁决主参考；只有当不同参考分别命中**不同职责**时，才允许同时采用。
- 提案、重构说明和实现说明里，默认只需要回答 3 件事：`当前在裁决什么职责`、`这个职责谁是正式 owner`、`其它候选为什么这次不采用`。不要求把所有已登记参考都展开重讲一遍。
- 若多个参考竞争的是同一职责、同一作者流程、同一资产模型或同一运行时 owner，则只能选一个正式主轴；其余来源只能保持 `仅观察`，或在明确降为局部证据后再吸收单点规则，不能并排落成正式实现。
- `局部吸收` 指的是吸收某个参考在线路中的单点强项，例如手感、反馈触点、可视化方式、数据结构或健壮性规则；不等于把多个参考在同一职责里拼成混编实现，也不等于给同一份数据保留多个并行入口。
- 若参考已经完整承载当前职责，默认直接复用参考实现；当前项目只允许为现有正式闭包补证据充分的最小微调，不允许先自写一个同职责“项目特化版”再尝试回收。
- 选择参考时优先追求人能读懂的单一结构，而不是“两个框架都包一层”。若需要解释三层以上调用链，默认说明当前设计过度，先收敛。
- `Koala2D` 这类 demo 不能单独冒充框架来源；若其核心能力实际来自 `TopDownEngine/Common`，则正式参考应记到 `TopDownEngine/Common`，`Koala2D` 只记样板价值。
- 任何吸收都必须回答两件事：`它比当前实现具体好在哪`，`吸收后谁是真相源`。答不清就不吸收。
- 参考择优不是“谁都抄一点”，而是“每个职责只留下最优的一条正式链”。若一个方案没有带来可证明的作者效率、可视化、稳定性、调试性或扩展性收益，只是增加理解成本，则默认不吸收。
- 一旦某个职责已经选定正式主轴，后续如果发现另一来源在**同一职责**上形成更明确的整体优势，默认动作是迁移到更优主轴并清退旧同职责实现，而不是长期保留混编或双轨兼容。
- 当某个参考职责已经被吸收到正式角色组件、正式系统或正式运行时 owner 后，同一职责必须收口到这一个正式真相源；业务调用方不得再各自保留同职责序列化字段作为并行入口。若确实需要空值退回或可选字段处理，该退回路径也必须收在同一个正式 owner 内部，而不是散落到调用方各自实现。
- 允许同时保留多个来源的前提，只能是它们分别服务于不同层次，例如“规则真相”“表现反馈”“编辑器可视化参考”或“局部合同补强”；即便如此，每一层内部也仍然只能有一个正式 owner，不得把同一层再拆成多套并行真相。
- 当一个来源已经被判定为 `仅观察`，后续不得顺手从里面零碎抄代码，除非先把它升级为 `局部吸收` 并补一句价值说明。
- 当前已经进入正式工程的 `Assets/Plugins/TopDownEngine` 只代表“已导入候选子集”，不自动等于“已采纳为正式项目框架”；后续仍要按模块决定谁留下、谁替换现有实现。
- `MMFeedbacks` 插件随 TopDownEngine 已进入项目；GameCore 当前已建立 `GameplayFeedbackSet` 作为能力/武器生命周期的最小反馈闭包。后续命中、受击、死亡、拾取和交互反馈也必须走 GameCore 正式反馈闭包；不得把 `MMFeedbacks` 字段零散塞进业务类，也不得让 TopDown `Health/Weapon/CharacterAbility` 接管生命、输入或玩家数据真相。
- 当前还没有任何 Unity Behavior、GOAP、DOTS 玩法依赖进入正式项目。工作区虽然已经导入 `Assets/Plugins/AStar 2D Grid Pathfinding` 候选源码，但它仍只按局部参考保留，不算正式玩法依赖；在没有具体功能、真相源和验收场景前，不得因为“源码已经在仓库里”就直接升格成正式导航闭包或项目默认寻路方案。
- 如果某个正式闭包已经在 `Assets/Scripts/GameCore` 落地，例如当前的 `Movable + IController/AController/PlayerController` 玩家控制器闭包，默认动作是继续在该闭包上对齐参考和补验证；不得再在 `Assets/Scripts/test` 或测试场景里另起一套同职责控制器证明“先能跑”。
- 当前项目是新游戏；当参考与正式闭包都已存在时，再新增 `TopDownTestController` 这类同职责 test 控制器、并行测试场景或其它“先能跑”的临时实现，默认视为技术债，不得直接落地。
- 只有在正式闭包与参考之间存在明确缺口，且该缺口不能通过直接对齐现有闭包解决时，才允许考虑临时试做；但在落任何代码、Prefab 或场景前，必须先补一份流程理由文档，并先向用户上报。
- 上述流程理由文档至少要写清 4 件事：`参考里缺了什么`、`为什么不能直接复用现有正式闭包`、`准备新增哪些文件/场景以及它们的临时边界`、`何时删除或并回正式闭包`。用户未明确同意前，不得落地这类临时代码。
- 这类流程理由文档属于当轮变更证据，不写进 `.spec/knowledge/features/project`；默认写到当前活跃 `openspec/changes/<change-id>/parallel-trial-rationale-<topic>.md`，再向用户上报。
