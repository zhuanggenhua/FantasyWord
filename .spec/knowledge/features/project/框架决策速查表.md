# 框架决策速查表

> 用途：给 `FantasyWord` 当前地基提供一页版裁决，不再从“现在放在哪里”“现在已经用了谁”倒推结论。
> 如果只看一份文档，默认先看 `框架最终裁决.md`。
> 若需要看更硬的逐系统胜负，先读 `框架三项判分矩阵.md`；本页只保留速查结论。
> 若需要直接看模块动作，读 `框架正式动作清单.md`。

## 判断标准

所有同职责冲突只按三项判断：

- `设计模式`：职责是否清楚，是否用组合和正式宿主表达行为，而不是靠第二套 manager、隐式广播或大控制器硬堆。
- `软件工程`：是否只有一个真相源，是否容易验证、限制回归面、保护 Unity 序列化和 Prefab 接线。
- `易用`：策划和开发能否靠 Inspector、Prefab、ScriptableObject 和少量代码稳定组装内容。

### 使用顺序

这三项不是平均投票，也不是简单加总。

正确顺序是：

1. 先用 `设计模式` 判断职责类型
   先分清当前系统属于长期世界状态、瞬时角色执行，还是通用工具。
2. 再用 `软件工程` 判断能不能成为正式真相源
   重点看会不会带入第二生命周期、第二输入根、第二 UI 栈或第二存档语义。
3. 最后才用 `易用` 决定在正确赛道里谁更适合快速开始做游戏。

这套顺序直接排除了“单一总冠军框架”这个想法。

## 错误理由

- `当前已经用了谁` 不是理由，只能算现态证据。
- `只是参考` 不是理由；既然拿来参考，就必须参加同职责比较。
- `都留着最稳` 不是理由；双轨通常只会制造第二真相。

### 为什么 `TopDownEngine` 不能只是参考

如果把 `TopDownEngine` 降成“只是参考”，等于默认接受一个错误前提：

- `2DRPGEngine` 既然赢了世界规则层，就可以顺便继续占有动作表现层。

这个前提不成立。

`TopDownEngine` 必须参加正式裁决，因为它在动作表现层三项都更强：

- `设计模式`：角色能力、移动、武器、命中、受击、反馈这一整段更像正式动作执行模型。
- `软件工程`：状态机、命中窗口、动作阻断和反馈触发点边界更清楚。
- `易用`：Inspector 和 Prefab 样板更适合快速把手感调到可玩。

因此它的正确身份不是“灵感来源”，而是：

- 动作表现层胜者
- 但不是世界规则层胜者
- 更不是生命周期、输入、UI 的总接管者

补充口径：

- 这页仍叫“三方表”，不是忘了 `uMMORPG`。
- `uMMORPG` 当前只作为 `2D 移动与场景组织` 的局部源码证据源使用，不参与世界规则、动作表现、工具层这三条主线的总胜负。

## 三方表总览

| 系统 | `2DRPGEngine` | `TopDownEngine` | `YokiFrame` | 裁决 |
| --- | --- | --- | --- | --- |
| 生命周期、地图、任务、背包、角色数据、存档语义 | 最强 | 会引入第二生命周期 | 不竞争玩法真相 | `2DRPGEngine` 做世界规则真相 |
| 动作能力、移动、武器、命中、受击、反馈 | 规则能接，但执行偏薄 | 最强 | 不竞争动作执行 | `TopDownEngine` 做动作表现来源，吸收到 `GameCore` |
| 对象池、文件层、输入重绑定、UI 缓存等工具 | 一般 | 为动作生态服务，不是通用底层 | 最强 | `YokiFrame` 做工具层真相 |
| 区域/Cell、队伍、派系、AI 日程、经济、局部模拟 | 不完整 | 不完整 | 不提供 | `FantasyWord` 自建世界模拟层 |

## 错误方案与正确方案

| 方案 | 为什么错或为什么对 |
| --- | --- |
| `2DRPGEngine` 整体接管 | 世界规则层会很稳，但动作执行会长期卡在偏薄实现上 |
| `TopDownEngine` 整体接管 | 动作层很强，但会顺带带入第二生命周期、第二输入根和第二 UI 根 |
| `YokiFrame` 整体接管 | 工具层很强，但不会回答“世界状态是什么” |
| 三方都包一层 | 只会制造双轨和伪统一 |
| `2DRPGEngine + TopDownEngine + YokiFrame + FantasyWord` 四层分治 | 世界规则、动作表现、工具和开放世界模拟分别由最适合的一层负责，这是当前唯一正确框架 |

## 四层正式框架

| 层 | 胜者 | 正式动作 | 正确理由 |
| --- | --- | --- | --- |
| RPG 世界规则层 | `2DRPGEngine` | 直接作为正式真相源 | 地图、任务、背包、角色数据和存档语义必须只有一套真相；`2DRPGEngine` 在三项标准上都更完整 |
| 俯视角动作表现层 | `TopDownEngine` | 替换薄实现并吸收到 `GameCore` | 角色能力、移动、武器、命中、受击和反馈的组合模式更成熟，但不能把它的 manager / 输入 / UI 一起带进来 |
| 通用工具层 | `YokiFrame` | 直接替换项目侧重复工具 | 对象池、文件层、输入重绑定、资源/场景工具和 UI 工具位更深，但它不竞争玩法真相 |
| 开放世界模拟层 | `FantasyWord` | 三方都不接管，项目侧后建 | 三方都不完整覆盖区域/Cell、队伍、派系、AI 日程、经济和局部模拟 |

## 直接替换

这些不是“参考一下”，而是薄弱实现应退场：

| 系统 | 替换方向 | 正式落点 |
| --- | --- | --- |
| 对象池 | 项目侧浅池退场，统一改 `YokiFrame GameObjectPoolService` | `GameCore` 现有调用点直接用 `GameObjectPoolService` |
| 武器执行层 | `2DRPG` 薄攻击执行退场，改用 `TopDown Weapon` 风格状态机 | `WeaponExecutionRuntime + WeaponHitWindowRuntime + ActiveAbilityBase` |
| 角色动作阻断模型 | 分散的 `CanFire/Can/IsPushed` 退场，改成统一权限合同 | `AbilityPermissionSettings + ActiveAbilityBase + CharacterBase` |
| 项目侧多余兼容层 | `Bootstrapper/RuntimeContext/ModuleInstaller/EventBus` 已撤出，不得复活 | `GameManager + AGameSystem + GameConfig` |

## 正式融合

这些不是二选一，而是“真相源一套，能力来源分层吸收”：

| 系统 | 真相源 | 吸收来源 | 正式边界 |
| --- | --- | --- | --- |
| 地图、检查点、传送、重生 | `2DRPG MapSystem` | `TopDown Level/Checkpoint` 的边界、出生点、重生延迟、相机样板 | 只吸收表现配置，不接入 `TopDown LevelManager` |
| 玩家移动和控制器 | `2DRPG` 的输入语义与玩家身份 | `TopDown CharacterMovement/Ability` 的动作执行与阻断模式 | 只保留 `GameCore` 正式控制器，不新增并行控制器 |
| 生命数值与受击表现 | `RPG Stats` | `TopDown` 的击退、无敌帧、反馈样板 | 数值真相不迁到 `TopDown Health` |
| 存档 | `2DRPG SaveDataBlock` | `YokiFrame SaveKit` 的槽位、版本、删除、文件承载 | `SaveKit` 不是世界状态模型 |
| 输入 | `GameCore InputSystem` | `YokiFrame InputKit` 重绑定工具 | 不接入 `TopDown InputManager` |
| 背包与角色操作目标 | 全局 `InventorySystem.items/money` | 当前控制角色边界 + `CharacterEquipment` 目标解析 | 背包仍一套真相，装备/使用目标跟随当前控制角色，但装备执行必须走正式角色装备组件 |

## 暂不动

这些现在硬做只会制造第二真相或提前拆层：

| 系统 | 当前结论 | 不动理由 |
| --- | --- | --- |
| UI 菜单整体迁 UIKit | 已完成宿主替换，不再回退双栈 | 当前正式菜单宿主已经是 `UIManager + UIKitMenuPanelBase + UIKit` 原生 stack；真正要防的是旧 `AUIMenu/UIMenuManager`、adapter、wrapper 或第二宿主回潮 |
| 世界层目录晋升 | 暂不把 `GameCore` 提前拆到 `World/Characters/Combat/...` | 对应系统还没形成 FantasyWord 自己的独立真相源 |
| 开放世界模拟代码骨架 | 暂不先写空 `World` 框架 | 没有具体能力和验收口径前，空壳只会制造伪架构 |
| 完整点击移动 / 自动靠近 / 控制组穿越 | 暂不硬做 | 当前只保留当前基础点击移动链路；完整能力仍缺导航 Provider、点击移动执行层、实例宿主和出生点分流宿主这 4 个一级参考位 |

## 目录裁决

| 位置 | 正式动作 | 正确理由 |
| --- | --- | --- |
| `Assets/Scripts/GameCore/Runtime` | 保留为当前正式 runtime 总根 | 在世界层、角色层、表现层还没形成独立真相源前，集中根更符合三项标准 |
| `Assets/Editor/GameCore` | 保留为只服务 `GameCore` 的编辑器根 | 编辑器工具本来就不属于玩法系统，应受 Unity `Editor` 编译边界保护 |
| `Assets/Plugins/TopDownEngine` | 保留第三方原件边界 | 便于升级、对照和阻止 TopDown manager 被误当项目正式入口 |
| `Assets/Plugins/YokiFrame` | 保留第三方工具层边界 | 便于直接用稳定工具入口，不再维护浅包装 |

## 当前硬缺口

这里要分成两层看，不能混成一张“还差 5 项”的待办单：

1. `2D 移动与场景组织` 的 4 个一级缺口：
   - 单机/本地 2D 导航 Provider
   - 2D 点击移动执行闭包
   - 单机/本地场景实例宿主参考
   - 单机/本地出生点分流宿主参考
2. 更大一层的长期缺口：
   - 开放世界模拟层的区域/Cell、队伍、派系、AI 日程、经济和局部模拟仍未开工

前四个决定的是“当前能不能继续补 2D 移动与场景组织正式闭包”；最后一个决定的是“Skyrim/Kenshi 目标下的大世界模拟何时正式开工”。它们不是同一层待办。

## 禁止项

- 禁止用“当前已经用了谁”作为技术理由。
- 禁止新增 `Compatibility`、`Adapter`、`Wrapper`、`Facade`、`FoundationSupport` 这类双轨层。
- 禁止让 `TopDownEngine` manager、`YokiFrame Architecture/EventKit/SingletonKit` 接管正式游戏生命周期。
- 禁止为了“看起来像最终产品目录”提前拆 `GameCore`。
- 禁止在一级缺口没补齐前，硬做点击移动、自动靠近、实例入口或控制组穿越。
