# 测试场景与 AI 复用入口

## 适用范围

- 测试场景、样例场景、AI 自动化复用入口和场景验证边界。
- 本文不记录历史恢复任务的下一步。

## 当前正式场景入口

- Build Settings 当前场景：`Assets/Scenes/SampleScene.unity`。
- `Assets/Scenes/EquipmentSystemDemo.unity` 是候选换装演示场景，不属于当前正式启动入口。
- `Assets/Scenes/ClickMoveTest.unity` 当前只能视为“目标中的验证场景路径”，不能继续无条件当成已纳入版本控制的正式验证入口。
  当前静态门禁已经锁到：`ClickMoveTest.unity` 与 `.meta` 目前未被 git 跟踪。
  在它重新进入版本控制前，任何 smoke、AIBridge 脚本、验收记录和完成口径，都不得把它当成和 `SampleScene.unity` 同等级的正式场景真相。
  同时，Unity 人类可见场景菜单也不得继续直接暴露它，避免误导成“正常可点的正式入口”。
- `Assets/_Recovery` 属于旧 Unity 恢复场景来源，不是当前正式场景入口。

## 场景分类

- 正式场景：玩家会进入或构成产品内容的场景。
- 测试场景：为某条正式合同提供可重复验证的场景。
- 恢复场景：Unity 崩溃、旧工程恢复或历史迁移留下的证据场景。
- 临时场景：一次性排查或展示用，任务结束后删除或归档。

## AI 自动化规则

- 默认用 AIBridge 后台执行，不聚焦 Unity，不切 PlayMode，不截图。
- 验证默认先做静态证据或编译敏感搜索；只有静态证据不足以覆盖真实玩家风险时，才升级到必要端到端 smoke。
- EditMode、PlayMode 和定向场景验证都不是每个需求的默认步骤；只有端到端 smoke 仍不足以保护正式数据合同、存档/序列化兼容、引用闭包或其他高风险回归时，才补少量定向验证。
- 场景验证入口只验证现有正式资产和场景，不在验证过程中补建正式链路。

## 编辑器直进约束

- 编辑器 PlayMode 不得把当前打开的项目场景劫持到另一套启动方式，例如壳场景、playtest snapshot、临时存档链或任何 `playModeStartScene` 重定向。
- 测试场景若需要“直进可见”“首帧不黑屏”“直接出现 UI”等表现，必须收口到该场景自身的正式配置、正式系统接线或正式资产状态，不能靠 editor 脚本在进入 PlayMode 前后偷改运行时入口。
- 不允许再新增“场景 marker -> 改写启动链”这类隐式约定；场景是否可直进、是否黑屏、是否展示 UI，必须能从场景自身配置直接读出来。

## 后续要求

- 为俯视角玩家、交互、地图、装备/换装、战斗建立测试场景前，先定义正式合同。
- 若 `GameCore` 中同职责正式闭包已经存在，例如当前 `Movable + Controllers/PlayerController`，不得再新建并行控制器测试场景来证明“功能先能跑”。
- 只有在参考缺口已被证据锁定、且无法直接在现有正式闭包上对齐时，才允许考虑临时测试场景；但必须先写流程理由文档并向用户上报，获批后才能创建。文档至少说明参考缺口、临时场景目的、拟新增对象以及删除/并回时机。
- 这类流程理由文档默认写到当前活跃 `openspec/changes/<change-id>/parallel-trial-rationale-<topic>.md`，不写进 `.spec/knowledge/features/project` 长期规范。
- 旧换装恢复场景不自动成为新游戏用户故事。
- 若要从旧恢复场景提取结构，先写清提取目标、来源场景和目标正式落点。
