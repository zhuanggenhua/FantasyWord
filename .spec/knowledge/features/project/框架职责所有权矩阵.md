# 框架职责所有权矩阵

> 用途：回答“什么是框架、什么是业务内容、什么重复、什么保留、什么剔除”。
> 本文优先级高于按来源整体搬运的判断。若同一职责冲突，只保留设计更好的正式真相，不因为当前已被依赖就继续保留。

## 判定原则

- `单一职责` 是最高优先级。一个系统只应拥有一种清晰真相，不把生命周期、输入、UI、存档、属性、内容流程全部塞进同一个全局对象。
- `系统` 不等于业务垃圾。背包、任务、对话、属性、能力、装备、制作、卡组、牌局这些系统可以是框架模块。
- `具体内容` 才是业务内容。某个物品、某张卡、某个 NPC、某个任务链、某个商店、某个菜单文案，不应决定框架形状。
- `被依赖` 不是保留理由。若同职责存在更好的实现，正确动作是迁移依赖并替换，不是为了少改调用点保留较差的一边。
- `单例` 不是默认答案。它只适合稳定宿主、工具缓存或项目唯一外设入口；不适合承载可切换模式、可保存世界、牌局状态、角色属性真相或 UI 栈真相。

## 三层分类

| 类别 | 说明 | 示例 | 当前动作 |
| --- | --- | --- | --- |
| 框架机制 | 负责生命周期、输入、资源、存档文件、对象池、UI 宿主、模式切换、事件派发机制 | `GameManager`、`InputSystem`、`SaveKit`、`GameObjectPoolService`、Yoki `EventKit`、`UIKit` 宿主 | 保留或替换成最清晰的一套入口 |
| 领域框架模块 | 可跨具体内容复用的玩法系统壳和数据真相 | `InventorySystem`、`JournalSystem`、`DialogueSystem`、`Stats`、`Ability`、卡组/牌局系统 | 可以保留，但要剥离具体流程和重复真相 |
| 具体业务内容 | 具体物品、卡牌、任务、商店、NPC、菜单文案、关卡样板 | 某把武器、某张卡、某条任务、某个店铺 | 当前框架阶段不主动扩写，不用它们验证地基 |

## 所有权总表

| 职责 | 正式所有权 | 保留什么 | 剔除什么 | 待裁决点 |
| --- | --- | --- | --- | --- |
| 项目生命周期宿主 | 当前暂由 `GameManager + AGameSystem` 承担最小启动宿主 | 场景启动、系统收集、`AGameSystem` 生命周期分发 | 新增 `GameManager.XxxSystem` 静态快捷入口；把开放世界、牌局、UI 栈继续塞进同一个根 | 是否拆成 `ProjectRoot / WorldRuntime / ModeRuntime` 三层宿主 |
| 单例策略 | 单例只作为宿主访问和工具缓存，不作为领域状态默认模型 | `GameManager.Instance` 作为当前场景根；继承自 2DRPGEngine 的 `GameManager.XxxSystem` 继续作为 RPG 基线正式入口；Yoki 工具内部池和缓存 | TopDown 式 `GameManager + LevelManager + InputManager + GUIManager` 多单例接管；Yoki `SingletonKit` 接管玩法生命周期；新增开放世界/牌局状态快捷入口 | 现有入口不因“单例形式”默认迁移；只有出现更具体的 World/Mode owner 或同职责退步证据时才收缩 |
| 背包 | 领域框架模块，不是具体业务 | 物品集合、金钱、装备位、存档数据块、通用转移合同，以及明确的查询/遍历入口 | 具体物品、具体商店流程、具体 UI 菜单跳转绑死背包真相；直接把内部可变 `Dictionary` 暴露给外部读写 | 全局背包还是角色/队伍/容器分层背包，需要开放世界和队伍语义锁定 |
| 任务/日志 | 领域框架模块 | 任务状态机、进度数据、条件合同、存档数据块，以及明确的查询/遍历入口 | 具体任务链、NPC 台词、任务菜单流程；直接把活跃/完成任务底层 `List` 当正式 API 暴露 | 开放世界动态任务、区域外任务推进和卡牌小游戏奖励是否共用同一任务系统 |
| 对话 | 领域框架模块 | 对话通道、节点树、选项推进、可中断播放合同 | 具体台词、具体 NPC 流程、具体 UI 样式 | UI 宿主迁移后对话 HUD 是否仍用现有菜单模型 |
| 属性 | 角色实体级 `AbilitySystemComponent + FormalGameplayAttributeSet` | 生命、法力、上限、基础数值、当前资源、属性事件 | `Stats/currentStats` 重新持有属性真相或与 `GAS AttributeSet` 并行结算 | `Stats` 只保留快照 DTO、UI/事件载荷、启动期 bootstrap buffer 或批量计算输入 |
| 能力/效果 | 当前是 `Ability/Effect/Stats`，TopDown 已吸收动作执行合同 | 能力数据、效果结算、武器执行状态机、命中窗口 | TopDown `Health/CharacterAbility/Weapon` 整体接管玩家数据和生命真相 | `EX-GAS` 是否替换能力/效果规则层，需要专项矩阵 |
| 输入 | `GameCore InputSystem` 保语义，`YokiFrame InputKit` 只做重绑定工具 | 输入动作订阅、当前输入目标、绑定导入导出 | TopDown `InputManager`、每个控制器自己订阅输入 | 卡牌小游戏进入后，需要 `ModeInputContext`，不能复用开放世界移动输入 |
| 玩家长期 Hero vs 当前受控对象 | `PlayerSystem` 同时拥有两种明确语义：`PlayerInstance` 是长期玩家 Hero，`currentControlledCharacter/currentControlledHero` 是当前前台受控对象 | 长期等级、长期背包归属、存档登记、地图穿越目标、当前前台 UI 跟随 | 用一个含糊的 `Player` 概念同时表示“长期玩家数据”和“当前前台控制对象”；让 UI、交互、命令层自己散落 `?? PlayerInstance` 回退规则 | 多角色、队伍和模式切换进入后，要继续沿 `PlayerSystem` 扩展，不再恢复模糊的全局 `Player` 别名 |
| 事件派发 | Yoki `EventKit.Type` | 强类型事件派发、注销 token、编辑器监控 | 恢复 `NotificationSystem`、继续使用 Yoki `StringEvent` 充当玩法总线 | 正式事件统一通过 `GameRuntimeEvents + EventKit.Type` 分发，不再保留第二事件总线 |
| 领域事件定义 | `GameCore` 项目侧事件结构 | 战斗、物品、任务、地图、UI、音频、世界、卡牌等事件的领域命名和载荷类型 | 把项目玩法事件定义进 Yoki 插件本体；恢复把所有领域事件继续堆进 `NotificationSystem` | 后续按领域目录拆分事件文件 |
| 数据库注册表 | `DatabaseRegistry` 自身 | GUID 建档、引用解析、转换映射、编辑器登记操作 | 把 `entries/GUIDConversionMap` 两张底层字典继续公开给外部直接读写 | 后续若要拆编辑器批处理，也应继续通过 `DatabaseRegistry` 自己的方法，不恢复裸字典口子 |
| 内容资产读取面 | 各资产类型自身 | 配方输入输出、任务提示覆盖、标记任务条件、商店商品、制作站配方、怪物掉落、对话行与选项等只读内容访问 | 继续把底层 `Array/Dictionary` 直接公开给运行时或编辑器调用点 | 后续若继续收口其他资产字段，也应沿“私有序列化字段 + 只读访问面”推进 |
| UI 栈 | 当前正式菜单宿主是 `UIManager + UIKitMenuPanelBase + UIKit` 原生 stack | 菜单语义、面板生命周期需求、UI 缓存需求 | 旧 `AUIMenu/UIMenuManager`、adapter、wrapper 或第二宿主回潮 | 后续只继续清理旧资源与共享构件，不再重新裁决宿主归属 |
| 开放世界运行时 | `FantasyWord` 自建 | 区域/Cell、队伍、派系、AI 日程、经济、局部模拟 | 塞进 `GameManager` 静态快捷入口；让 TopDown `LevelManager` 接管世界 | 需要独立 `WorldRuntime` 或同级宿主，不应只是 `MapSystem` 子功能 |
| 游戏内卡牌自走棋模式 | 独立 `ModeRuntime` / 子域宿主 | 卡牌收藏、卡组、牌局棋盘、自动战斗回合、奖励结算接口 | 直接复用开放世界当前地图、移动输入、当前控制角色或菜单栈作为牌局真相 | 卡牌收藏可接存档/背包；牌局状态必须独立于开放世界当前地图，但可依赖项目级服务和长期玩家数据 |

## 单例裁决

单例对本项目不是“最适合”或“不适合”的二选一，它只适合很窄的职责：

| 用法 | 裁决 | 理由 |
| --- | --- | --- |
| 项目唯一启动根 | 暂可保留 | Unity 场景需要一个可见 composition root，当前 `GameManager.Instance` 可作为最小启动锚点 |
| 工具缓存和对象池 | 可用 | 例如池、资源句柄、设置对象，状态不表达世界真相 |
| 领域系统真相 | 不作为默认 | 背包、任务、属性、牌局、开放世界状态都可能随存档、世界、模式或角色变化，不能天然全局唯一 |
| 多游戏模式 | 禁止直接全局化 | 开放世界和卡牌自走棋有不同输入、UI、状态推进和存档边界，应由模式宿主持有 |
| 第三方 manager 整体接管 | 禁止 | TopDown 多 manager 会制造第二生命周期；Yoki `SingletonKit` 是工具，不是玩法宿主 |

推荐方向是：

- `ProjectRoot`：项目级服务和配置，例如包、资源、音频后端、存档文件层。
- `WorldRuntime`：开放世界当前存档、地图、区域、角色、派系、经济和世界事件。
- `ModeRuntime`：当前游戏模式，如开放世界探索、游戏内卡牌自走棋牌局、剧情演出、主菜单。
- `Entity/Component`：角色、物品、卡牌单位、棋盘格等局部状态。

这套方向接近 UE 的分层思路：项目级、世界级、模式级、实体级分开，而不是所有东西都挂到一个全局 manager 上。

## GAS 与当前属性系统

当前事实：

- `GameCore` 正式运行时代码已经引用 `GAS.Runtime`、`AbilitySystemComponent`，并且角色实体级 ASC 已真实挂接。
- 当前属性真相已经收口到角色实体级 `AbilitySystemComponent + FormalGameplayAttributeSet`；`Stats / ObservableStats / CharacterBase.currentStats` 只作为快照、事件载荷、启动缓冲或局部计算输入。
- 当前最大风险不再是“是否能接 GAS”，而是旧 `Stats/IEffect` 残留如果长期保留，会形成第二规则真相。

正式裁决：

- EX-GAS 2.0 已是当前项目的正式属性/能力规则方向，不再按“候选工具”口径描述。
- 当前项目处于起步期；当同职责旧实现与 EX-GAS 正式链冲突时，默认允许直接替换，不为了历史资产保留长期兼容层。
- 禁止新增任何把旧 `Stats/IEffect` 与 EX-GAS 并行长期运行的包装层、镜像层或双写层。
- 仍允许项目侧保留 `AbilitySheet` 的旧数据读取和 `GameplayFeedbackSet` 的表现资源桥；`AbilityExecutionAsset`（已删除） 不再保留，且不得重新拥有与 EX-GAS 同职责的规则真相。

## TopDown 与当前 GameSystem 的对比

| 维度 | 当前 `GameManager + AGameSystem` | TopDown manager 体系 | 当前裁决 |
| --- | --- | --- | --- |
| 生命周期 | 一个根收集多个系统 | `GameManager/LevelManager/InputManager/GUIManager` 多根互相调用 | 当前更容易控；现有 RPG 基线快捷入口保留，新增 World/Mode 状态不得继续挂到静态入口 |
| 输入 | `InputSystem` 统一订阅，再转给当前目标 | `InputManager` 单例并绑定 TopDown 控制假设 | 保留当前输入真相，吸收 TopDown 手感，不接 TopDown 输入根 |
| UI | `UIManager + UIKitMenuPanelBase + UIKit` 原生 stack | `GUIManager` 绑定暂停、死亡、移动端控件和点数 | 正式宿主已经裁决为 `UIKit`；TopDown `GUIManager` 继续禁止接管 |
| 角色动作 | 2DRPG 较薄，当前已吸收 TopDown 执行合同 | TopDown 组件拆分更成熟 | 动作层继续按 TopDown 模式替换薄实现 |
| 世界规则 | RPG 数据、存档、地图、背包、任务闭合 | 动作关卡、生命、点数和 GUI 假设更强 | 世界规则继续保 RPG 真相，但要拆清全局 system 边界 |

## 事件系统裁决

`NotificationSystem` 和 Yoki `EventKit` 确实重复，裁决如下：

| 职责 | 胜者 | 理由 |
| --- | --- | --- |
| 事件派发机制 | Yoki `EventKit.Type` | 强类型载荷、注销 token、编辑器监控、派发时可安全注销监听者，优于巨大 `UnityEvent` 字段表 |
| 事件领域语言 | `GameCore` | 战斗、物品、任务、地图、世界、卡牌等事件属于本项目语义，不能写进 Yoki 插件本体 |
| 当前正式调用面 | `GameRuntimeEvents` + Yoki `EventKit.Type` | 旧通知中心文件、测试、场景对象和项目侧调用面都已删除；正式入口只剩一套 |
| 长期方向 | `GameCore` 事件结构 + Yoki `EventKit.Type` | 不保留第二事件总线，不为兼容再包一层 |

因此后续新增事件不得再恢复 `NotificationSystem`。如果必须触发新事件，应先定义项目侧强类型事件结构，再用 Yoki `EventKit.Type.Send` 派发。

这里要再拆一层，避免把“删除旧通知中心”和“删除全部 UnityEvent”混成一件事：

| 事件范围 | 正式做法 | 当前例子 | 为什么保留/替换 |
| --- | --- | --- | --- |
| 项目级领域事件 | `GameRuntimeEvents` + `EventKit.Type` | 地图加载、存档载入、任务状态、背包变化、音频请求、受击/恢复/掉落/拾取等表现广播 | 这类事件会跨系统、跨宿主传播，必须只有一套正式总线 |
| 宿主级或对象级局部通知 | `UnityEvent` 可保留 | `CharacterBase.currentStatsChanged`、`Hero.equippedAbilitiesChanged`、`Movable.teleported`、`PlayerSystem.currentControlledCharacterChanged` | 真相就在拥有者对象自己身上，监听者只是跟随刷新，不应升级成项目总线 |
| Inspector 接线或动画/UI 层局部协作 | `UnityEvent` 可保留 | 对话通道、UI 条目点击、本地动画收尾 | 这是 Unity 原生局部通信能力，不等于第二事件总线 |

判定标准不是“是不是 UnityEvent”，而是：

- 同一个事实是否出现了两套跨系统入口。
- 事件真相是否已经离开原拥有者，变成了项目级广播。
- 监听者是不是需要跨地图、跨宿主、跨系统统一接入。

只要答案是否定的，局部 `UnityEvent` 不是问题；真正要删的是旧 `NotificationSystem` 这类并行项目级总线。

结论：

- TopDown 不是更纯的总框架。
- 当前 GameSystem 也不是最终理想形状。
- 正确下一步是收缩静态入口、建立 `Project/World/Mode/Entity` 所有权层级，并逐项替换重复真相。

## 直接门禁

当前已经可以直接守住的重复真相：

- 禁止新增 `GameManager.XxxSystem` 静态快捷入口；现有继承自 2DRPGEngine 的 RPG 基线入口不因“单例形式”默认收缩，只有在参考流程对照或新 World/Mode owner 证明它承载了错误职责时才迁移。
- 禁止把“GameCore 不得正式引用 GAS”继续当作活跃规则。当前真正的门禁是：不得新增 EX-GAS 与旧 `Stats/IEffect` 的并行长期真相。
- 禁止 `GameCore` 直接依赖 TopDown `GameManager/LevelManager/InputManager/GUIManager/Health` 作为正式真相。
- 禁止 `AUIMenu` 与 `UIKit UIPanel` 通过 adapter/wrapper 双栈运行。
- 禁止开放世界或卡牌自走棋模式状态挂到 `GameManager` 静态快捷入口。
- 禁止 `InventorySystem`、`JournalSystem`、`QuestProgress`、`Hero` 重新公开内部可变 `List/Dictionary/Array` 作为正式运行时入口；外部只能走显式查询、遍历、快照或单项查询方法。
- 禁止 `DatabaseRegistry` 重新公开 `entries/GUIDConversionMap` 两张底层表给运行时或编辑器代码直接改写；正式入口应继续收敛在 `HasGUID/GetEntries/Register/Unregister/SetConversion/...` 这组方法。
- 禁止 `Recipe`、`Quest`、`GameFlagTask`、`CraftingStation`、`Shop`、`MonsterSheet`、`DialogueSequence` 这类正式内容资产继续把底层 `Array/Dictionary` 当公开可变接口暴露给运行时或编辑器调用点。
- 禁止 `GameConfig`、`DialogueNode`、`Quest`、`MonsterSheet` 这类正式拥有者继续把内部 `ICommand` 本体直接借给外部；外部只能让拥有者自己执行，或走显式注入/显式方法。
- 禁止 `SaveFile`、`DialogueTree` 这类模板/运行时缓存对象继续把内部模板块、根节点或消息缓存直接挂成 public 入口；模板必须走快照，缓存必须走最小方法口。
- 禁止 `Persistable` 再把内部 persistence handler 公开给 runtime 调用方直接强转；正式协作只能拿标识符、实例化参数或 editor 专用入口。
- 禁止 `DialogueSystem` 再把 `DialogueChannel` 子对象直接挂成 public 入口；正式调用必须回到系统自己的播放、排队、监听和跳过方法。
- 禁止恢复 `NotificationSystem` 或任何等价旧通知壳；新增事件必须用项目侧强类型事件结构承载，并由 Yoki `EventKit.Type` 派发。
- 禁止恢复 `GameplayFeedbackSet` 静态 C# 事件或 `Raise*Presentation(...)` 转发壳；纯表现广播也必须统一走 `GameRuntimeEvents + EventKit.Type`。
