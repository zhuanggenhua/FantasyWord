# 开发与验收规范

## 前提锁定

准备修改代码、配置、数据、资源、场景或包配置前，必须确认：

- 问题对象：本轮处理的具体文件、资源、目录、包或场景。
- 真相来源：用什么证据证明它确实命中本轮问题。
- 目标入口/环境：修改作用在哪个 Unity 工程、Editor、包配置或运行入口。
- 验收口径：修完后用什么方式确认。

四项缺一时，只能继续补证据或提出最小问题。

## 需求确认反馈

- 开工前必须先把本轮要做的范围说清楚，再动手。
- 如果执行中发现任务已经偏出用户明确范围，必须立刻停下，先回到范围确认，不得顺手扩写。
- 用户明确说“不做端到端”或“不启动编辑器”时，默认直接遵守，不再继续推进对应流程。
- 当用户明确说“这是测试 UI / 测试预览入口，不是成品界面”时，默认只收口到可测、易用、低信息密度的测试入口；不得自行扩写为玩家向 UI 优化、装饰性改版或额外流程设计。

## 旧内容处理

- 旧恢复记录、乱码文档、旧测试脚本和旧资源残留先分类：正式链路、归档参考、真正垃圾。
- 仍有参考价值但不进入正式链路的内容归档，不直接删除。
- 真正垃圾必须同时满足：无正式引用、无参考证据价值、无归档必要、无未来明确复用面。

## 验证层级

- 若本轮命中 `2D 移动与场景组织`，先记住：这里的 4 个一级缺口只描述这一条线缺什么正式参考，不覆盖开放世界模拟层本身；区域/Cell、队伍、派系、AI 日程、经济和局部模拟仍是另一层长期架构任务。
- 默认验收不是“功能代码一份、测试代码再写一份”。测试只在能降低真实回归风险时出现；若静态证据已经能证明结论，不为每个需求机械补测试。
- 新需求默认不新增自动化测试；默认验收顺序是：静态证据或编译敏感搜索 -> 必要端到端 smoke -> 仅在端到端仍不足时才补少量关键合同测试。只有前一层不足以覆盖真实风险时，才升级到后一层。
- 除非用户明确要求，或风险已经被证据锁定为“静态证据和必要端到端都保护不了”，否则不得把“补测试”当成默认实施步骤。任何会把实现代码和测试代码拉成近似 1:1 体量的方案，默认先判定为过度建设。
- 若一轮需求看起来会演变成“功能代码写一份，测试代码再镜像写一份”，默认直接判退该测试方案，先回到最小真实入口的端到端 smoke，而不是接受近似双倍代码量作为常态。
- 除非用户明确要求 TDD，或当前改动命中高风险合同，否则不把“补一份同粒度自动化测试”当成完成条件，也不以测试数量作为工作量目标。
- 默认不建立“一个需求对应一个测试文件/一组测试用例”的映射。若已有端到端 smoke 已覆盖风险，优先复用或最小补强现有 smoke，而不是再复制一套同粒度测试代码。
- 文档与包清单改动：先做静态读取、路径检查、关键词检查。
- C# 代码改动：至少做编译敏感搜索；只有触及玩家可见流程、跨系统合同、存档/序列化兼容、引用闭包或高风险回归时，才新增或修改 Unity Test Framework 测试。
- 测试不是每个需求的默认交付物。优先用必要端到端测试；只有端到端无法稳定保护真实风险时，才补场景/Prefab 合同测试或其他关键合同测试。禁止为了“看起来完整”给每个 helper、薄入口转发、简单 API、目录调整或文档同步机械补测试。
- 新增非端到端测试前，必须能说明它保护的现实风险、为什么静态门禁或现有端到端测试不够，以及它是否不会演变成和功能同等体量的维护负担。说不清时不写；如果只是为了让测试数量看起来完整，也不写。
- 端到端 smoke 也不是越多越好。默认只保留能直接覆盖真实玩家入口、真实数据入口或真实存档入口的最小链路；已经被更上层 smoke 覆盖的重复场景，不再平行扩张。
- 包或 ProjectSettings 改动：需要 Unity 导入确认时，用当前唯一正常 Editor + AIBridge。
- 场景、Prefab 和 PlayMode 行为：只有静态证据不足时才升级到场景/PlayMode 验证。
- 若正式闭包已经存在，例如当前 `GameCore/Movable + Controllers/PlayerController` 玩家控制器闭包，验证默认应围绕该正式闭包补组件、补接线、补测试或补场景证据；不得通过在 `Assets/Scripts/test` 或测试场景里另起一套同职责实现来替代正式闭包验证。
- 若本轮涉及 2D 导航、点击移动、场景实例宿主、出生点分流，或相关的控制组穿越/自动靠近/入口条件问题，先用 `.spec/knowledge/features/project/2D移动与场景组织找参考清单.md` 快速筛掉明显不合格的来源，再用 `.spec/knowledge/features/project/2D移动与场景组织缺口矩阵.md` 锁定它命中的是一级缺口还是二级缺口；一级缺口没有正式参考时，不得进入实施态。
- 若因为参考缺口确实需要临时试做同职责控制器、测试场景或其它并行验证入口，必须先有流程理由文档，并先向用户上报批准。文档至少包含：`参考缺口`、`不能直接复用正式闭包的原因`、`拟新增文件/场景清单`、`回收或并回正式闭包的退出条件`。未批准前不得实施。
- 不启动 Unity 的迁移收口可使用 `scripts/Invoke-WorkspacePreflight.ps1` 检查空目录和禁用废弃入口；已登记的未来扩展占位目录按合同占位保留，不作为待清理垃圾；该脚本失败只代表仓库结构需处理，不等同于 Unity 编译失败。
- 地基启动链静态收口可使用 `scripts/Invoke-FoundationStaticGate.ps1` 检查 `GameManager + AGameSystem + GameConfig` 最小闭包和 `SampleScene` 的新启动接线；该脚本通过只证明静态入口闭合，不等同于 Unity 已成功导入或运行。
- 插件正式边界静态收口可使用 `scripts/Invoke-PluginFacadeBoundaryGate.ps1` 检查项目侧代码是否绕过正式插件边界而直接依赖第三方插件类型；当前允许的正式边界包括 `Presentation/Runtime/Audio`、`Items/Runtime/Equipment`、`GameCore/Runtime/Audio`、`GameCore/Runtime/Database/Audio`、唯一已登记的 `GameCore/Runtime/Presentation/GameplayFeedbackSet.cs` 反馈闭包，以及 `FormalGameplayEffectDamageBridge` / `FormalGameplayEffectDamageHelper` / `FormalGameplayEffectDamageSystem` / `Gas2DTargetCatchers` / `FormalAbilitySystemAttributeExtensions` / `ActiveAbilityBase` / `TimelineActiveAbility` / `TaskApplyWorldElement` / `CharacterBase.Abilities` / `CharacterCommandExecutor` / `CuePlayGameCoreAnimator` / `CuePlayGameCoreAudio` / `CuePlayGameCoreFeedback` / `CharacterAbilitySet` / `CharacterAbilitySet.FormalRules` / `FormalAbilityRuntimeBootstrap` 这组已被正式 spec 登记的 RPG/GAS 规则桥、正式伤害桥、正式属性写入适配、通用 Timeline 输入桥、世界元素 Task、角色激活上下文入口、玩家命令到 GAS 激活上下文的转换桥、2D TargetCatcher 扩展、Cue 表现桥与启动引导闭包；对应的正式 EX-GAS 合同测试及 `GasEditModeTestHelper` 测试辅助入口也允许在 `Assets/Editor/GameCore/Tests/` 内直接引用第三方类型；`MeleeAttackAbilityEditModeTests` 允许直接构造 `MMFeedbacks` 探针，只用于验证 `CuePlayGameCoreFeedback -> GameplayFeedbackSet` 正式反馈边界。该脚本通过只证明架构边界未被静态打穿，不等同于运行时行为完整。

## Bug 经验沉淀

- 具体 bug 案例、误判路径、根因证据和原始位点验收不得长期堆在本文件；统一登记到 `.spec/knowledge/features/project/Bug排查索引.md` 与 `.spec/knowledge/features/project/bugs/`。
- 本文件只保留通用验收规则：任何 bug 修复都必须回到原始位点验证，止血、降噪、绕过不得称为根因修复。
## Unity 自动化边界

- 默认不聚焦 Unity，不切 PlayMode，不打开/切换场景，不截图。
- 需要高层验证时，先说明当前低层证据缺口。
- 同一轮没有新成批修复前，不重复跑高成本验证。
- 排查“已经打开的编辑器窗口/插件窗口里某个控件无反应、拖动卡顿、选帧不刷新、预览不显示”时，问题对象默认是**当前已打开窗口实例和用户刚操作的窗口状态**。自动化取证必须优先附着现有窗口实例读取状态或模拟同一路径；不得先调用 `ShowWindow()`、重新打开窗口、强制读表、刷新缓存、重建页面、切换场景或重新绑定预览对象来复现。只有问题本身就是“窗口打不开 / 首次打开初始化失败 / 刷新按钮失败”时，才允许测试打开或刷新入口。
- 插件编辑器问题的验收必须回到用户原始操作位点。例如用户说“时间轴窗口已打开后拖选帧线卡、切到第 8 帧没显示判定框”，验收就必须在同一个已打开窗口、同一个预览实例、同一个选帧线/当前帧入口下验证；不能用“重新打开窗口后下拉框有 ID”“直接反射调用内部评估函数成功”替代原位点验收。
- 已暂停：2026-07-14 按用户要求停用 `.codex/skills/safe-image-reading` 与 AI 看图前压缩/上下文预算门禁；原文已备份到 `.spec/backups/safe-image-reading-disabled-20260714-224319/`。
- 验收截图必须区分真实截图与辅助图。局部放大图、裁切图、标注图、合成对照图只能作为排查辅助；用户要求截图或真实画面证据时，主证据必须来自真实 Unity 画面或真实运行入口，拿不到就说明当前没有真实截图证据。
- 可视 UI / 场景表现问题的主验收图必须来自同一真实执行现场：同一 Unity 工程、同一打开场景、同一 PlayMode / Editor 状态、同一批当前代码和资源。旧截图、兄弟目录截图、历史证据、临时合成图或只截外围容器的图，不能冒充当前完成证据。
- 当用户质疑“你看图了没有”“整体图”“端到端截图”或问题涉及布局、缩放、叠加、角色/装备/动作本体时，主证据优先使用当前真实 GameView 的 ScreenCapture 完整运行图，必须能同时看到问题对象和周边上下文；局部裁图只能作为细节辅证，并且必须明确来自同一张整屏真相源。临时离屏相机、RenderTexture、只渲染临时对象的截图和旧运行截图不得冒充真实验收图。
- 截图验收必须看见本轮问题本体。比如角色缩略图尺寸、中心展示叠加、装备图标、动作按钮和方向切换，证据图或审计表必须直接覆盖对应对象；只证明按钮存在、日志无报错、局部裁图看起来正常，不能替代“原始位点已经达标”。
- 若后续证据证明截图来自错误场景、错误角色、错误动作、错误方向、旧运行状态、审计脚本遗留状态或与当前修改无关的运行实例，该截图必须作废并回到正确入口重新取证，不得继续在错误图上解释细节。
- 若 Unity 启动被 `Recovering Scene Backups` 或同类“恢复未保存场景临时备份”流程拦住，默认先点击恢复场景并保留现场继续验证；不得把清理 `Temp/__Backupscenes` 当成首选恢复动作。
- 若本轮问题对象、目标入口和验收场景已经锁定，且恢复弹窗对应的正是该场景或同一条当前验证链的临时备份，必须直接点击恢复并继续；这不是需要用户额外确认的风险点，不得用“是否恢复场景”阻塞本轮排查。若用户已手动恢复，同一恢复动作不得再次阻塞排查，后续必须以恢复后的当前场景继续取证。
- 若 Unity 弹出“场景文件已在外部修改 / Scene has been modified externally”或语义等价弹窗，默认直接选择 `重新加载 / Reload`，从磁盘重新加载当前已锁定的目标场景，并继续复查场景、编译状态和 Console；不得再次把选择抛给用户。
- 其它阻塞当前任务的 Unity 模态弹窗，默认点击当前高亮的默认按钮或主操作按钮并继续，不得因普通确认弹窗长期挂起任务。若默认动作会删除本地资产、清理用户数据或覆盖无法确认归属的未知未保存内容，仍受删除核实和未知脏场景红线约束，只允许先取证。
- 只有恢复按钮不可用、用户当轮明确同意清理，或已经确认这些文件只是自动化生成且无保留价值的临时恢复残留时，才允许清理项目 `Temp/__Backupscenes`；不得自动处理 `Assets/Scenes`、用户手工备份目录、未知恢复目录或其它无法证明只影响恢复流程的文件。
- 若当前打开场景栈里混入 `Assets/_Recovery/*` 这类项目内已明确判定为“旧恢复场景来源、非正式入口”的场景残留，默认也先保留现场；只有确认它们只是已恢复后的无效临时残留，且不会丢失用户未保存内容时，才允许丢弃。
- 如果证据不足以证明恢复来源安全，或可能涉及正式场景脏数据、用户未保存内容或未知恢复来源，不得自动清理，必须先补证据或停下说明风险。
- 若 Editor 仍可响应、`isCompiling = false` 且“脚本编译失败标志”为真，而 `Console` / `Editor.log` 只有 Bee 后端异常，例如 `Internal build system error`、缺少 `BuildFinishedMessage`，没有 `error CSxxxx` 这类真实脚本编译错误，可先做一次公开重编译请求，再重新检查编译状态；这类动作只算验证环境恢复，不算业务代码修复。
- 上述 Bee 恢复只允许做一轮最小尝试；如果重编译后仍失败，或日志已经出现真实 C# 编译错误、资源导入错误、包解析错误，就必须回到具体报错继续定位，不得把它继续描述成“只是环境问题”。
- 若 `Editor` 长时间停在 `isCompiling = true`，且已锁定到 `AssetImportWorker*.log` / Unity crash 目录里的 `AssetImportWorker*.log` 崩溃，而不是业务脚本编译错误，默认先把它视为 Unity 验证环境异常；在确认当前正式场景是否 `dirty` 之前，不得擅自重启 Editor、重开场景、丢弃场景改动或做其它会影响用户当前编辑状态的恢复动作。
- 若同一时刻打开的是正式场景，且 `scene-list-opened` 证据表明该场景 `isDirty = true`，先判断它是否就是本轮已经锁定的问题对象、目标入口或验收场景。
- 如果 `dirty` 的正式场景就是本轮已经锁定的目标场景，并且它是在本轮自动化验证、截图、修复、PlayMode、场景恢复或同一条验证链中被弄脏的，默认直接保存该目标场景后继续验证；不得再向用户追问“是否保存 / 是否恢复 / 要不要更新规范”。保存前后必须各做一次 `scene-list-opened` 取证，并在汇报中说明保存的是哪个场景。
- 如果 `dirty` 的正式场景不是当前目标场景，或 dirty 来源不能证明来自本轮同一目标链路，才降级为只读取证：`editor-application-get-state`、`scene-list-opened`、读取 `Editor.log` / `AssetImportWorker*.log` / crash 目录；不得擅自重启 Editor、关闭窗口、磁盘重开场景或保存/丢弃未知用户改动。
- 用户当轮明确说“可以保存”“允许直接保存”“直接保存”或语义等价表达时，只是在上述目标场景规则之外补充授权当前已确认的正式场景保存动作；不得把这个问题反复抛回给用户，也不得把“是否要更新规范”作为继续任务的阻塞点。
- 若本轮为了 smoke 或取证确实进过正式场景相关的 PlayMode / `script-execute` / 场景受保护命令，收尾不以“命令返回成功”为准，必须额外用 `scene-list-opened` 复查正式场景是否仍 `dirty`。只要还是 `dirty`，就视为本轮自动化没有收尾完成，不得继续下一条写操作型 Unity 命令。
- 若 `Editor` 长时间停在 `isCompiling = true`，且已锁定到 `AssetImportWorker*.log` / Unity crash 目录里的 `AssetImportWorker*.log` 崩溃，同时 `scene-list-opened` 证据表明当前没有正式场景 `dirty`，则允许把它作为“验证环境恢复”自行处理一轮，顺序固定为：先取证当前 `Editor` 状态与相关日志，再执行一次最小 Editor 重启，随后只复查 heartbeat、编译态与 Console/日志是否收敛；这不算业务问题已修复。
- 上述“可自行恢复一轮”只适用于两类安全前提：① 当前没有打开任何 `dirty` 场景；② 当前只有项目已明确定义为自动化生成的临时场景 `dirty`，且可以按既有规则安全丢弃。除此之外一律视为前提未锁定，不得擅自恢复。
- 若完成这轮最小恢复后仍旧卡在 `isCompiling = true`、再次出现 `AssetImportWorker` 崩溃，或日志开始出现真实 C# 编译错误、资源导入错误、包解析错误，则必须停止自动恢复，回到具体报错继续定位；不得无限重试或把它继续归类成“只是环境问题”。

## 完成性口径

- 不把“已写文档”说成“已完成迁移”。
- 不把“包清单已改”说成“Unity 已成功导入”，除非经过 Unity 导入或包解析验证。
- 不把旧历史计划中的完成状态当成当前完成状态。
- 不把“临时 test 场景里有一套能跑的脚本”说成“正式闭包已经验证完成”；若正式闭包已存在，验收必须回到该正式闭包本身。
