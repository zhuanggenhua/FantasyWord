# 三方框架系统对照

> 先看长表时，建议同时打开 `框架三项判分矩阵.md`。
> 这份文档负责完整解释，矩阵负责把胜负压成可直接裁决的短表。
> 如果你只想直接知道“该替换什么、该融合什么、该冻结什么”，再配合 `框架正式动作清单.md` 一起看。
> 如果你只想先看结论，默认入口是 `框架最终裁决.md`。

## 为什么这里还是“三方表”

这里仍然只比较 `2DRPGEngine`、`TopDownEngine`、`YokiFrame`，不是漏掉了 `uMMORPG`。

原因很简单：

- `uMMORPG` 当前只够资格当 **2D 移动与场景组织的局部源码证据源**
- 它不参与 `RPG 世界规则真相 / 动作表现层 / 工具层` 这三条主线的总胜负
- 它也不构成当前项目的联机实现基线，更不是开放世界模拟层基线

所以这份表继续叫“三方框架系统对照”；`uMMORPG` 的职责是补一级缺口边界，不是升格成第四个总框架候选。

## 判断标准

本表不以“当前已经用了谁”作为理由。每个系统按三项判断：

| 标准 | 判断问题 | 胜出含义 |
| --- | --- | --- |
| 设计模式 | 模块职责是否清楚，行为是组合出来的还是靠巨型管理器堆出来的，数据和表现是否分离，生命周期是否有明确宿主 | 玩家和编辑器都能理解“这个系统负责什么”，扩展一个能力不需要改一串无关系统 |
| 软件工程 | 是否有单一真相源，是否容易测试和验证，是否减少重复状态，是否保护 Unity 序列化和 Prefab 接线，错误是否集中在少数入口 | 后续由 AI 或人修改时，出错面小，能用门禁和测试证明没有打穿边界 |
| 易用 | 策划/开发者能否通过 Inspector、Prefab、ScriptableObject 和少量代码快速组装玩法，是否有成熟样板和可复制配置 | 能更快开始做游戏，而不是先维护一套自造框架 |

### 三项标准的使用顺序

这里不是三列分数简单相加。

正确顺序是：

1. `设计模式` 先定职责类型
   先分清它是在解决长期世界状态、瞬时角色执行，还是通用工具问题。
2. `软件工程` 再定能否当正式拥有者
   重点看它会不会顺带带入第二生命周期、第二输入根、第二 UI 栈或第二存档真相。
3. `易用` 最后决定在正确赛道里谁更适合快速开始做游戏

所以本表不是在选“总冠军框架”，而是在判：

- 谁拥有世界规则真相
- 谁拥有动作表现真相
- 谁拥有工具真相
- 哪一层必须由项目自建

裁决规则：

- 三项都明显胜出的模块，直接作为正式真相源。
- 一方设计模式强，另一方软件工程或易用性强，则融合，但融合后的正式入口只能有一个。
- 一方只是“功能多”，但带来第二套生命周期、第二套输入、第二套 UI 或第二套存档真相，则不整体接管，只吸收具体模块。
- `YokiFrame` 默认只竞争工具层，不竞争 RPG 世界规则真相源；除非某个工具能明显替换项目侧重复实现。

## 错误理由与正确理由

以下这些说法都不成立：

| 错误说法 | 为什么错 | 正确口径 |
| --- | --- | --- |
| `GameCore` 现在就在项目里，所以继续放 `GameCore` 合理 | 这是现状描述，不是架构理由 | 只有当“集中根”在 `设计模式 / 软件工程 / 易用` 三项上都优于“提前拆成多个顶层目录”时，`GameCore` 才合理 |
| `TopDownEngine` 只是参考，所以不用和 `2DRPGEngine` 正面对比 | 参考源也必须参加同职责比较；否则“参考”会变成一个逃避替换的借口 | 应逐个系统比较：动作、移动、武器、命中、反馈这些位，`TopDownEngine` 是否明确更强；若更强，就吸收或替换 |
| `YokiFrame` 只是工具包，不需要纳入框架裁决 | 工具层也是框架的一部分；对象池、存档文件层、输入重绑定、UI 缓存都直接影响工程质量和易用性 | `YokiFrame` 不竞争玩法真相，但必须竞争工具层真相 |
| 只要三方都各有优点，就都包一层最稳 | 这会制造第二生命周期、第二输入根、第二 UI 栈和第二存档语义 | 允许的动作只有三种：`直接替换`、`正式融合`、`暂不动`；不允许双轨并跑 |

## 三方总表

这张表先回答“每一层该由谁正式拥有”，再往下看每个系统的细节。

| 框架层 | 设计模式胜者 | 软件工程胜者 | 易用胜者 | 最终动作 | 一句话理由 |
| --- | --- | --- | --- | --- | --- |
| RPG 世界规则 | `2DRPGEngine` | `2DRPGEngine` | `2DRPGEngine` | 直接作为正式真相源 | 地图、任务、背包、角色数据和存档语义必须只有一套真相，2DRPG 在这件事上最完整 |
| 俯视角动作表现 | `TopDownEngine` | `TopDownEngine` | `TopDownEngine` | 替换薄实现并吸收到 `GameCore` | 角色能力、移动、武器、命中和受击的组合模式更成熟，调手感也最快 |
| 通用工具 | `YokiFrame` | `YokiFrame` | `YokiFrame` | 直接替换项目侧重复工具 | 对象池、存档文件底层、输入重绑定和 UI 缓存这类工具位，YokiFrame 深度更够且不争夺玩法真相 |
| 开放世界模拟 | `FantasyWord` | `FantasyWord` | `FantasyWord` | 三方都不接管，项目侧后建 | 三方都不完整覆盖区域/Cell、队伍、派系、AI 日程、经济和局部模拟 |

对应到正式框架，就是：

- `2DRPGEngine` 管世界规则真相。
- `TopDownEngine` 管动作执行和表现样板。
- `YokiFrame` 管通用底层工具。
- `FantasyWord` 自己补开放世界模拟内核。

## 三方裁决主表

这张表只看“同一职责，三方谁更适合当正式来源”。它不引用“当前已经放在哪里”作为理由。

| 系统 | `2DRPGEngine` | `TopDownEngine` | `YokiFrame` | 裁决 |
| --- | --- | --- | --- | --- |
| 生命周期与系统宿主 | 优势是 `GameManager + AGameSystem` 能把地图、存档、数据库和 RPG 系统放在同一运行时根下 | 劣势是 `GameManager/LevelManager/InputManager/GUIManager` 多 manager 并存，容易形成第二生命周期 | `Architecture/EventKit/SingletonKit` 适合工具，不适合作为 RPG 正式宿主 | `2DRPGEngine` 胜出，正式宿主继续用 `GameCore GameManager + AGameSystem` |
| 地图、检查点、传送、场景恢复 | 优势是地图名、检查点栈、地图存档和玩家重生语义天然是一套真相 | 优势在关卡边界、默认出生点、检查点顺序、重生延迟和相机接线；劣势是 `LevelManager` 绑了输入、GUI 和场景生命周期 | 不提供同等级的地图/传送/检查点闭包 | `2DRPGEngine` 保地图真相，吸收 `TopDownEngine` 的关卡表现样板 |
| 玩家数据、成长、装备位、技能槽 | 优势是角色数据天然和任务、背包、装备、存档闭合 | 劣势是动作角色组件里不该再存一套玩家长期数据真相 | 不竞争这一层 | `2DRPGEngine` 直接胜出，动作层不得另存玩家真相 |
| 移动、动作能力、武器执行、命中与受击 | 规则语义能接 RPG `Ability/Effect/Stats`，但移动、武器状态机和受击表现偏薄 | 优势是 `CharacterAbility/CharacterMovement/Weapon/DamageOnTouch/Health/MMFeedbacks` 这一整段动作生态更成熟 | 不竞争动作执行层 | `TopDownEngine` 胜出，按正式吸收进入 `GameCore`，不引入它的 manager/输入/UI |
| 物品、背包、装备、制作、任务、对话 | 优势是和数据库、存档、菜单、命令、条件闭合 | TopDown 更适合作拾取和掉落样板，不适合作 RPG 背包/任务真相 | 不竞争这一层 | `2DRPGEngine` 胜出，TopDown 只供拾取/掉落/机关样板 |
| 存档 | 优势是 `SaveDataBlock` 聚合的是 RPG 世界状态，而不是单纯文件 | 不提供同等级的 RPG 存档语义 | 优势是 `SaveKit` 的文件槽位、版本、删除、迁移和承载工具更强 | 正式融合：`2DRPGEngine` 保语义，`YokiFrame` 保文件层 |
| 输入 | 优势是 Unity Input System 语义、地图锁输入和玩家控制入口清楚 | 优势是动作/移动端样板多；劣势是 `InputManager` 会引入第二输入根 | 优势是运行时重绑定、绑定保存和冲突查询 | 正式融合：`2DRPGEngine` 保输入真相，`YokiFrame` 补重绑定；TopDown 只供手感样板 |
| UI / HUD | 优势是 RPG 菜单和背包/任务/对话语义闭合 | 优势是动作 HUD、血条、移动端显示样板开箱快 | 优势是 `UIKit` 的缓存、层级、预加载和原生面板栈工具深度高 | 当前正式裁决是“GameCore 菜单语义 + Yoki `UIKit` 宿主”融合：菜单语义仍归项目侧，正式宿主已切到 `UIManager + UIKitMenuPanelBase + UIKit`；TopDown 只供 HUD 样板 |
| 对象池、资源句柄、输入重绑定、UI 缓存等通用工具 | 工具层深度一般，很多实现偏轻 | 动作样板内有工具，但目标是服务 MoreMountains 生态，不是做项目通用底层 | 优势是对象池、文件层、输入重绑定、资源/文本/UI 工具都更成体系 | `YokiFrame` 胜出，工具位直接替换项目侧重复浅实现 |
| 开放世界模拟 | 没有完整覆盖区域/Cell、队伍、派系、AI 日程和局部模拟 | 有战斗 AI 和关卡样板，但没有长期世界模拟真相 | 没有这层世界规则能力 | 三方都不胜出，由 `FantasyWord` 自建正式世界模拟层 |

## 为什么不是“某一边整体接管”

| 候选 | 不能整体接管的根本原因 |
| --- | --- |
| `2DRPGEngine` 整体接管 | 它在 RPG 世界规则层很强，但动作能力、武器状态机、受击反馈和 Inspector 调手感明显不如 `TopDownEngine`，整体照搬会把动作层短板一起保留 |
| `TopDownEngine` 整体接管 | 它在动作生态上很强，但 `LevelManager/InputManager/GUIManager/GameManager` 会把生命周期、输入、UI 和场景流程整套带进来，直接制造第二真相 |
| `YokiFrame` 整体接管 | 它强在通用工具，不表达 RPG 世界状态、任务、地图、背包、角色成长或开放世界模拟；拿工具框架当玩法框架会让“世界是什么”这件事失焦 |

## 为什么 `TopDownEngine` 不能只当“参考”

把 `TopDownEngine` 降成“只参考、不参赛”，等于默认认同：

- 世界规则层的胜者，可以顺便继续占有动作表现层。

这正是本轮要推翻的错误前提。

`TopDownEngine` 必须参加正式裁决，因为它在动作表现层不是“略有帮助”，而是明确胜出：

- `设计模式`：角色能力、武器、命中、受击、反馈的组件拆分更像正式动作执行模型。
- `软件工程`：状态机、命中窗口、动作阻断和反馈触发点边界更清楚。
- `易用`：Inspector 和 Prefab 样板能更快把动作手感调到可玩。

因此它的正确身份不是“灵感来源”，而是：

- 动作表现层正式胜者
- 但不是世界规则层胜者
- 更不是生命周期、输入、UI 的总接管者

## 关键裁定条文

下面这几条是本轮最重要的正式裁定，不需要再从长表里自行归纳。

### 裁定一：`2DRPGEngine` 不是总框架

- 它赢的是 `长期世界状态`，不是全部系统。
- 它在地图、任务、背包、角色数据、存档这些系统上最适合充当正式真相源。
- 它一旦越界去接管动作表现层，就会把本来应当替换的薄执行一起保留下来。

所以正式结论不是“继续用 `2DRPGEngine` 做总框架”，而是：

- `2DRPGEngine` 只负责世界规则真相。

### 裁定二：`TopDownEngine` 必须进入正式框架

- 它不是挂名参考，也不是灵感来源。
- 它在移动、能力、武器、命中、受击、反馈这一整段上，是动作表现层的正式胜者。
- 如果不让它参加正式裁决，就等于默认接受“世界规则层胜者可以顺便占有动作表现层”这个错误前提。

所以正式结论不是“参考一下 `TopDownEngine`”，而是：

- `TopDownEngine` 必须参与正式胜负。
- 它胜出的动作层必须进入正式实现。

### 裁定三：`TopDownEngine` 只能赢动作层，不能顺带赢生命周期

- 它一旦整体接管，就会把 `GameManager/LevelManager/InputManager/GUIManager` 一起带进来。
- 这不是“更多现成能力”，而是第二生命周期、第二输入根、第二 UI 根。
- 这会直接破坏本项目要的单一真相源。

所以正式结论不是“既然动作层赢了，就顺便全接进来”，而是：

- 只吸收 `TopDownEngine` 胜出的动作模式。
- 明确拒绝它的 manager、输入、GUI、Level 生命周期升格。

### 裁定四：`YokiFrame` 不是玩法框架，但它也不是可选项

- 它不表达世界规则，也不表达动作表现。
- 但在对象池、文件层、重绑定、缓存这类通用工具问题上，它是明确胜者。
- 如果继续保留项目侧重复浅工具，只会增加维护负担，不会增加架构正确性。

所以正式结论不是“有空再接 `YokiFrame`”，而是：

- 工具层该替换的就直接替换。

### 裁定五：正确框架只能是四层分治

- 世界规则真相归 `2DRPGEngine`
- 动作表现真相归 `TopDownEngine`
- 通用工具真相归 `YokiFrame`
- 开放世界模拟真相归 `FantasyWord`

这不是折中方案，而是唯一不自相矛盾的方案。

## 源码证据摘要

| 来源 | 证据 | 对裁决的影响 |
| --- | --- | --- |
| `2DRPGEngine` `SaveSystem` | `SaveDataBlock` 直接聚合地图、任务、背包、游戏标记、玩家和持久化对象，并由 `LoadDataBlock/CreateDataBlock` 统一读写 | 它表达的是 RPG 世界状态，不只是文件读写；适合作为存档语义真相源 |
| `2DRPGEngine` `InventorySystem` | 背包数量、金钱、装备/卸装、数据库引用和通知在同一系统内闭合 | 物品、背包、装备语义比 TopDown InventoryEngine 更贴近 RPG 数据流 |
| `2DRPGEngine` `PlayerController` | 输入、交互、技能释放和菜单打开直接绑定 RPG 角色、技能槽和交互对象 | RPG 语义清楚，但移动和战斗手感偏薄，适合保留语义、替换动作实现 |
| `2DRPGEngine` `MeleeAttackAbility` | 依赖动画事件、碰撞盒和效果列表，规则能接进 RPG `Effect/Ability` | 规则数据可保留，但武器生命周期、连击、后摇、反馈不如 TopDown 成熟 |
| `TopDownEngine` `CharacterAbility` | 所有角色能力通过组件组合，统一有权限、阻断状态、动画、反馈和输入处理钩子 | 角色能力设计模式明显优于 2DRPG 的控制器集中式写法 |
| `TopDownEngine` `CharacterMovement/TopDownController2D` | 移动方向、加减速、摩擦、洞/地面检测、移动平台、碰撞和 Rigidbody2D 移动分层明确 | 俯视角移动和手感实现应以 TopDown 为主参考 |
| `TopDownEngine` `Weapon/DamageOnTouch/Health` | 武器状态机、弹药/换弹、攻击间隔、击退、无敌帧、伤害区域和反馈配置完整 | 武器和受击表现应吸收 TopDown；但生命值本身需接回 RPG stats |
| `TopDownEngine` `LevelManager/InputManager/GUIManager` | 依赖 MoreMountains 单例、事件、旧输入轴/移动端 UI、加载管理和整套场景假设 | 易用但侵入大；不能整体替换 `GameCore` 生命周期、输入和 UI |
| `YokiFrame` `GameObjectPoolService` | 支持 prefab/path 出租、预热、最大容量、诊断、资源句柄释放和场景卸载释放 | 对象池比 `2DRPGEngine InstancePool` 深，正式替换项目侧重复池 |
| `YokiFrame` `SaveKit` | 提供序列化器、加密器、版本迁移、槽位、路径和异步文件能力 | 应作为存档底层工具，不替换 RPG 存档语义 |
| `YokiFrame` `InputKit` | 提供运行时重绑定、冲突检测、绑定保存等工具 | 应补强当前 Input System 入口，不替换玩家输入语义 |
| `YokiFrame` `UIKit` | 提供面板缓存、预加载、层级、面板操作和调试工具 | 已成为正式 UI 宿主机制；项目侧只保留承接菜单语义的唯一 seam，不再保留旧 `AUIMenu/UIMenuManager` 双栈 |

## 总体框架裁决

正确框架不是三套都包一层。按职责类型复核后，地基应明确分成四层：前三层来自三方取舍，第四层是三方都没有完整覆盖的开放世界模拟层。

| 层 | 正式方向 | 理由 |
| --- | --- | --- |
| RPG 世界规则层 | `GameCore` 以 `2DRPGEngine` 的数据/存档/地图/背包/任务/对话为主 | 设计模式上，它把“世界是什么”建成数据和系统闭包；软件工程上，存档、数据库引用、任务/背包/地图状态能共用一个可审计真相；易用上，ScriptableObject 数据资产比动作样板更适合 RPG 内容生产 |
| 俯视角动作表现层 | 用 `TopDownEngine` 的角色能力、移动、武器、受击、反馈、相机和关卡样板替换或补强薄实现 | 设计模式上，它以角色能力、武器状态机、伤害区域和反馈组件组合行为；软件工程上，动作状态、阻断、输入释放、命中窗口和反馈配置各有边界；易用上，Inspector 参数与 Prefab 样板能更快调出手感 |
| 通用工具层 | 用 `YokiFrame` 替换重复工具：对象池、资源句柄、存档文件底层、输入重绑定、UI 缓存、日志诊断 | 设计模式上，它提供可复用工具而不表达玩法规则；软件工程上，统一池、槽位、重绑定和生成入口减少项目侧重复实现；易用上，开发者能直接拿工具接业务，不必维护浅包装 |
| 开放世界模拟层 | 由 FantasyWord 在具体能力进入正式范围时逐项建立自己的世界运行时内核；参考 Skyrim 的 Cell/Worldspace、Quest Alias/Radiant Story、AI Package 思路，以及 Kenshi 的队伍、派系、基地和局部模拟 | 2DRPG/TopDown/Yoki 都不能完整承担 Skyrim/Kenshi 类长期世界模拟；继续把这层塞进 `GameManager.*` 会制造后期重构 |

因此最终目录分工应是：

| 目录 | 职责 |
| --- | --- |
| `Assets/Scripts/GameCore` | FantasyWord 正式运行时代码。这里可以吸收 TopDown 的模式和改造后的实现，但命名和外部入口必须服务本项目 |
| `Assets/Editor/GameCore` | 只服务 GameCore 的编辑器工具、验证器、PropertyDrawer、AIBridge 编辑器恢复入口 |
| `Assets/Plugins/TopDownEngine` | 保留第三方源码和样板，作为动作/表现参考源；正式玩法不能散落直调它的 manager |
| `Assets/Plugins/YokiFrame` | 保留工具插件；项目侧重复工具应迁到这里或直接调用这里的稳定工具入口 |
| `Assets/Scripts/World` | 只在具体能力进入正式范围时承载世界运行时内核、区域/Cell、派系、队伍、AI 调度、经济/生产和局部模拟；不得为空目录堆架构 |

这里再补一层，避免把“参考源”和“已导入候选子集”混成一个概念：

- `ReferenceSources/TopDownEngine`：原始参考镜像，用来做源码对照、裁决取证和“为什么 TopDown 在动作层更强”的证据源。
- `Assets/Plugins/TopDownEngine`：已经导入工程、可参与编译与局部吸收的候选子集，用来承接当前正式动作层融合。
- 这两层并存不代表允许再造兼容层；它们只是“取证源”和“导入源”的分工。

### 目录边界裁决

`Editor` 和 `GameCore` 的放法是刻意裁决，不是碰巧长成这样。正式边界是：

- 运行时代码放 `Assets/Scripts/GameCore/Runtime`
- 项目侧编辑器工具放 `Assets/Editor/GameCore`
- 第三方源码继续留在 `Assets/Plugins/*`

这样放的理由仍然只按三项判断：

| 目录决策 | 设计模式理由 | 软件工程理由 | 易用理由 | 不选什么 |
| --- | --- | --- | --- | --- |
| `GameCore` 继续作为当前运行时总根，而不是立刻拆散到 `Characters/World/Items/Combat/Presentation` 多个顶层目录 | `GameCore` 现在承担的是“RPG 世界规则层 + 吸收后的动作/工具正式入口”这一整段连续职责；在世界层、角色层、表现层还没各自形成独立真相源前，先拆顶层目录只会制造名字上分层、运行时上仍耦合的伪模块 | 先把序列化、Prefab 接线、场景宿主、系统入口和审计面集中在一个稳定根上，能减少迁移期的状态分叉、漏改和错误归因；过早拆散会同时扩大引用闭包和回归面 | 开发者当前只需要记住“地基 runtime 看 `GameCore/Runtime`”，不必先猜哪些目录已经是正式真相、哪些还只是未来产品分层草案 | 不选“为了看起来像最终游戏结构，先把所有代码拆到多个顶层目录” |
| 编辑器工具放 `Assets/Editor/GameCore`，而不是混进 `Assets/Scripts/GameCore/Runtime` 或业务目录里 | 编辑器代码本质上是对运行时资产、检查器和验证入口的支撑，不是玩法模块本身；把它单独放在 `Editor` 下，职责最清楚 | 直接利用 Unity 的 Editor 专用编译边界，能天然阻断编辑器代码误进运行时程序集、玩家构建和序列化引用闭包；参考 `2DRPGEngine Core/Editor/Scripts` 只是佐证，不是根本理由 | 对 Unity 使用者来说，找 PropertyDrawer、EditorWindow、验证器时先看 `Assets/Editor/GameCore` 最直观 | 不选“运行时和编辑器脚本按功能混放，只靠 asmdef 或命名区分” |
| `TopDownEngine` 和 `YokiFrame` 保留在 `Assets/Plugins/*`，不并入项目侧 `GameCore` | 第三方框架应保持来源边界，项目只吸收胜出的模式和最小正式入口，不把整个插件伪装成项目自有代码 | 保留原来源结构更利于升级、对照、门禁和问题归因；也能防止 AI 或人把第三方 manager 当成项目正式入口继续扩写 | 查问题时能直接分清“项目真相在哪”“第三方原件在哪”“哪些是项目吸收后的正式实现” | 不选“为了整齐，把第三方源码剪碎并回项目目录” |

因此，当前目录裁决不是“先这样凑合，等以后再说”，而是：

- `GameCore/Runtime` 代表当前仍需保持单一真相、集中宿主和连续职责的正式地基闭包。
- `Editor/GameCore` 代表只服务这套地基、并受 Unity 编辑器编译边界保护的项目侧支撑。
- `World/Characters/Items/Combat/Presentation` 这些顶层目录只应在对应系统真正变成 FantasyWord 自己的独立真相源后再晋升，不得为了看起来整齐提前拆家。

执行证明（不参与裁决）：

- `scripts/Sync-2DRPGFoundation.ps1`、parity 门禁和 patched 台账当前都围绕 `GameCore` 工作，这证明“目录裁决”和“现态执行”一致。
- 这些脚本和门禁是执行证据，不是把 `GameCore` 留在当前位置的根本理由；根本理由仍然是上表里的三项判断。

## 正确框架蓝图

以下是裁决后的正式框架，不以现有落点作为理由：

| 职责 | 真相源 | 吸收来源 | 判断理由 |
| --- | --- | --- | --- |
| 游戏生命周期、系统发现、数据库注册 | `GameCore GameManager + AGameSystem + GameConfig` | 只吸收 Unity/插件必要工具 | 设计模式上是单一运行时根；软件工程上避免多 manager 互相抢生命周期；易用上场景只需挂一个明确根节点 |
| 世界地图、检查点、传送、存档地图状态 | `GameCore MapSystem + MapInfo + ICheckpoint` | 吸收 TopDown `LevelManager/CheckPoint` 的边界、默认出生点、重生延迟、相机接线样板 | 地图名、检查点栈、存档地图状态必须一个真相；TopDown 强在场景可配置体验，但它的 LevelManager 同时绑定输入、GUI、场景加载和生命循环，不能整体接管 |
| 玩家数据、等级、生命数值、装备、技能槽 | `Hero/CharacterBase/CharacterSheet/Stats` | 吸收 TopDown 受击、无敌帧、击退、反馈参数 | RPG 数据必须可保存、可被任务/背包/装备共享；TopDown 的 `Health` 适合作为受击表现样板，不适合另存玩家数值真相 |
| 玩家动作、移动、武器输入、命中窗口 | `GameCore` 正式角色闭包内的控制器与能力执行 | TopDown `CharacterAbility/CharacterMovement/TopDownController2D/Weapon/DamageOnTouch` | 行为用组合组件和状态机表达更清楚；但输入、数据、存档不能被 TopDown manager 接走，所以吸收到正式闭包而不是挂第二套角色体系 |
| 物品、背包、装备、制作、任务、对话 | 2DRPG RPG 系统 | TopDown 只提供拾取、掉落、机关交互样板 | 这些是世界规则和内容生产系统，设计上依赖数据库引用与存档；软件工程上不能和动作游戏 InventoryEngine 重复状态 |
| 文件存储、对象池、输入重绑定、资源/文本强类型、UI 缓存工具 | YokiFrame | 不承载玩法真相 | 工具层只解决“怎么存、怎么复用、怎么绑定、怎么生成入口”，不回答“世界状态是什么” |

## 模块裁决表

| 系统 | 设计模式判断 | 软件工程判断 | 易用判断 | 裁决 |
| --- | --- | --- | --- | --- |
| 启动和系统生命周期 | `2DRPGEngine GameManager + AGameSystem` 比 TopDown 多 manager 单例更集中；YokiFrame Architecture 会引入新范式 | 保持一个系统宿主能减少第二套状态；TopDown `GameManager/LevelManager/InputManager/GUIManager` 会打穿生命周期 | TopDown 更开箱，但代价是整套运行时假设 | 保留 `GameCore GameManager + AGameSystem`；不得整体接入 TopDown manager |
| 地图、传送、检查点 | `2DRPGEngine MapSystem` 表达地图名、检查点栈、传送和地图存档；TopDown `LevelManager/CheckPoint` 表达默认出生点、关卡边界、检查点顺序和重生表现 | 世界地图和存档应统一由 `MapSystem` 负责；TopDown `LevelManager` 同时绑定 MoreMountains 单例、场景加载、GUI、相机和生命事件，整体引入会制造第二套场景生命周期 | TopDown 的场景接线更直观，特别是边界、出生点、重生延迟和相机目标 | 融合：`MapSystem` 保留地图/存档真相，吸收 TopDown 的边界、默认出生点、检查点顺序、重生延迟和相机接线样板；不挂 TopDown `LevelManager` |
| 世界穿越目标 | 当前 `MapSystem` 仍只对玩家存档 Hero 的传送与复活建模；控制对象接口是另一条正在推进的线 | 先把“谁被传送/复活”集中到一个正式入口，比提前把触发器改到 `currentControlledCharacter` 更重要；否则会出现“当前控制角色触发传送，但真正被传送的是另一人”的双重真相 | 对场景作者来说，当前仍是单一明确目标，直到控制组与世界实体规则落地 | 当前保留玩家存档 Hero 作为世界穿越真相；等控制组/多 Hero 世界穿越语义正式定稿后，再决定是否切到当前控制对象 |
| 玩家身份、角色数据、成长 | `2DRPGEngine Hero/CharacterBase/CharacterSheet` 更贴 RPG 数据、装备、技能槽、存档 | 玩家存档、等级、装备和任务引用必须集中在 RPG 数据层 | 2DRPG 数据资产更适合 RPG 内容制作 | 保留 2DRPG 语义；动作组件不得成为玩家数据真相 |
| 角色移动和控制器 | TopDown `CharacterAbility + CharacterMovement + TopDownController2D` 是组合式能力；2DRPG `PlayerController/Movable` 把 RPG 输入、交互、技能和实体移动集中在少数类里 | TopDown 在移动、碰撞、摩擦、方向限制、能力阻断上更成熟；2DRPG 在玩家身份、技能槽、交互对象和存档语义上更贴 RPG。直接替换成 TopDown 角色会把输入、生命、UI、manager 和玩家数据一起带入第二真相 | TopDown Inspector 配置更适合调手感；2DRPG 控制器更容易接 RPG 任务/交互 | 融合：玩家数据和输入语义归 2DRPG；移动执行、能力阻断和碰撞手感按 TopDown 模式吸收进正式闭包；不新增并行控制器 |
| 输入 | 2DRPG `InputSystem` 使用 Unity Input System 并接入地图锁定；TopDown `InputManager` 是 MoreMountains 单例和旧轴/移动端模式 | 第二个 InputManager 会制造状态重复；YokiFrame InputKit 可补重绑定 | TopDown 对移动端开箱强，YokiFrame 对重绑定强 | 保留 `GameCore InputSystem`；融合 YokiFrame 重绑定/保存；只吸收 TopDown 输入手感参数，不接管入口 |
| 战斗规则、技能、状态效果 | 2DRPG `Ability/Effect/Stats` 与数据库和存档闭合；TopDown 武器/伤害表现强；EX-GAS 可作为更强规则候选 | 规则真相不能同时在 Ability、TopDown Health、EX-GAS 里重复 | TopDown 武器最易调，EX-GAS 可视化/扩展待评估 | 分层融合：RPG 效果/属性暂归 2DRPG；武器执行、命中、后摇、反馈吸收 TopDown；EX-GAS 需专项矩阵决定是否替换规则层 |
| 武器和攻击手感 | TopDown `Weapon/ProjectileWeapon/MeleeWeapon/CharacterHandleWeapon` 状态机完整；2DRPG 攻击较薄 | TopDown 的武器状态机能减少自造攻击流程；但伤害结果要回写 RPG 效果系统 | TopDown 的 Prefab/Inspector 最容易做武器 | 替换薄实现：攻击执行层向 TopDown 武器模型迁移，伤害结算接回 RPG stats/effects |
| 生命、受击、无敌帧、击退 | TopDown `Health/DamageOnTouch` 配置面广；2DRPG `CharacterBase` 更贴 RPG 属性 | 生命值真相应在 RPG stats；受击表现和无敌帧可独立 | TopDown 更容易调受击反馈 | 融合：RPG stats 做数值真相，TopDown 受击/反馈模式改造成表现和碰撞执行层 |
| 物品、背包、装备、制作 | 2DRPG `InventorySystem/Item/Equipment/Recipe` 与数据库、UI、存档闭合；TopDown InventoryEngine 更偏动作游戏拾取和槽位 | RPG 背包真相不能切到 TopDown InventoryEngine，否则任务、存档、装备数据会重复 | 2DRPG 对 RPG 内容更直接，TopDown 对拾取样板更直观 | 保留 2DRPG；吸收 TopDown 拾取交互和掉落表现，不替换背包系统 |
| 背包真相与当前操作目标 | 全局背包/货币与“当前要把物品用在谁身上、给谁穿装备”不是同一层语义 | 若直接把 Inventory 整体改成多 Hero 私有，会同时牵动存档、商店、任务、掉落和制作；但若继续把装备/消耗品操作硬绑唯一主角，又会妨碍控制对象扩展 | 对玩家和策划来说，“背包还是这一份，但现在给当前角色穿/吃/看属性”比“立刻拆多套背包”更可用 | 融合：`InventorySystem.items/money` 继续是全局真相；物品使用目标和属性栏显示跟随当前控制角色，装备执行目标再通过 `CharacterEquipment` 正式解析 |
| 任务、对话、命令、条件 | 2DRPG 有 `JournalSystem/DialogueSystem/ICommand/ICondition` 闭环；TopDown 不提供同等 RPG 语义 | 这些系统是剧情和任务真相，必须可保存、可审计 | 2DRPG 更贴 RPG 制作 | 保留 2DRPG；不从 TopDown 替换 |
| 存档语义 | 2DRPG `SaveSystem` 聚合地图、任务、背包、玩家、持久化对象 | RPG 语义强，但文件层薄；YokiFrame SaveKit 文件、版本、加密、槽位更强 | YokiFrame 槽位和迁移更好用 | 融合：`SaveSystem` 保留语义，底层文件槽位/版本迁移改用 YokiFrame SaveKit |
| 对象池 | YokiFrame `GameObjectPoolService` 是深工具；2DRPG `InstancePool` 是浅数组池；TopDown 池只服务 MoreMountains 内部 | 单一池可集中诊断和容量管理 | YokiFrame API 更统一 | 替换：项目侧 `InstancePool/FloatingTextPool` 逐步退场；TopDown 内部池不外扩 |
| UI 菜单语义 | 2DRPG UI 与背包、任务、对话、存档闭合；YokiFrame UIKit 是 `UIPanel` 面板工具；TopDown GUIManager 偏动作 HUD | RPG 菜单真相保留在 GameCore，但正式宿主已经切到 `UIKit` 原生模型；不能保留两套栈 | YokiFrame 缓存和预加载更好，且当前迁移已经落到正式运行时代码 | 当前正式融合已经完成宿主替换：`UIManager + UIKitMenuPanelBase + UIKit` 承担正式菜单宿主，TopDown 只参考 HUD/血条/移动端显示 |
| 资源和场景加载工具 | 2DRPG MapSystem 表达地图语义；YokiFrame ResKit/SceneKit 表达加载工具；TopDown 场景加载绑定 MoreMountains 流程 | 地图语义和加载工具应分离 | YokiFrame 资源句柄更易维护 | 融合：MapSystem 调 YokiFrame 工具，不让 YokiFrame 成为世界地图真相 |
| 音频 | 2DRPG 命令/通知触发音频；BroAudio 是正式音频包；TopDown SoundManager/MMFeedbacks 表现样板强 | 音频入口应统一，表现反馈可吸收 | TopDown Feedbacks 易做手感，BroAudio 更适合正式后端 | 融合：GameCore 正式音频闭包 + BroAudio 后端；TopDown 反馈结构只吸收模式 |
| 编辑器工具 | 2DRPG Editor 工具服务数据库和场景；YokiFrame/TopDown 工具服务各自插件 | 第三方编辑器工具留在插件，项目数据工具留在 GameCore | 各自保留最清楚 | 保持当前目录，但项目工具要补中文说明和验证入口 |

| 生命值真相与受击表现 | `TopDownEngine` | `2DRPGEngine` | `TopDownEngine` | 正式融合：生命数值留 RPG，受击/击退/无敌帧/反馈吸收 `TopDown` | `CharacterBase/Stats + GameplayFeedbackSet + EffectImpactSettings` |
| 背包、装备、制作、任务、对话 | `2DRPGEngine` | `2DRPGEngine` | `2DRPGEngine` | 直接保留 `2DRPG`，只吸收 TopDown 拾取/掉落/机关样板 | `InventorySystem / JournalSystem / DialogueSystem / Item/Equipment` |
| 存档语义与文件承载 | `2DRPGEngine` | `2DRPGEngine` | `YokiFrame` | 正式融合：世界状态聚合留 `2DRPG`，文件槽位/版本/删除换 `SaveKit` | `SaveSystem + SaveKit` |
| 输入入口、重绑定、未来控制组 | `2DRPGEngine` | `2DRPGEngine` | `YokiFrame` | 正式融合：输入入口留 `GameCore InputSystem`，绑定工具用 `InputKit` | `InputSystem + PlayerSystem + IPlayerInputTarget` |
| UI 菜单语义、缓存、层级 | `2DRPGEngine` | `2DRPGEngine` | `YokiFrame` | 正式融合已落地：菜单语义留 GameCore，宿主/缓存/层级改走 `UIKit`，不再保留旧双栈 | `UIManager + UIKitMenuPanelBase + UIKit` |
| 对象池、资源句柄、日志诊断 | `YokiFrame` | `YokiFrame` | `YokiFrame` | 直接替换项目侧重复工具实现 | `GameObjectPoolService / SaveKit / InputKit / SceneKit/...` |
| 编辑器工具与验证入口 | `2DRPGEngine` | `2DRPGEngine` | 各自保留 | 暂不混合；项目工具留 `GameCore`，插件工具留插件目录 | `Assets/Editor/GameCore` + `Assets/Plugins/*` |
| 开放世界模拟层 | `FantasyWord` | `FantasyWord` | `FantasyWord` | 三方都不接管；只在具体能力进入正式范围时逐项建立项目自有模块 | 优先落到项目侧正式世界入口，按能力逐个建立 |

## Skyrim/Kenshi 目标架构复核

本项目现在的目标不是“2D RPG 样板”或“TopDown 动作样板”，而是接近《上古卷轴5》和《Kenshi》的开放世界沙盒。公开资料能提炼出几个硬需求：

| 参考 | 对地基的要求 | 当前三方覆盖情况 |
| --- | --- | --- |
| Skyrim Creation Kit 的 Worldspace/Cell 思路 | 世界不是单场景；需要区域、Cell、加载状态、区域内对象和持久化状态的明确模型 | 2DRPG `MapSystem` 只有地图/检查点/场景加载语义；还不是 Cell/区域流送系统 |
| Skyrim 的 Quest Alias / Radiant Story 思路 | 任务不只引用固定对象，还要能在运行时绑定角色、地点和物品；世界事件可以驱动任务 | 2DRPG 任务/条件/命令可作为基础，但缺动态别名、任务候选、世界事件选择层 |
| Skyrim 的 AI Package 思路 | NPC 行为应由日程、条件、地点、目标和优先级驱动，不应写死在单个触发器 | TopDown 有角色 AI 行为样板，2DRPG 有 NPC/交互，但缺长期日程和包式调度 |
| Kenshi 的队伍沙盒 | 玩家可能控制多个角色，角色可受伤、被俘、分工、远离玩家继续存在 | 当前 `GameManager.Player` 是单英雄快捷入口；它不适合直接扩成队伍真相 |
| Kenshi 的派系、基地、经济和局部模拟 | 世界需要派系关系、城镇/基地生产、商店/资源、区域内外模拟降级 | 2DRPG 背包/商店/制作是 RPG 菜单级闭包，还不是经济与生产模拟 |

结论必须降级得更准确：当前 `GameCore` 是可继续施工的 RPG 基线，不是已经足够支撑 Skyrim/Kenshi 的完整开放世界地基。它缺的不是一个控制器，而是开放世界模拟层。

### 立即替换的架构假设

| 旧假设 | 新裁决 | 理由 |
| --- | --- | --- |
| `GameManager + AGameSystem` 可以继续作为所有系统的公开入口 | 保留 `GameManager` 作为启动宿主，但停止把新的开放世界系统继续暴露成 `GameManager.*` 静态快捷入口 | 静态全局快捷入口会把系统定位、调用和保存语义混在同一层，天然不利于局部模拟、测试替身、多角色控制和未来联机控制权切分 |
| `Player` 等于唯一世界主角 | 玩家输入的当前控制对象和世界里的角色实体必须分开；后续队伍/随从/基地成员不能绑死到 `GameManager.Player` | Kenshi 类目标要求多角色、分队和脱离镜头的角色状态 |
| `MapSystem` 等于开放世界地图系统 | `MapSystem` 只保留当前地图/检查点/场景加载语义；开放世界需要新的区域/Cell/流送/模拟层 | Skyrim/Kenshi 都要求地图外的世界状态继续存在或可降级模拟 |
| `NotificationSystem` 可以继续当全局事件中心 | 新增世界事件必须先有明确拥有者和保存语义；不能把世界模拟事件全部倒进通知系统 | 大通知中心是浅 Module，Interface 接近所有调用者的总和，缺少 Locality |

### 新增世界运行时内核候选

开放世界模拟层不能先创建空目录或空类。只有进入具体能力时，才按下表逐个落地深 Module：

| 候选 Module | Interface 应该隐藏的复杂度 | 第一验收场景 |
| --- | --- | --- |
| 世界区域/Cell 注册表 | 区域 ID、加载状态、对象归属、区域内外模拟等级、保存快照 | 从一个测试地图切到另一个地图，离开区域的对象状态仍能保存和恢复 |
| 角色实体注册表 | 玩家、队友、NPC、临时召唤物、死亡/失踪/被俘等身份状态 | 不通过 `GameManager.Player` 也能找到当前可控制角色和队伍成员 |
| 队伍与控制权 | 当前选中角色、编队、命令队列、跟随/待机/工作状态 | WASD/点击移动只作用于当前控制组，而不是硬绑单个 Hero |
| AI 日程/行为包 | 条件、目标、地点、优先级、行为图/状态机引用、暂停和保存 | NPC 能在没有对话触发器时按日程巡逻、工作、休息 |
| 派系关系 | 阵营、敌友、通行权、犯罪/声望、区域归属 | 同一伤害/偷窃/入侵事件能影响派系关系和 NPC 态度 |
| 经济与基地生产 | 资源输入输出、库存、工作岗位、生产 tick、离线/区域外简化 | 基地工作站在玩家离开区域后仍能按简化规则推进 |
| 世界事件与任务绑定 | 事件源、候选地点/角色/物品、任务别名绑定、失败/替代路径 | 任务可以绑定“附近一个可用 NPC/地点”，而不是写死对象引用 |
| 导航提供者 | 地图格、阻挡、代价、区域内路径、跨区域入口 | 点击移动、NPC 日程和队伍命令共用同一个路径能力 |

### 新增来源

| 参考 | 使用方式 | 当前裁决 |
| --- | --- | --- |
| Unity Behavior | 作为单个 NPC/对象行为图来源，适合把行为树/状态机做成可视化资产；不负责世界级调度和存档真相 | 可评估，但不安装、不接管 GameCore |
| A* Pathfinding Project 或 Unity 2D/Tilemap 导航方案 | 作为 2D 点击移动、NPC 路径、区域内寻路来源 | P0 来源；做点击移动前应先定导航 Provider，避免控制器自带一套寻路 |
| GOAP / Utility AI | 作为 NPC 目标选择、工作分配、队伍命令来源 | P1 来源；先从简单 AI Package/日程开始，别过早上复杂规划器 |
| DOTS/Entities | 作为大量区域外模拟、生产 tick、群体 NPC 的性能来源 | 只在 MonoBehaviour/普通数据模型证明不够时再评估；当前不作为起步地基 |

## 开放世界架构复核：TopDown 更好的部分与当前地基风险

选择 `2DRPGEngine GameManager + AGameSystem` 做 RPG 地基的理由不是“它已经在项目里”，而是它把 RPG 世界状态、存档、地图、背包、任务和玩家数据集中到可保存真相源。这个选择仍有架构风险：`GameManager` 静态快捷入口如果无约束扩张，会让开放世界后期的区域流送、多人控制权、测试替身和局部模拟变难。因此后续只能把它作为世界规则宿主，而不能把所有动作表现和工具能力继续塞进总入口。

TopDown 不应整体替换 `GameCore GameManager`，因为 TopDown 自己也有 `GameManager / LevelManager / InputManager / GUIManager` 等单例和场景假设；整体搬运会把第二套暂停、输入、UI、场景加载、玩家出生和生命真相一起带进来。但 TopDown 在下列设计上明显更适合复杂动作游戏，应该作为后续融合或替换候选：

| 方向 | TopDown 更好的点 | 当前 GameCore 风险 | 推荐动作 |
| --- | --- | --- | --- |
| 角色能力结构 | `Character` 缓存多个 `CharacterAbility`，并统一跑 `EarlyProcess / Process / LateProcess / UpdateAnimator`；新增移动、冲刺、武器、交互等**角色功能模块**不用继续膨胀单个控制器。这里说的是移动/武器/交互/库存这类模块，不是把每个 RPG 技能资产拆成一个 MonoBehaviour | 当前 `PlayerController/Movable/CharacterBase` 更集中，后续开放世界能力多了容易变成大类和大量条件分支 | P0 评估是否把“能力组件调度”正式吸收到 `CharacterBase/Hero`，但玩家数据仍归 RPG 层 |
| 能力权限与阻断 | `CharacterAbility` 内置 movement/condition/weapon 阻断状态和 `AbilityPermitted` | 原先行动锁、技能释放、受击、死亡、交互等条件分散在多个方法里；当前已收口到 `AbilityPermissionSettings` | P0 已提炼正式 `Action/Ability Permission` 合同，后续具体能力继续扩展同一配置 |
| 动作表现与反馈 | Ability、Health、Weapon 都有反馈、音效、动画参数、死亡/受击回调 | 当前规则能保存，但表现配置较薄，容易把音效/特效散落到业务代码 | P1 吸收 TopDown Feedbacks 结构，但走 GameCore 音频/表现闭包 |
| 移动控制器 | `TopDownController2D` 把摩擦、外力、移动平台、洞/地面、障碍探测和速度计算分层 | 当前 `Movable` 已吸收输入手感，但碰撞/摩擦/地形执行仍薄 | P1 判断是否把 `Movable` 的移动执行替换成更接近 `TopDownController2D` 的内部结构 |
| 关卡边界与出生/重生 | `LevelManager` 的出生点、关卡边界、相机目标、重生流程易接线 | `MapSystem` 强在地图/存档语义，但不应自己发明表现配置合同；TopDown 样板可提供成熟接线方式 | P1 吸收出生点、边界、相机接线样板，不接管地图真相和场景加载主入口 |
| 输入模式和移动端 | TopDown `InputManager` 对移动端 UI、PlayerID、按键状态封装开箱更完整 | 当前 `InputSystem` 保留 Unity Input System 语义并接了重绑定，但点击移动/移动端模式尚未形成正式合同 | P1 只吸收输入模式和 UI 样板，不引入第二套 InputManager |

结论：需要准备“动作角色层”的融合或替换评估，而不是替换整个地基。若后续证明 TopDown 的 `Character + CharacterAbility + TopDownController2D` 闭包整体比当前 `CharacterBase + Movable + PlayerController` 更适合开放世界动作扩展，可以启动正式替换；但替换目标必须落回 GameCore 正式入口，且先解决玩家数据、存档、输入、生命、背包、UI 的真相归属，不能让 TopDown manager 和 GameCore manager 并存。

## TopDown 全系统横向复核

TopDown 更好不只发生在“控制器”。它在动作表现、反馈、AI 行为样板、交互区、拾取/掉落、出生/重生和移动端 HUD 上都有成熟样板；但这些样板多数绑定 MoreMountains 单例、事件、旧输入或 TopDown `Health/Character` 数据模型，不能整体替换 GameCore 的 RPG 世界真相源。

| TopDown 系统 | 源码证据 | 比当前 GameCore 更好的点 | 不整体搬的原因 | 当前裁决 |
| --- | --- | --- | --- | --- |
| 角色能力和动作权限 | `Character`、`CharacterAbility`、`CharacterMovement`、`CharacterHandleWeapon` | 能力组件组合、统一 tick、权限阻断、动画参数和反馈触点成熟；这里的组件是“角色功能模块组件”，不是 RPG 技能一技能一组件 | 直接搬会把 TopDown `Character`、输入、生命和 manager 一起带入第二套玩家真相 | P0 局部吸收；正式入口仍是 `CharacterBase/Movable/PlayerController` |
| 移动、碰撞和地形执行 | `TopDownController2D`、`SurfaceModifier`、`MovingPlatform2D` | Rigidbody2D 移动、摩擦、移动平台、地面/洞/障碍处理更完整 | 当前像素 RPG 还要保留 2DRPG 实体、存档、交互和属性速度修正 | P1 深化 `Movable` 内部执行；不新增并行控制器 |
| 武器、命中和受击表现 | `Weapon`、`ProjectileWeapon`、`MeleeWeapon`、`DamageOnTouch`、`Health` | 武器状态机、连发、弹匣、换弹、命中窗口、每目标冷却、击退、无敌和反馈闭环成熟 | TopDown `Health` 不能成为 RPG 生命值真相；伤害必须回写 GameCore stats/effects | 已吸收武器执行、近战命中窗口、击退/受击保护、命中反馈、受击反馈和死亡反馈；相机/屏幕反馈继续补 |
| 反馈系统 | `CharacterAbility`、`Weapon`、`DamageOnTouch`、`Health`、`Loot` 里的 `MMFeedbacks` | 反馈触发点覆盖能力、武器、命中、受击、死亡、掉落、拾取和交互，Inspector 配置效率高 | 不能让玩法代码散落直接依赖第三方字段；需要 GameCore 正式反馈闭包约束触发点 | 已通过 `GameplayFeedbackSet` 接入能力/武器生命周期、命中、受击、死亡、奖励掉落、拾取和交互反馈；相机/屏幕反馈继续补 |
| AI 行为样板 | `AIAction*`、`AIDecision*`、`CharacterPathfinder3D` | 巡逻、追击、逃离、瞄准、射击、换弹、视野检测等单体敌人行为样板丰富 | 这是战斗 AI/单体行为，不等于 Skyrim/Kenshi 的日程、派系、工作、区域外模拟 | P1 作为 NPC 战斗行为参考；开放世界 AI 日程只记录缺口 |
| 拾取和掉落 | `PickableItem`、`PickableWeapon`、`Loot` | 拾取触发、掉落表、死亡/受击掉落、避障生成、掉落反馈和调试按钮成熟 | TopDown InventoryEngine 与 GameCore 背包/任务/装备/存档语义冲突 | 局部吸收拾取/掉落表现合同；背包和物品真相仍归 2DRPG/GameCore |
| 交互区和机关 | `ButtonActivated`、`DialogueZone`、`MovementZone`、`ProximityMine`、`TimeZone` | 自动/按键激活、次数限制、冷却、视觉提示、进入/退出/拒绝反馈、UnityEvent 接线成熟 | 具体交互结果应走 GameCore `IInteraction/ICommand`，不能直接把场景事件当世界规则 | `MovementZone` 已吸收为速度区域合同；`ButtonActivated/DialogueZone/ProximityMine/TimeZone` 仍只记录样板 |
| 关卡出生、边界和重生 | `LevelManager`、`CheckPoint`、`Respawnable`、`AutoRespawn` | 出生点、检查点顺序、重生延迟、边界、相机目标和可重生对象接线成熟 | `LevelManager` 同时持有 TopDown 输入、GUI、场景加载、死亡循环和 GameManager 状态 | 只吸收到 `MapSystem/MapInfo` 场景表现配置；不接管场景生命周期 |
| 相机和屏幕表现 | `Camera` 目录、`MMCameraEvent`、反馈系统 | 目标切换、边界、震动、淡入淡出和事件接线完整 | 与 MoreMountains 事件和 LevelManager 绑定较深；正式相机要适配像素、URP 2D 和 GameCore 表现闭包 | P1/P2 参考事件和反馈触点；不整体接管 |
| GUI/HUD 和移动端控件 | `GUIManager`、`HealthBars`、`AmmoDisplays`、`Joystick/Buttons/Arrows` | 血条、弹药、暂停/死亡屏、移动端按钮和摇杆可快速接线 | `GUIManager` 是第二 UI 根，且绑定 TopDown InputManager、PlayerID、点数和死亡流程 | 只参考 HUD/移动端显示样板；正式 UI 仍归 GameCore/Yoki UIKit 迁移路线 |
| 音频 | `SoundManager`、`MMFeedbacks` 声音反馈 | TopDown 事件驱动音频和反馈音效配置方便 | 正式音频后端已是 BroAudio/GameCore 音频闭包 | 只吸收反馈触发点；不接管 SoundManager |
| 成就和分数 | `AchievementRules`、TopDown points events | 动作游戏分数/成就规则开箱 | 不符合当前开放世界 RPG 核心，且与任务/存档/统计真相未对齐 | 仅观察，不进入当前地基 |
| Procedural/Rooms/Demo 样板 | `Procedural`、`Demos/Koala2D` | 可提供地牢、房间、Tilemap 接线参考 | Demo 不是真相源，且开放世界 Cell/区域流送不是 TopDown Rooms 直接替代 | 仅作为样板参考；正式区域系统只记录缺口 |

因此，TopDown 的优势不是“只有动作方面”，而是“动作表现生态”整体更强：能力、移动、武器、反馈、AI 战斗样板、交互样板、关卡接线和 HUD 样板都强。它不适合作为总地基，是因为 RPG 数据、任务、背包、存档、开放世界长期状态和未来控制组真相不在 TopDown 里。

### 暂不实现的开放世界缺口

第四层开放世界模拟没有现成可直接整段搬来的完整闭包：当前只补上了当前的 live runtime 角色实体注册，其余区域/Cell、队伍控制、派系、AI 日程、经济/基地生产、世界事件和动态任务绑定仍只能先登记。没有参考闭包时不得空写 `World` 模块、空目录、空接口或空系统；等找到能证明价值的参考或进入具体功能验收时，再按单个 Module 落地。

## TopDown 融合优先顺序

在实施点击移动 / WASD / 摇杆切换前，先补 TopDown 已经证明更成熟、且会影响后续控制器边界的地基层。这里的“搬”不是复制 TopDown 整套 `Character/GameManager/InputManager/GUIManager`，而是把同职责优势吸收到 `GameCore` 的正式闭包里。

| 顺序 | 先搬内容 | 参考来源 | 当前处理 |
| --- | --- | --- | --- |

### 反馈系统状态

`MMFeedbacks` 插件本体已经随 TopDownEngine 进入 `Assets/Plugins/TopDownEngine/ThirdParty/MoreMountains/MMFeedbacks`，TopDown 源码里也大量使用 `MMFeedbacks` 和 `PlayFeedbacks`。但这不等于 FantasyWord 的反馈系统已经完成。

当前 GameCore 的事实是：

## 目录位置裁决

| 位置 | 正式动作 | 设计模式理由 | 软件工程理由 | 易用理由 | 不选什么 |
| --- | --- | --- | --- | --- | --- |
| `Assets/Scripts/GameCore` | 保留为当前正式运行时总根；只继续替换内部薄弱模块，不提前拆家 | 在开放世界层、角色层、表现层都还没形成独立真相源前，`GameCore` 继续承担“RPG 世界规则真相 + 吸收后的动作/工具正式入口”这段连续职责；先拆成多个顶层目录只会形成名字上分层、运行时上仍耦合的伪模块 | 把序列化、Prefab 接线、场景宿主、系统入口和门禁集中在一个稳定根上，能减少迁移期状态分叉、漏改和错误归因 | 当前开发者只需要记住“正式 runtime 在 `GameCore`”，不必先猜哪些目录已经是真正产品层、哪些还只是未来规划 | 不选“为了看起来像最终产品目录，先拆成 `Characters/World/Combat/Presentation/...` 多个顶层根” |
| `Assets/Editor/GameCore` | 保留为只服务 `GameCore` 的项目侧编辑器根 | 编辑器工具的职责是服务运行时资产、检查器、验证器和 AI 自动化恢复入口，不是玩法模块本身 | 直接利用 Unity `Editor` 编译边界，天然阻断编辑器代码误进运行时程序集、玩家构建和序列化闭包 | Unity 使用者找 PropertyDrawer、EditorWindow、验证器时入口稳定且直观 | 不选“运行时和编辑器脚本按功能混放，只靠 asmdef、后缀或命名约定区分” |
| `Assets/Plugins/TopDownEngine` | 保留第三方原始来源边界；项目侧只吸收胜出的动作模式和正式入口 | `TopDownEngine` 的价值是动作能力、武器、反馈、关卡样板，不是项目侧总生命周期；保留原件更能清楚表达“参考源”和“正式吸收实现”是两层东西 | 原结构更利于升级、对照、问题归因和门禁；也能防止 AI 或人把 TopDown manager 误当正式项目入口继续扩写 | 查问题时能直接分清“第三方原件在哪”“项目正式吸收落点在哪” | 不选“把 TopDown 源码剪碎并回项目目录，再让项目代码散落直调它的 manager” |
| `Assets/Plugins/YokiFrame` | 保留第三方工具层来源边界；项目侧直接用稳定工具入口或替换重复工具实现 | `YokiFrame` 竞争的是对象池、文件层、输入重绑定、UI 工具等通用能力，不应伪装成项目玩法模块 | 保留原结构最利于升级和定位工具问题，同时避免把 `Architecture/EventKit/SingletonKit` 误升格为游戏生命周期 | 对开发者来说，工具能力集中在插件根最容易复用；项目侧无需再维护一层浅包装 | 不选“把工具源码拆进项目业务目录，或额外再包一层 `Wrapper/Facade` 做伪统一入口” |
| `Assets/Scripts/World`、`Assets/Scripts/Characters`、`Assets/Scripts/Items`、`Assets/Scripts/Combat`、`Assets/Scripts/Presentation` | 只作为未来晋升目标，当前不提前落正式闭包 | 只有当对应系统已经脱离参考直拷闭包、形成 FantasyWord 自己的独立真相源时，顶层产品目录才有真实职责；否则只是目录名先行 | 现在提前晋升只会把引用闭包、迁移边界和回归面一起放大，还会让“哪些代码是地基、哪些是产品层”重新变混 | 当前团队先记住一条规则更省认知成本：未形成独立真相源的代码继续留 `GameCore` | 不选“先建一套看起来完整的产品目录，再把仍受 parity/同步门禁约束的代码搬过去” |

## 当前实施进度

- 已完成对象池替换收口：`FloatingText`、`FloatingTextPool`、`UIHUDEffectBar`、`UICharacterInfo`、`UICraft` 已使用 YokiFrame `GameObjectPoolService`，不再维护项目侧 `InstancePool` 或浮字数组池。
- 项目侧 `InstancePool` 已从 `GameCore` 退场；`Sync-2DRPGFoundation.ps1` 与 `Test-FoundationReferenceParity.ps1` 已登记排除，后续同步 2DRPG 参考时不会把旧池刷回。
- 玩家移动对齐已完成当前地基所需收口：`Movable` 保留 2DRPG 的实体、控制器、存档和 RPG 速度修正语义，同时吸收 TopDown `CharacterMovement` 的方向模式、模拟输入、加速、减速、闲置阈值、移动禁止开关和上下文速度倍率栈；`uMMORPG Movement` 的 `Reset/Warp/IsValidSpawnPoint/NearestValidDestination` 与 `Navigate(destination, stoppingDistance)` 停止半径语义，以及 `PlayerNavMeshMovement.MoveWASD()` 的“直接方向驱动取消旧路径”规则，只作为合同/规则补强融合到该现有闭包，用于移动重置、`TeleportTo` 目标修正、停止距离判定与后续导航 Provider 边界。后续只有在进入真实玩法阶段时，才继续评估更完整的碰撞控制器边界。
- 场景恢复链也融合了一条来自 uMMORPG 的健壮性规则：`MapSystem.LoadDataBlock(...)` 现在会像 `Database.CharacterLoad()` 一样，在恢复当前地图后校验保存位置是否仍对当前 2D 碰撞闭包合法；若已失效，就回退到 `MapInfo.initialSpawnCheckpoint`，而不是让角色先带着坏坐标进图。
- 世界穿越入口当前也融合了一条来自 uMMORPG 的入口鲁棒性规则：`Teleporter` 进入判定现在会像 `Portal.cs` 一样，从子碰撞体向父级回溯正式 `Hero`，而不是要求触发 collider 自己就是角色根对象；这样子碰撞体或骨骼碰撞体进入传送门时不会漏掉正式穿越目标。
- 能力调度与动作权限已完成第一段收口：`AbilityPermissionSettings` 把 TopDown `CharacterAbility` 的能力许可、角色条件阻断、移动阻断和其它武器状态阻断压到 `ActiveAbilitySheet` 的 Inspector 配置里；`ActiveAbilityBase.CanFire()` 统一走该合同；`CharacterBase` 只暴露 GameCore 自己的能力武器状态查询；`AbilityBase.UpdateAnimationState()` 提供动画状态更新触点。该实现不接入 TopDown `Character`、`Health`、`InputManager` 或 MoreMountains 状态机。
- 武器执行层第三段已完成：`ActiveAbilityBase` 现在承接 TopDown `Weapon` 风格状态机，`PlayerController` 增加按键松开语义，`CharacterBase` 暴露停止开火/换弹入口，近战、投射物、冲刺、自施法和召唤能力都改为“状态机决定出手时机，子类只执行一次真实出手”；`MeleeAttackAbility` 进一步吸收 TopDown `MeleeWeapon/DamageOnTouch` 的短时命中窗口、忽略 owner、持续扫描、每目标冷却、击退覆盖和短暂无敌。正式入口仍在 `GameCore`，不是 TopDown 兼容层。
- 存档文件层已完成当前地基融合：`SaveSystem` 保留 2DRPG 的 `SaveDataBlock` 世界状态聚合，底层文件读写、槽位、头部元数据、版本和删除改用 YokiFrame SaveKit；旧菜单 `SAVEFILE_A/B/C` 稳定映射到 SaveKit 槽位 0/1/2，未引入第二套存档真相。
- 输入重绑定与输入目标解耦已完成当前地基融合：`InputSystem` 保留 2DRPG 的 Gameplay/UI action 语义、地图切换锁输入和 `PlayerInput` 生命周期，同时成为唯一 `InputAction` 订阅者；YokiFrame InputKit 只作为绑定导出/导入、保存/加载、重置、显示名和冲突查询工具；`PlayerSystem` 则把“玩家 Hero 数据真相”和“当前接输入的控制对象”分开。未接入 TopDown `InputManager`、MoreMountains 输入事件或第二套移动端 UI 输入根。
- 当前控制对象的 UI/表现/拾取收口继续推进：HUD 技能栏、HUD 状态条、HUD 效果栏、能力菜单、角色菜单、效果列表、区域音频、玩家触发器、`CameraShake` 和 `PickableItem` 的“仅玩家可拾取”判定，已开始跟随 `PlayerSystem.currentControlledCharacter/currentControlledHero`；其中 `CameraShake` 现在通过 `GameplayFeedbackSet` 的正式受击反馈上下文判断是否震动，不再直接监听全局伤害通知。角色菜单里的货币仍保留全局背包真相，主背包和货币等也继续保留在玩家 Hero 长期存档语义，不在没有进一步裁决前草率改成“任何当前控制角色都共用”。与此同时，角色能力增减事件发布、技能槽自动装配/移出，以及装备效果压制的默认入口也已经从 `Hero` 收回角色级 owner，不再依赖 Hero override 才成立。
- 玩家长期真相入口也已继续收口：玩家命令、能力解锁条件、怪物奖励、任务等级校验和重生入口，现已显式统一到 `PlayerSystem.PlayerInstance`，不再让新补丁继续依赖 `GameManager.Player` 静态别名。这样“当前前台控制谁”和“玩家长期存档 Hero 是谁”在代码层已经分成两条明确边界。
- Inventory 菜单的边界也已收口：背包格子和金钱仍然来自全局 `InventorySystem.items/money`，但装备目标、物品使用目标和属性栏显示已经统一切到显式上下文或当前控制角色解析链，而不是子控件自己猜当前 Hero。这样是在不拆第二套背包真相的前提下，把前台角色操作收回正式入口。
- 当前控制对象的回退规则也已正式收进 `PlayerSystem`：`currentControlledCharacterOrPlayerInstance` 现在是 UI、表现、拾取和玩家命令入口的统一角色查询 API；明确需要成长语义的入口，再在业务位点按需做 `character as Hero`。这样后续若控制组语义变化，只需要改正式系统，不需要再扫一轮各处散落的 `?? PlayerInstance` 判断。
- `2026-06-17` 已把没有真实调用者的 `CharacterRegistrySystem` 撤回：当前项目还没有任何正式代码真正消费“live runtime characters 在哪”这类集合真相，因此不再为未来队伍、派系、离线角色或区域外模拟提前保留项目级预留系统。等这些能力进入正式规格并出现真实调用者后，再裁决是否需要重建注册入口。
- Hero 专属前台查询不再作为 `PlayerSystem` 的长期公开主入口；当前正式口径是统一先查当前控制角色，再在明确需要成长语义的业务位点按需做 `character as Hero` 判定。这样避免系统级再保留一套与角色级入口并行的 Hero 前台 API。
- `Hero` 上那组装备查询/穿脱兼容公开口也已经退场；当前装备查询、穿脱、尸体转移和生命周期卸装都直接走 `CharacterEquipment`，不再保留一层 Hero 平行入口。
- 世界穿越链当前仍保留在玩家存档 Hero 真相上：`MapSystem.TeleportTo/RespawnPlayer`、`Checkpoint` 和 `Teleporter` 现已显式统一到 `PlayerSystem.PlayerInstance`。这不是保守偷懒，而是避免在控制组和世界角色实体语义尚未锁定前，先制造“触发器目标”和“实际被传送目标”不一致的问题。
- 地图表现层基础配置已完成：`MapInfo` 在保留 2DRPG `playtestCheckpoint` 合同的同时，新增默认出生点、重生延迟、地图边界和相机目标；`Checkpoint` 在保留 `PersistableCheckpoint` 存档语义的同时，新增检查点顺序和强制覆盖规则；`MapSystem` 保存有序检查点状态并按地图配置延迟重生。该融合没有挂 TopDown `LevelManager`、`GUIManager`、`MMCameraEvent` 或 TopDown 场景加载流程。
- UI 宿主替换已落到正式代码：当前正式菜单宿主已经是 `UIManager + UIKitMenuPanelBase + UIKit` 原生 stack，旧 `UIMenuManager/AUIMenu` 不再是现役运行时真相。后续不再讨论“要不要接 UIKit”，只继续清理旧资源、共享构件和文档遗留，并保持禁止双栈回潮。
- 投射物暂未池化，因为 `Projectile` 继承 `Persistable` 并参与存档/恢复；必须先定“投射物生命周期 + 持久化”规则。
- TopDownEngine 已导入为参考闭包；角色移动已完成输入手感与速度上下文吸收，原先额外的移动状态胶水已收口。能力权限、武器执行、近战命中窗口和受击表现参数已完成当前地基吸收；能力/武器生命周期、命中、受击、死亡、奖励掉落、拾取和交互反馈已通过 `GameplayFeedbackSet` 接入。`PickableItem` 的通用拾取条件、禁用流程和 `InventorySystem` 交付入口也已吸收到 `GameCore/Runtime/Loot`。碰撞控制器边界、交互区/机关区样板、相机/屏幕反馈和投射物池化仍属于后续阶段。
- Skyrim/Kenshi 目标复核已完成：当前缺口不是控制器，而是开放世界模拟层。后续不得再把“GameCore 静态基线已收口”描述成“足够支撑完整开放世界”；只能说它足够承载下一阶段世界运行时内核设计。

## 禁止项

- 禁止用“当前已经用了谁”作为技术理由。
- 禁止新增 `Compatibility`、`FoundationSupport`、`Adapter`、`Wrapper`、`Facade` 这类为同时保留两套玩法实现而存在的目录或类型。
- 禁止让正式玩法代码直接散落依赖 TopDownEngine manager；吸收 TopDown 能力时必须裁掉它自己的总生命周期假设。
- 禁止把 YokiFrame `Architecture/EventKit/SingletonKit` 当成新游戏生命周期。
- 禁止为了“所有成熟框架都用上”而引入重复公开入口。
- 禁止新增开放世界系统时继续添加 `GameManager.XxxSystem` 静态快捷入口。
- 禁止把 Unity Behavior、GOAP、DOTS 这类候选来源直接装进项目；工作区虽已保留 `Assets/Plugins/AStar 2D Grid Pathfinding` 本地候选源码，但它也不得因为“已经导入仓库”就直接升格成正式导航依赖。所有这类来源都必须先有对应功能、真相源和验收场景。
- 禁止把第三方插件本体移出 `Assets/Plugins` 或改 `.meta/GUID`，除非用户当轮明确授权。
