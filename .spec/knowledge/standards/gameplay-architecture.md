# Gameplay 架构规范

## 适用范围

本文件只裁决 FantasyWord 具体业务层内部怎么组织，不重新裁决 YokiFrame / GameCore / Gameplay 的总分层。涉及三层依赖、GameCore 特化、迁移落点或外部参考吸收时，先读 [`framework-layering.md`](framework-layering.md)，再读本文件。

FantasyWord 的 Gameplay 层承载玩家可见规则、本项目作者内容和产品取舍。它不是 CardLoop 的卡牌生存业务副本；从 CardLoop 同步到这里的只有“领域对象优先、唯一写入口、协作者降级、不为未来扩展空建结构、不让 Mod/联机压力制造第二真相”这些通用做法。

## 总结论

Gameplay 具体业务必须围绕玩家可感知的领域对象和生命周期组织，而不是把主结构拆成平铺的 `State`、`Solver`、`Resolver`、`Projector`、`System` 文件集合。

- 区域 / Cell、世界运行、队伍、角色、派系、基地、生产、探索、任务事件、战斗遭遇、装备表现和具体游戏模式，必须有清楚的对象边界、核心状态和唯一写入口。
- 规则计算、候选生成、投影刷新、校验器、索引器可以存在，但它们是领域对象的内部协作者，不是领域主结构。
- 不采用“看起来更可扩展”的贫血拆分，除非已经有真实性能、数据布局、同步或调试证据证明对象模型不够用。
- Mod、作者工具和未来有限人数联机不是拆掉对象的理由；正确做法是让内容身份、命令入口、快照、权限、随机源、版本和失败语义清楚。

## 外部参考候选

外部工程、成熟游戏、官方文档和历史代码只能提供候选证据，不能自动成为 FantasyWord 的业务知识库、目录规范、运行时 owner、测试入口或完成标准。

使用参考前必须说明：

1. 它证明的现实职责是什么。
2. 它不证明什么。
3. FantasyWord 当前同职责 owner 是谁。
4. 它的结构、命名、资源路径、场景、单例、测试或业务数据是否进入本项目。
5. 进入本项目后的验证入口是什么。

如果只是“来源项目这么写过”，但说不清 FantasyWord 的玩家目标、生命周期和唯一写入口，就不得写成正式实现或正式规范。

## Gameplay 对象层级

后续 Gameplay 目录和代码应优先表达对象、生命周期和业务归属，而不是表达实现阶段：

```text
Gameplay
  Content/        具体内容作者源、稳定 ID、索引和校验
  World/          世界运行、区域 / Cell、区域内外模拟、世界事件
  Characters/     玩家、队友、NPC、怪物、控制组和角色长期身份
  Factions/       派系、声望、敌友关系、通行权和区域归属
  Economy/        基地、生产、库存流转、商店和区域外简化 tick
  Items/          具体物品、装备、掉落、制作和可用规则
  Combat/         本游戏战斗内容、遭遇规则、技能配置和状态策略
  Presentation/   角色表现、装备换装、相机、反馈、动画和项目 UI
  Modes/          开放世界探索、剧情演出、局内小游戏或其它模式运行态
```

这只是职责组织示意，不要求一次性创建空目录。只有具体业务、作者源、运行时 owner 和验收入口已经锁定时，才创建对应文件夹。

## 设计门禁

### 领域对象优先

遇到新名词时，先判断它是不是玩家可感知对象：

- 是：优先建立对象或聚合，让对象持有自己的核心状态和行为入口。
- 不是：再判断它是值对象、作者定义、内部协作者、UI 投影、编辑器工具还是测试夹具。
- 不能因为出现一个名词就创建 `XSystem`、`XContext`、`XRegistry`、`XManager` 或 `XService`。

### 继承与组合裁决

先判断领域关系，再决定 C# 结构；不能因为“以后也许扩展”或“想避免空字段”直接选择组合、接口或继承。

| 事实关系 | 正式结构 | 约束 |
| --- | --- | --- |
| 子对象在整个运行生命周期内都是父对象的一种，并且必须参与父对象核心契约、保存、查询或规则执行 | 继承 | 派生类直接继承父类，父级集合保存基类引用；不要把稳定子类型伪装成父类上的可选组件。 |
| 行为、效果、装备、表现或临时状态可以独立添加 / 移除、可同时出现多个，或有独立生命周期但不改变对象身份 | 组合 | 被组合对象必须有自己的真实状态、唯一 owner 和可解释生命周期；不能只是为避免类型判断而包一层字段。 |
| 只是一次规则计算、查询、投影、校验或短暂输入姿态 | 不建立领域组件 | 作为父级对象的方法、值对象或内部协作者处理；不要为了名词再建一个可选运行时对象。 |

### 唯一写入口

状态必须由最接近业务不变量的对象修改：

- 世界区域、Cell 加载状态、区域外简化模拟和区域内对象归属由 `Gameplay/World` 的正式 owner 提交，不挂到 `GameManager.*` 静态快捷入口。
- 队伍、当前控制组、跟随 / 待机 / 工作命令和角色长期身份由角色 / 队伍 owner 提交，不散落在输入、UI 或相机脚本里。
- 派系关系、声望、犯罪、通行权和区域归属由派系 owner 提交，不让任务、战斗或 UI 各自改一份。
- 基地生产、库存流转、工作岗位和区域外 tick 由经济 / 生产 owner 提交，不用场景触发器或菜单回调直接写世界真相。
- 装备表现、MiniFantasy 资源、动画、相机和反馈属于 Gameplay 表现领域或 GameCore 表现扩展点的具体实现；它们不能反向拥有背包、属性、能力或任务真相。
- 技能、属性、效果、标签和时间轴的正式规则继续服从 EX-GAS 与 GameCore 集成边界；Gameplay 只提供具体内容、策略和作者源，不建立第二套技能 / 属性规则真相。
- UI 和表现只提交用户意图或订阅状态，不保存第二份玩法状态。

如果非法状态只能由绕过正式入口形成，应收窄入口或直接抛错，不新增防护表、兜底状态或静默修复。

### 协作者降级

`Solver`、`Resolver`、`Projector`、`Validator`、`Index` 的存在条件：

- 背后有足够复杂的算法或转换，删除后复杂度会分散到多个调用方。
- 只服务一个父级对象时，应放在父级对象目录下，并尽量设为内部协作者。
- 不能保存第二份玩法真相，不能要求作者手填内部 key。
- 公开 API 必须比实现更小；否则就是浅模块，应并回父级或删除。

### 目录表达对象

目录应优先表达游戏对象和生命周期，而不是表达实现阶段：

- 推荐：`World/Regions`、`Characters/Party`、`Factions`、`Economy/Production`、`Items/Equipment`、`Combat/Encounters`、`Presentation/Equipment`、`Modes/<模式名>`。
- 谨慎：把所有 `State`、`Snapshot`、`Resolver`、`Projector`、`System` 同级堆在一个大目录。
- 禁止：为了以后可能有而提前建空目录、空接口、空 Context、空 Manager 或无真实职责的兼容壳。

## Mod 与未来联机

Mod 和有限人数主机权威合作通过以下方式保证，不通过第二套状态保证：

- 内容作者源使用稳定 ID、资源系统、数据库引用、GAS 标签和内容包依赖，不允许第二套身份。
- 运行时改动通过命令或请求进入对应聚合根，聚合根复核权限、版本、内容存在性和随机源。
- 可保存 / 可同步状态通过快照表达；快照保存事实，不保存 Unity 表现对象或资源句柄。
- 客户端 UI 可以生成候选和意图，但不能绕过世界 / 队伍 / 角色 / 模式 owner 直接写权威状态。
- 过期联机指令、缺失 Mod 内容、版本不匹配属于真实外部失败，可以显式拒绝；内部不变量破坏必须直接报错。

当前阶段仍不接入网络框架，也不创建网络空壳。联机只作为单机架构的可迁移性约束。

## 回审口径

每个已经完成或准备继续的 Gameplay 模块，都必须用以下问题回审：

1. 玩家可感知对象是什么？它现在有没有直观对象承载？
2. 谁拥有核心状态？是否存在第二份状态、第二套 ID、第二套资源、第二套事件或第二写入口？
3. 外部资料只能证明哪些事实？哪些事实必须回到 FantasyWord 当前目标和当前源码判断？
4. 当前结构更像对象聚合，还是贫血平铺？如果是后者，是否真的有性能、同步或调试证据？
5. 删除某个 `System`、`Context`、`Solver`、`Projector` 后，复杂度会回到多个调用方，还是会直接消失？
6. Mod、作者工具、存档和未来联机压力下，是否需要新增第二真相？如果需要，说明设计还没收口。

测试通过只能证明覆盖到的行为；架构正确还必须有对象边界、职责归属、参考候选裁决和扩展压力证据。

## 当前订正方向

- 内容定义继续保留稳定内容 ID、ScriptableObject 作者源、GAS 标签和资源系统归属，但要避免把所有内容做成万能父类，或让非资源事实强行拥有资源表现字段。
- 开放世界进入正式实现时，优先围绕 `World / Regions / Cells` 这类玩家可感知对象建立 owner；没有具体区域、作者源、运行时生命周期和验收入口前，不创建空 `WorldSystem`、空 `WorldContext` 或顶层占位目录。
- 角色、队伍、派系、经济和基地生产只有在持有 FantasyWord 具体状态、命令或作者内容时才进入 Gameplay；仍属于通用 RPG 闭包、输入门面、存档门面或资源门面的代码继续留在 GameCore。
- 表现业务后续向 `Gameplay/Presentation` 收口，但当前 `Assets/Scripts/Gameplay/Runtime/Presentation/EquipmentSystem` 已被资源引用，迁移前必须完成脚本、`.meta`、Prefab、Scene、作者资产和测试入口对账。
- 技能、属性、效果和时间轴继续以 EX-GAS 与 GameCore 集成边界为规则主轴；Gameplay 只提供具体内容、策略和表现接入，不建立第二套技能 / 属性规则真相。
- 后续具体模式、项目 UI、任务事件和小玩法不能提前按空系统拆分；必须先有玩家可见对象、作者源、生命周期和完成验收。
