# 一级缺口候选优先级台账

> 用途：把 `S3` 当前真正可追的本地候选源排出优先级，避免再把“概念候选”“只有文档名的候选”“强绑 3D/Mirror 的负证据”混在一起。
> 本文只记录**本地现态证据**，不把未来可能找到的来源写成已具备。
> 边界：本文只服务 `2D 移动与场景组织` 的 4 个一级缺口，不覆盖开放世界模拟层本身。

## 当前本地现态结论

- `uMMORPG` 本地源码可读，且 `Movement.cs`、`NavMeshMovement.cs`、`RegularNavMeshMovement.cs`、`PlayerNavMeshMovement.cs`、`PlayerCharacterControllerMovement.cs`、`CharacterController2k.cs`、`Instance.cs`、`PortalToInstance.cs`、`NetworkManagerMMO.cs`、`NetworkStartPositionForClass.cs`、`SafeZone.cs`、`Entity.cs`、`Player.cs`、`Monster.cs` 与 `_UI/UIRespawn.cs` 都实际存在。
- 其中 `MovementSystems` 目录已经可以固定分型：`NavMeshMovement.cs / RegularNavMeshMovement.cs` 只算 `NavMesh + Mirror` 负证据，`PlayerCharacterControllerMovement.cs + CharacterController2k.cs` 只算 `Mirror + 3D CharacterController` 负证据；真正还保留局部移动参考价值的，只剩 `Movement.cs` 与 `PlayerNavMeshMovement.cs`。
- `TopDownEngine` 本地源码可读，但当前与点击寻路/出生点分流最相关的本地证据仍是：
  - `MouseDrivenPathfinderAI3D.cs`
  - `CharacterPathfinder3D.cs`
  - `CharacterPathfindToMouse3D.cs`
  - `CharacterGridMovement.cs`
  - `GridManager.cs`
  - `GoToLevelEntryPoint.cs`
  - `GameManager.cs`
  - `LevelManager.cs`
- 当前**没有**找到本地 `CharacterPathfinder2D`、`MouseDrivenPathfinderAI2D` 这类 2D 点击寻路正式闭包。
- `uMMORPG` 当前也没有独立 `Respawn.cs` 或统一区域/出生点宿主来承接玩家复活与怪物自复活；玩家复活写在 `Player.UpdateServer_DEAD()`，怪物自复活写在 `Monster` 自己的状态机里，`SafeZone` 只是局部区域标记脚本。
- 当前工作区已导入本地 `Assets/Plugins/AStar 2D Grid Pathfinding` 源码；它提供 `AStarPathfinding.cs`、`AStarBoolMap.cs`、`AStarCostMap.cs` 这组 2D 网格 A* 算法，以及 `randomPather.cs` / `PathFindTest.cs` 这类示例脚本。
- 它还自带 `Example 1/DemoGrid.cs` 与 `Example 2/Scripts/Grid/GridManager.cs` 这两类 demo 宿主，证明 world/grid 映射、walkable/cost map 生成和点格取样也已经有本地源码，不是只剩一层纯算法。
- 但这些能力目前仍停留在 demo 单例、测试点击和 `MoveTowards` 跟随层，没有正式导航状态、取消、停止半径、UI 遮挡和 `Movable / PlayerController` 统一落点，因此还不能直接当当前项目的单机/本地 2D 导航正式闭包。

## 优先级规则

| 优先级 | 含义 |
| --- | --- |
| `A` | 本地源码已存在，且直接命中当前一级缺口，应先继续深读和摘证据 |
| `B` | 本地有部分证据，但明显强绑 3D / Mirror / demo，只能作为局部负证据或边界样板 |
| `C` | 当前只有概念候选或来源名，本地没有可直接复核的正式闭包 |

## 当前最值得继续深挖的 5 个本地源码点

1. `uMMORPG/Movement.cs`
2. `uMMORPG/MovementSystems/PlayerNavMeshMovement.cs`
3. `uMMORPG/Instance.cs`
4. `uMMORPG/NetworkManagerMMO.cs + NetworkStartPositionForClass.cs`
5. `Assets/Plugins/AStar 2D Grid Pathfinding/AStar/Needed Scripts/*`

原因很简单：

- 它们都是真实存在的本地源码
- 都直接命中 4 个一级缺口
- 即使最后不能直接搬，也能给出“为什么现在不能写”的强证据

补充：

- 这里的“继续深挖”已经不再包含 `uMMORPG MovementSystems` 目录里的负证据文件。
- 那组目录当前只保留为固定边界，不再作为优先继续阅读对象。

## 当前统一结论

- `A` 级候选基本都来自 `uMMORPG`，因为当前本地真有可读源码，且直接命中缺口；这里的 `A` 只代表“优先继续摘证据”，不代表“已经可以直接吸收”。
- `TopDown` 在 `S3` 里当前更像 `B` 级边界样板，而不是可直接吸收来源。
- `Assets/Plugins/AStar 2D Grid Pathfinding` 已从“概念候选”升级为可读本地源码；它当前不止算法层，还带有 demo 级 world/grid 映射与路径跟随宿主。但离当前项目的正式导航 Provider 仍差运行时状态、取消、停止半径、UI 遮挡与输入/移动闭包整合。
- `Unity 2D/Tilemap 导航方案` 这类未锁定具体来源的项仍只算 `C` 级概念候选；没有实际源码证据前，不得当成“下一步就能接入”。
- 对前两个一级缺口来说，本机现有参考池已经复核到当前边界；后续优先动作不是再给本机候选重新排级，也不是据此直接进入实现，而是按 `2D移动与场景组织外部参考搜索指引.md` 去补外部新源码。
