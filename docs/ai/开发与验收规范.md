# 开发与验收规范

## 前提锁定

准备修改代码、配置、数据、资源、场景或包配置前，必须确认：

- 问题对象：本轮处理的具体文件、资源、目录、包或场景。
- 真相来源：用什么证据证明它确实命中本轮问题。
- 目标入口/环境：修改作用在哪个 Unity 工程、Editor、包配置或运行入口。
- 验收口径：修完后用什么方式确认。

四项缺一时，只能继续补证据或提出最小问题。

## 旧内容处理

- 旧恢复记录、乱码文档、旧测试脚本和旧资源残留先分类：正式链路、归档参考、真正垃圾。
- 仍有参考价值但不进入正式链路的内容归档，不直接删除。
- 真正垃圾必须同时满足：无正式引用、无参考证据价值、无归档必要、无未来明确复用面。

## 验证层级

- 文档与包清单改动：先做静态读取、路径检查、关键词检查。
- C# 代码改动：至少做编译敏感搜索；必要时走 Unity Test Framework。
- 包或 ProjectSettings 改动：需要 Unity 导入确认时，用当前唯一正常 Editor + AIBridge。
- 场景、Prefab 和 PlayMode 行为：只有静态证据不足时才升级到场景/PlayMode 验证。

## Unity 自动化边界

- 默认不聚焦 Unity，不切 PlayMode，不打开/切换场景，不截图。
- 需要高层验证时，先说明当前低层证据缺口。
- 同一轮没有新成批修复前，不重复跑高成本验证。

## 完成性口径

- 不把“已写文档”说成“已完成迁移”。
- 不把“包清单已改”说成“Unity 已成功导入”，除非经过 Unity 导入或包解析验证。
- 不把旧历史计划中的完成状态当成当前完成状态。
