# 2D移动与场景组织缺口矩阵

> 本文只记录当前**框架缺口**，不记录业务实现计划。
> 目的不是催生实现，而是把“还缺什么正式参考、为什么现在不能写、后面补参考时该看什么”固定成一张表。

## 适用范围

- 只覆盖当前 `FantasyWord` 在 **2D 移动** 与 **场景组织** 上还没有正式参考闭包的部分。
- 默认服务于后续参考复核、参考接入和“为什么现在不能实现”的说明。
- 不代替 `openspec`；正式约束仍以 `openspec/changes/define-fantasyword-foundation-framework/` 下的 change 为准。
- 本文不覆盖开放世界模拟层本身；区域/Cell、队伍、派系、AI 日程、经济和局部模拟是否开工，是另一层长期架构问题。

## 当前总原则

- 有参考才做；没有正式参考就只登记，不实现。
- 能直接搬就直接搬；不能直接搬的只记录证据，不造兼容层、不造空宿主、不造过渡层。
- `uMMORPG Remastered - MMORPG Engine [2.41]` 当前只算**局部源码证据源**，不是整体替换运行时。
- 当前 2D 移动与场景组织一共还有 **4 个一级框架缺口**；未补齐前，相关二级问题一律不得绕过一级缺口先落代码。

## 术语修正

- 旧文档曾用网络框架反向命名来描述这类缺口，容易误导；准确表述应是：当前正式移动闭包必须先能在单机本地成立，不能把导航、点击移动、实例宿主或出生点分流绑死在 Mirror 的生命周期、网络对象、服务器权威或 MMORPG 业务流上。
- Mirror、NGO 或其它网络框架解决的是同步、权威、对象复制和网络生命周期；它们不是路径搜索、地面命中、落点修正、路径跟随和停止半径本身的替代品。
- 当前联机是确定目标，但本阶段不实现联机，所以后续缺口统一按“单机/本地闭包”理解；网络代码只能作为负证据或职责证据，不作为当前实现目标。
- `uMMORPG` 在产品复杂度上确实比普通单机移动更大，但不能简单理解成“MMORPG 移动减去 Mirror 就是当前完整移动参考”。它的可运行移动闭包同时依赖 `NavMeshAgent`、`NetworkNavMeshAgent/NetworkNavMeshAgentRubberbanding`、3D 射线、本地玩家状态和 MMORPG 行为流；当前能直接吸收的是移动合同和局部规则，不是整套 2D `Rigidbody2D + Sprite` 移动实现。
- 按当前目录级复核，`uMMORPG/Assets/uMMORPG/Scripts/MovementSystems` 已经扫到边界：`NavMeshMovement.cs / RegularNavMeshMovement.cs` 继续只算 `NavMesh + Mirror` 负证据，`PlayerCharacterControllerMovement.cs + CharacterController2k.cs` 继续只算 `Mirror + 3D CharacterController` 负证据；真正还保留局部移动参考价值的，只剩 `Movement.cs` 与 `PlayerNavMeshMovement.cs`。
- RTS 参考可以用于闭合移动缺口，前提是它提供可映射到俯视角 2D 的导航/路径执行闭包，例如地面命中、路径请求、路径跟随、停止半径、取消旧路径、单位/NPC 共用导航真相。
- 3D RTS 参考也可以用，但分两种：如果核心是网格、图搜索、流场、A* 或与维度无关的路径跟随，可以考虑直接映射；如果核心强绑 `NavMeshAgent`、3D 射线、3D Collider、CharacterController 或场景高度语义，就只能当职责样板，不能单独关闭当前 2D `Rigidbody2D + Sprite` 导航缺口，除非项目正式改成 2.5D/3D NavMesh 运动体系。

| 单机/本地场景实例宿主参考 | `Instance.cs` 证明实例宿主至少要显式承载入口、归属、边界、实例内出生点和清理策略；`PortalToInstance.cs` 证明入口脚本最多只该负责查找/创建实例并把玩家送到实例入口 | 现有证据强绑 Mirror 队伍副本、网络实体清理与 3D 边界；不能直接塞回当前单机 `MapSystem + MapInfo + Teleporter` | 实例模板放哪、实例入口归谁、归属如何表达、边界如何定义、实例内出生点如何挂、离场清理和实例定位规则归谁；还要回答实例运行时位置是否由宿主统一稳定重建 | 不得新增 `InstanceHost`、`MapInfo` 临时实例字段、`Teleporter` 内硬编码副本逻辑 |
| 单机/本地出生点分流宿主参考 | `NetworkManagerMMO.GetStartPositionFor(...) + NetworkStartPositionForClass.cs` 证明出生点分流应有正式宿主 | 现有证据强绑 Mirror 出生点体系与角色创建流程；不能直接抄成当前地图入口逻辑 | 分流规则挂在哪、默认回退点在哪、失败如何回退、地图入口/角色模板入口/控制组入口是否同宿主；还要回答“专用出生点缺失时如何正式回落到默认入口” | 不得把分流 if/else 硬编码进 `Teleporter`、`MapInfo`、`PlayerSystem` |

### 当前新增 RTS 候选复核

`C:\Gamedev\Unity\Project\RTS Starter Kit\RTS Starter Kit` 已不再是空模板判断。按 `2026-06-14` 本地源码复核，真实 RTS 源码位于 `Assets/InsaneSystems/RTSStarterKit`。

已确认的高价值源码证据：

- `Controls/InputHandler.cs`：左键选择、右键下达命令、UI 遮挡拒绝点地、鼠标点击阈值。
- `Controls/Ordering.cs`：屏幕点位转世界命中，按命中对象创建 `MovePositionOrder / FollowOrder / AttackOrder`，再统一下发到选择集。
- `Order.cs`：订单对象把“移动到点、跟随目标、攻击目标”抽成可克隆命令。
- `Units/Unit.cs`：单位持有订单队列，`AddOrder(..., isAdditive)` 支持替换或追加订单，`EndCurrentOrder()` 负责停止当前移动。
- `Units/Movable.cs`：移动模块拥有 `MoveToPosition / Stop / isMoving / sqrDistanceFineToStop / customSpeed`，并把移动阻断放在执行层。
- `UnitsFormations.cs` 与 `AI/UnitsGroup.cs`：组下发、阵型落点和 AI 复用同一订单入口。

当前裁决：

- 它不能关闭“单机/本地 2D 导航 Provider”缺口，因为移动执行强绑 3D `NavMeshAgent`、3D Collider、3D 射线和场景高度语义。
- 它不能直接关闭“完整 2D 点击移动执行闭包”，因为点地和路径执行不是当前项目的 2D `Rigidbody2D + Sprite` 真相。
- 它当前只能登记为“点击移动输入裁决、订单链、组命令和阵型落点”的职责证据；就算后续只吸收这类证据，正式落点也必须继续是现有 `Movable / PlayerController / IPlayerInputTarget`，不能另起 RTS 控制器或同职责测试控制器。
- 当前 `Movable` 已经有 2D 直线 `MoveTo(destination, stoppingDistance)` 和“手动输入取消旧 MoveOrder”的既有正式闭包；这只能证明项目里已存在第一阶段基础点击移动链路，不等于当前缺口已经允许继续进入实现态。

## 一级缺口取证优先级

| 一级框架缺口 | 当前最优先要找的参考特征 | 次优先可接受特征 | 明确不接受 |
| --- | --- | --- | --- |
| 单机/本地 2D 导航 Provider | 直接 2D 运行时代码，含落点合法性、导航取消和停止半径 | 官方包或成熟插件的 2D 运行时样板，只要能映射到当前正式闭包 | Mirror、3D NavMeshAgent、CharacterController 绑定实现 |
| 2D 点击移动执行闭包 | 直接 2D 点击寻路代码，含 UI 遮挡、最近合法落点和路径取消 | 2D demo 样板，但必须能抽出正式闭包而非整套 manager | 只有设计说明、只有视频、只有 3D 鼠标寻路 |
| 单机/本地场景实例宿主参考 | 单机都能成立的实例模板与运行时宿主 | 只要职责明确，也可接受不是开放世界项目但场景组织成熟的参考 | 纯 MMORPG 副本流、Mirror Scene/Interest 强绑定 |
| 单机/本地出生点分流宿主参考 | 明确把分流规则、默认回退和失败处理挂在正式宿主上 | 可以不是职业分流，但必须是“按入口/模板/条件分流”这类正式闭包 | 把分流散在传送门脚本、地图脚本、角色 Prefab if/else |

## 二级缺口总表

> 二级缺口不是“下一步直接做”，而是“依赖一级缺口补齐后才能继续复核”的派生问题。

| 二级缺口 | 依赖的一级缺口 | 当前已知证据 | 当前口径 |
| --- | --- | --- | --- |
| 控制对象与世界穿越目标统一 | 场景实例宿主、出生点分流宿主 | 当前 `MapSystem/Teleporter` 仍只对 `PlayerSystem.PlayerInstance` 建模 | 只能登记，不能先把世界穿越目标切到 `currentControlledCharacter` |
| 超距后自动靠近再施法/交互 | 2D 导航 Provider、点击移动执行闭包 | `PlayerSkills.cs`、`Monster.cs` 证明“超距后先靠近到可执行半径，再续接动作”是成熟规则 | 只能登记，不能先把“移动后续接动作”硬写进技能/交互/控制器 |
| 传送入口条件 | 场景实例宿主、出生点分流宿主 | `Portal.requiredLevel` 只证明“入口可以有条件” | 只能登记，不能先把等级条件或其它入口条件硬编码进 `Teleporter` |

## 当前已融合与仍未吸收

### 已融合/补强

- `Movement.Reset / Warp / IsValidSpawnPoint / NearestValidDestination` 的合同已融合到 `Movable`
- `Navigate(destination, stoppingDistance)` 的停止半径合同已融合到 `Movable`
- `PlayerNavMeshMovement.MoveWASD()` 的“直接方向驱动取消旧导航路径”规则已融合到 `Movable.SetMovementDirection(...)`
- `Database.CharacterLoad()` 的“失效保存位置回退到正式出生点”规则已融合到 `MapSystem.LoadDataBlock(...)`
- `Portal.cs` 的“子碰撞体回溯正式玩家实体”规则已融合到 `Teleporter.OnTriggerStay2D(...)`

这些条目不是重复搬运 `uMMORPG` 的同职责实现；当前项目仍以已有 `Movable / MapSystem / Teleporter` 为正式闭包，只把源码证据中可脱离 Mirror、3D NavMesh 和 MMORPG 业务的规则补进去。

### 当前只登记，不吸收

- 导航 Provider 其余部分
- `uMMORPG NavMeshMovement/RegularNavMeshMovement` 的可运行导航实现
- 点击移动完整执行链
- 超距后自动靠近再施法/交互
- `Instance.cs` 的实例宿主运行时闭包
- `GetStartPositionFor(...)` 的出生点分流运行时闭包
- `Portal.requiredLevel` 对应的正式入口条件闭包

补充：

- 对 `uMMORPG` 来说，`MovementSystems` 目录当前已经不需要再反复复核；目录级裁决已经固定。
- 后续若没有新的 `uMMORPG` 文件进入视野，优先动作应是补外部新参考，而不是回头重审这批 `NavMesh / CharacterController / Mirror` 运动实现。

## 后续补参考时的最小记录格式

当你后面提供新的参考来源时，默认按下面 6 项补证据：

1. 参考路径
2. 命中的一级缺口
3. 直接可搬的源码文件
4. 不能直接搬的绑定条件
5. 准备落到 `GameCore` 的正式闭包位置
6. 验收口径：这次是只登记，还是可以直接吸收
