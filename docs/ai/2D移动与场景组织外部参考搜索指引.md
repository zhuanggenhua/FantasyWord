# 2D移动与场景组织外部参考搜索指引

> 本文只服务一件事：当本机现有参考池已经扫到当前边界后，后续该去外部找什么类型的源码。
> 它不是实现计划，也不是 intake 台账；它只负责帮你把“找什么参考最值钱”说清楚。

补充边界：

- 本文只服务 `2D 移动与场景组织` 的 4 个一级缺口。
- 它不处理开放世界模拟层本身；区域/Cell、队伍、派系、AI 日程、经济和局部模拟是否开工，是另一层长期架构问题。
- `uMMORPG` 在这里也只算局部证据源，不是第四个总框架候选。

## 当前前提

- 本机现有参考池已复核到当前边界：
  - `uMMORPG` 仍只提供局部源码证据；
  - `uMMORPG/MovementSystems` 目录当前已经扫到边界：`NavMeshMovement.cs / RegularNavMeshMovement.cs` 只算 `NavMesh + Mirror` 负证据，`PlayerCharacterControllerMovement.cs + CharacterController2k.cs` 只算 `Mirror + 3D CharacterController` 负证据；真正还保留局部移动参考价值的，只剩 `Movement.cs` 与 `PlayerNavMeshMovement.cs`；
  - `uMMORPG PlayerCharacterControllerMovement.cs + CharacterController2k.cs` 已正式判退：它是 `Mirror + 3D CharacterController` 玩家运动体系，不是当前项目要的 2D 导航/点击移动闭包；
  - `TopDownEngine` 仍只提供动作表现层和单场景入口样板；
  - `2DRPGEngine NodeCanvas Pathfinding` 已确认只是 `NavMeshAgent` 包装；
  - 本机 `Assets` 范围内未发现 `AstarPath / GridGraph / Seeker / AIPath / RichAI / AILerp / CharacterPathfinder2D / MouseDrivenPathfinderAI2D` 这类新闭包。
- 因此，后续要补：
  1. `单机/本地 2D 导航 Provider`
  2. `2D 点击移动执行闭包`

  这两个一级缺口，默认需要**外部新参考**。
- 后两个一级缺口：
  3. `单机/本地场景实例宿主参考`
  4. `单机/本地出生点分流宿主参考`

  当前本机只有局部证据，仍欢迎外部新参考补闭包。

## 使用方式

后面你找外部参考时，优先按下面 4 组来筛：

1. 命中哪个一级缺口
2. 是否真有源码，不是视频或宣传页
3. 是否避开 `Mirror / NavMeshAgent / CharacterController / 3D only`
4. 是否能抽出当前项目可直接搬的正式闭包

补充：

- RTS 参考可以用，尤其是单位导航、点地命令、路径跟随、路径取消、停止半径、队伍/单位共用导航真相这些代码。
- 3D 参考也可以用，但要拆开看：网格/图搜索/流场/路径跟随这类维度无关逻辑可以映射；强绑 `NavMeshAgent`、3D 射线、3D Collider、CharacterController 或高度语义的部分只能当职责样板。
- 当前项目确定会做有限联机，但当前阶段不实现联机，所以网络框架不是本阶段实现目标；若参考强绑 Mirror、服务器权威或网络对象生命周期，默认只登记证据，不直接搬。
- 就算外部仓库第一眼看起来很强，也必须先过 `movement-scene-reference-intake.md` 的 intake；在 intake 裁决明确落到 `直接吸收` 前，一律只算候选证据，不进入实现。

## 看到什么算“高优先级外部参考”

如果一个外部仓库同时满足下面 4 条，优先级默认很高：

1. 命中 4 个一级缺口中的一个，而且不是擦边球
2. 有本地可读运行时代码，不只是 README、视频或宣传页
3. 能把“可直接搬部分”和“强绑定部分”明显拆开
4. 看起来能直接落到现有 `GameCore` 正式闭包，而不是逼你再造一个宿主或兼容层

## 看到什么算“即使很像也先别浪费时间”

下面这些来源，就算看起来名字很像，也默认优先级很低：

- 3D `NavMesh` 鼠标寻路 demo
- `Mirror + 3D CharacterController` 玩家移动体系
- 已经在本机判退过的 `uMMORPG MovementSystems` 负证据文件
- 只给编辑器网格工具、不带运行时寻路
- 只有“副本入口”或“场景切换入口”的脚本
- 只有一组出生点和一个 `int index`
- 强依赖另一整套 manager / UI / 输入 / 生命周期
- 看完整个仓库仍找不到正式宿主类

再补 4 类常见假阳性：

- 只有安全区 trigger、区域 gizmo 或 `inSafeZone` 这类局部布尔标记
- 只有死亡后弹复活按钮的 UI
- 只有怪物/NPC 自己记 `startPosition + respawnTime` 的自复活状态机
- 只有一张名字很像开放世界入口的 `World.unity` 大场景，但看不到实例宿主、区域宿主或出生点分流宿主源码

这些内容最多只能证明：

- 局部区域规则可以靠 trigger 给实体打状态标记
- 最近出生点复活或实体自复活可以作为局部行为成立

它们不能单独关闭：

- `单机/本地场景实例宿主参考`
- `单机/本地出生点分流宿主参考`

补充：

- 对 `uMMORPG` 来说，后续不必再把 `NavMeshMovement.cs / RegularNavMeshMovement.cs / PlayerCharacterControllerMovement.cs / CharacterController2k.cs` 当成新发现提交。
- 这几份当前已经是固定负证据；若没有新的 `uMMORPG` 文件进入视野，优先去找外部新仓库，而不是回头重翻它的旧移动目录。

## 缺口 1：单机/本地 2D 导航 Provider

### 最值钱的仓库特征

- 明确是 `2D top-down`
- 有运行时代码，不只是编辑器工具
- 玩家和 NPC 共用同一导航能力
- 能回答：
  - 当前是否在移动
  - 目标是否可落地
  - 不可达时如何修正
  - 停止半径
  - 导航取消

### 优先关键词

- `unity 2d top down pathfinding grid movement source`
- `unity 2d click to move pathfinding github`
- `unity tilemap pathfinding 2d runtime github`
- `unity 2d ai path grid graph topdown`
- `unity 2d navigation provider topdown`

### 命中后最先看的源码名字

- `Movement`
- `Navigation`
- `Pathfinder`
- `GridNavigation`
- `PathRequest`
- `AgentMover`
- `PathfindingSystem`

### 直接排除

- `Mirror`
- `NavMeshAgent`
- `CharacterController`
- 只支持 3D 地面
- 只有接口，没有运行时代码

## 缺口 2：2D 点击移动执行闭包

### 最值钱的仓库特征

- 同时覆盖：
  - 鼠标/触摸点地
  - UI 遮挡
  - 目标修正
  - 路径取消
  - 到达停止距离
- 最好已经和 WASD/摇杆共存
- 不是单纯 `MoveTowards` 或 `lerp`

### 优先关键词

- `unity 2d click to move topdown github`
- `unity 2d point and click movement tilemap source`
- `unity 2d mouse move player pathfinding source`
- `unity topdown click move wasd switch github`
- `unity 2d touch click movement pathfinding`

### 命中后最先看的源码名字

- `ClickToMove`
- `MouseMovement`
- `PointAndClick`
- `TouchMovement`
- `PathToCursor`
- `MoveToPointer`
- `PlayerInputMovement`

### 直接排除

- 只有 `ScreenPointToRay`
- 只有 3D 地面射线
- 只有输入脚本，没有路径执行层
- 只有 demo 场景，没有正式运行时代码

## 缺口 3：单机/本地场景实例宿主参考

### 最值钱的仓库特征

- 明确存在“实例模板”或“实例运行时宿主”
- 不是只有传送门
- 能看见：
  - 实例入口
  - 实例归属
  - 实例边界
  - 实例内出生点
  - 离场清理
  - 实例运行时定位/重建规则

### 优先关键词

- `unity topdown instance dungeon system source`
- `unity single player dungeon instance runtime github`
- `unity scene instance template spawn points github`
- `unity procedural dungeon instance host source`
- `unity session instance world area runtime`

### 命中后最先看的源码名字

- `Instance`
- `DungeonInstance`
- `SceneInstance`
- `AreaInstance`
- `InstanceManager`
- `ZoneInstance`
- `RuntimeDungeon`

### 直接排除

- 只是一对传送门
- 只是“建副本后把人传进去”的入口脚本
- 强绑 `Mirror`
- 强绑网络实体清理
- 强绑 `NavMeshSurface`
- 只有安全区 trigger / 区域 gizmo，没有实例宿主
- 只有产品型 `World.unity` 场景混放，没有实例运行时宿主类

## 缺口 4：单机/本地出生点分流宿主参考

### 最值钱的仓库特征

- 分流规则挂在正式宿主，不散在多个脚本里
- 明确支持至少一种：
  - 地图入口分流
  - 模板入口分流
  - 条件入口分流
- 能看见：
  - 默认回退
  - 分流失败处理
  - 入口点索引或入口点标识

### 优先关键词

- `unity spawn routing system source`
- `unity point of entry system scene spawn github`
- `unity topdown entry point spawn manager`
- `unity checkpoint entry point routing source`
- `unity scene transition spawn point index github`

### 命中后最先看的源码名字

- `SpawnRouter`
- `EntryPoint`
- `PointOfEntry`
- `SpawnManager`
- `SpawnResolver`
- `StartPosition`
- `RespawnPointManager`

### 直接排除

- 分流写在传送门脚本里
- 分流写在角色 Prefab 初始化里
- 分流散在多个地图脚本 if/else
- 只是一组出生点数组，没有正式宿主
- 只有“死亡后点击复活”UI
- 只有怪物/NPC 自己的自复活状态机

## 现在最值得你优先找的顺序

1. `单机/本地 2D 导航 Provider`
2. `2D 点击移动执行闭包`
3. `单机/本地出生点分流宿主参考`
4. `单机/本地场景实例宿主参考`

理由：

- 前两个一级缺口已经确认本机参考池没有新闭包；
- 后两个虽然本机有局部证据，但还不足以直接搬；
- 点击移动、超距自动靠近、控制组穿越，都会先卡在前两个缺口上。
