## 1. `Movement.cs`

来源：

- `C:\Gamedev\Unity\Engine\2dmmorpg\uMMORPG Remastered - MMORPG Engine [2.41]\Assets\uMMORPG\Scripts\Movement.cs`

### 摘录结论

这份源码最有价值的不是具体实现，而是它把“移动能力”压成了一组独立合同，而不是塞回 `Player` 或控制器。

当前能直接确认的抽象入口有：

- `GetVelocity()`
- `IsMoving()`
- `SetSpeed(float speed)`
- `LookAtY(Vector3 position)`
- `Reset()`
- `Warp(Vector3 destination)`
- `CanNavigate()`
- `Navigate(Vector3 destination, float stoppingDistance)`
- `IsValidSpawnPoint(Vector3 position)`
- `NearestValidDestination(Vector3 destination)`
- `DoCombatLookAt()`

### 对当前项目真正有用的地方

| 类型 | 结论 |
| --- | --- |
| `设计模式` | 它证明“导航、传送、落点合法性、停止半径、战斗朝向”应从具体控制器中拆出来，成为统一移动合同 |
| `软件工程` | 它证明玩家、NPC、技能、传送、读档恢复不该各自维护一套移动判断 |
| `易用` | 只要合同统一，后面玩家/NPC/控制组才能复用一套移动语义，而不是每个控制器自己拼 |

### 当前可抽取的证据点

- `Reset / Warp / IsValidSpawnPoint / NearestValidDestination` 这一类“移动真相层应该回答什么”的合同口径
- `Navigate(destination, stoppingDistance)` 里的停止半径语义
- `CanNavigate()` 和 `DoCombatLookAt()` 这类“能力是否可用”的边界意识

### 当前不能直接搬

- `Movement : NetworkBehaviour`
- 整个 `Mirror` 生命周期
- 任何默认把导航实现建立在 `NavMeshAgent` 之上的假设

### 当前结论

`Movement.cs` 当前最适合被当成**合同级参考源**，而不是实现级来源。

## 2. `PlayerNavMeshMovement.cs`

来源：

- `C:\Gamedev\Unity\Engine\2dmmorpg\uMMORPG Remastered - MMORPG Engine [2.41]\Assets\uMMORPG\Scripts\MovementSystems\PlayerNavMeshMovement.cs`

### 摘录结论

这份源码当前最值钱的是两条成熟规则，不是它整套实现：

1. `MoveWASD()` 开始时会先 `agent.ResetMovement()`，也就是**直接方向输入优先于旧路径**
2. `MoveClick()` 里点击地面后，会先求 `NearestValidDestination(hit.point)`，也就是**点击目标应先修正到最近合法落点**

此外它还证明点击移动至少包含以下职责：

- 地面命中
- UI 遮挡拒绝
- 点击目标修正
- 目标指示器更新
- 点击路径下发
- 旧路径取消
- casting / stunned 时的 pending destination

### 对当前项目真正有用的地方

| 类型 | 结论 |
| --- | --- |
| `设计模式` | 点击移动不该只是输入脚本里的一次 `MoveTowards`，而应是一条正式执行链 |
| `软件工程` | “手动输入取消旧路径”“最近合法落点”“停止半径”这些规则应在同一正式闭包里，不应散进 UI、相机、控制器和技能系统 |
| `易用` | 玩家会直觉地认为“点到不可走的墙边也应尽量走到最近合法处”，这条规则成熟且可复用 |

### 当前可抽取的证据点

- `MoveWASD()` 对旧路径的取消优先级规则
- 点击后先做 `NearestValidDestination(...)` 的规则
- “点击移动是一整条正式闭包，不是输入脚本小功能”的职责拆分依据

### 当前只能当证据

- `MoveClick()` 这一整段本体，因为它强绑：
  - `Camera.ScreenPointToRay`
  - 3D `Physics.Raycast`
  - `NavMeshAgent`
  - `Mirror` 玩家状态
  - `PlayerIndicator`

### 当前明确不该搬

- `Input.GetAxis / GetMouseButtonDown` 这一套直接输入接法
- `NavMeshMovement` 体系
- `NetworkNavMeshAgentRubberbanding`

### 当前结论

`PlayerNavMeshMovement.cs` 当前是**规则级强证据源**，不是当前项目可直接复制的 2D 点击移动实现。

## 3. `Instance.cs`

来源：

- `C:\Gamedev\Unity\Engine\2dmmorpg\uMMORPG Remastered - MMORPG Engine [2.41]\Assets\uMMORPG\Scripts\Instance.cs`

### 摘录结论

这份源码最重要的价值是把“实例宿主”该负责什么说清了。

当前能直接确认它承担的职责有：

- `entry`
- `requiredLevel`
- `bounds`
- `instanceLimit`
- `instances`
- `spawnPoints`
- `template`
- `partyId`

补充：

- `spawnPoints` 缓存的是 `InstanceSpawnPoint`
- `InstanceSpawnPoint.cs` 本体只有一个 `NetworkIdentity prefab` 字段
- 也就是说，它不是“实例内出生点逻辑宿主”，而是“创建实例时要顺手生成哪些网络 prefab”的标记组件

以及一套实例生命周期职责：

- `OnValidate()` 缓存出生点
- `Awake()` 计算边界
- `Update()` 周期性检查实例内玩家
- 不属于实例归属的玩家会被踢回正式出生点
- 实例无人后销毁
- `OnDestroy()` 清理模板索引与网络实体
- `CreateInstance(...)` 负责按模板创建实例、设置归属、定位实例、生成实例内对象

### 对当前项目真正有用的地方

| 类型 | 结论 |
| --- | --- |
| `设计模式` | 实例入口、归属、边界、实例内出生点、销毁和清理应归同一个正式宿主，不应散在传送门、地图脚本或角色脚本里 |
| `软件工程` | 没有宿主，实例定位、归属验证、离场清理、回退入口一定会分叉 |
| `易用` | 策划只有在实例宿主存在时，才能明确配置“从哪进、谁能进、离开后回哪、实例何时清掉” |

### 当前可抽取的证据点

- “实例宿主必须显式存在”的结论
- 实例宿主至少要拥有：入口、归属、边界、实例内出生点、实例清理策略
- 实例运行时位置应由宿主统一稳定决定，而不是由入口脚本临时算

### 当前只能当证据

- `CreateInstance(...)` 的大部分流程，因为它强绑：
  - `Mirror`
  - `partyId`
  - 网络实体生成/销毁
  - `NavMeshSurface`
  - 3D 边界与空间偏移

### 当前明确不该搬

- `partyId -> instance` 这一套 MMORPG 副本归属模型
- `NetworkServer.Spawn/Destroy`
- `SpatialHashingInterestManagement`
- 把 `InstanceSpawnPoint` 误判成当前项目已经找到了单机实例内出生点宿主

### 当前结论

`Instance.cs` 当前是**宿主职责级强证据源**，能证明该有实例宿主，但不能直接作为当前单机实例实现。

## 4. `NetworkManagerMMO.GetStartPositionFor(...) + NetworkStartPositionForClass.cs`

来源：

- `C:\Gamedev\Unity\Engine\2dmmorpg\uMMORPG Remastered - MMORPG Engine [2.41]\Assets\uMMORPG\Scripts\NetworkManagerMMO.cs`
- `C:\Gamedev\Unity\Engine\2dmmorpg\uMMORPG Remastered - MMORPG Engine [2.41]\Assets\uMMORPG\Scripts\NetworkStartPositionForClass.cs`

### 摘录结论

这一组源码最重要的价值是：**出生点分流应归正式宿主，而不是散在入口脚本里。**

当前能确认的行为是：

- 宿主会遍历 `startPositions`
- 如果命中 `NetworkStartPositionForClass.playerPrefab.name == className`，则走专用出生点
- 如果找不到专用出生点，就回退到默认 `GetStartPosition()`
- 创建角色时，会直接调用这条宿主逻辑决定初始位置
- 进一步按 `2026-06-17` 复核，直接调用点就在 `CreateCharacter(...) -> player.transform.position = GetStartPositionFor(player.className).position`
- 同轮对 `World.unity` 复核，还能直接看到 `Respawn & Spawn for Warrior`、`Respawn & Spawn for Archer` 这类职业出生点对象

### 对当前项目真正有用的地方

| 类型 | 结论 |
| --- | --- |
| `设计模式` | 出生点分流应归正式宿主，不能散在 `Teleporter`、`MapInfo`、`PlayerSystem` 的 if/else |
| `软件工程` | “专用入口优先，默认入口兜底”必须是统一规则，不然地图入口、角色模板入口和控制组入口会各写一套 |
| `易用` | 策划能明确配置“专用入口”和“默认入口”的关系，而不是靠脚本猜 |

### 当前可抽取的证据点

- “分流逻辑应在正式宿主里”的架构结论
- “找不到专用出生点时必须有默认回退”的规则
- 专用入口和默认入口共存的配置思路

### 当前只能当证据

- `GetStartPositionFor(...)` 的具体实现，因为它强绑：
  - `Mirror` 的 `NetworkStartPosition`
  - 角色创建流
  - `playerPrefab.name == className` 这类 MMORPG 职业分流模型
  - `World.unity` 里的职业出生点对象组织

### 当前明确不该搬

- 把当前项目出生点分流绑定到角色创建阶段
- 把 `Mirror` 出生点体系直接搬回 `GameCore`
- 把 `Respawn & Spawn for Warrior/Archer` 这种职业对象布局误读成单机地图入口或世界穿越入口宿主

### 当前结论

这组源码当前是**分流宿主职责级强证据源**，但它证明的是“Mirror 角色创建流里的按职业出生点分流”，不是当前项目可直接吸收的单机/本地出生点分流实现。

## 7. `Assets/Plugins/AStar 2D Grid Pathfinding`

来源：

- `C:\Gamedev\Unity\Project\FantasyWord\Assets\Plugins\AStar 2D Grid Pathfinding\AStar\Needed Scripts\AStarPathfinding.cs`
- `C:\Gamedev\Unity\Project\FantasyWord\Assets\Plugins\AStar 2D Grid Pathfinding\AStar\Example 1\Scripts\DemoGrid.cs`

- `C:\Gamedev\Unity\Project\FantasyWord\Assets\Plugins\AStar 2D Grid Pathfinding\AStar\Example 3\Scripts\MinimalExample.cs`

### 摘录结论

这组源码当前最有价值的点是：它已经证明“**单机/本地 2D 求路 + world/grid 映射 + 路径点跟随**”可以脱离 `NavMeshAgent` 和 `Mirror` 成立，但还没有形成当前项目能直接搬的正式导航闭包。

当前能直接确认的事实：

- `AStarPathfinding.cs` 提供两组正式入口：
  - `GeneratePath / GeneratePathSync(..., bool[,] walkableMap, ...)`
  - `GeneratePath / GeneratePathSync(..., float[,] costMap, ...)`
- `MinimalExample.cs` 直接证明：
  - 纯 `bool[,]` 可走图可以独立求路
  - 纯 `float[,]` cost map 可以独立求路
  - async 调用返回 `(int, int)[]` 路径点
- `DemoGrid.cs` 与 `GridManager.cs` 都已经提供 demo 级：
  - `world -> grid`
  - `grid -> world`
  - walkable/cost map 生成
  - 点格取样
- `randomPather.cs` 证明路径点跟随本身不依赖 NavMesh，而是“求出路径后按点逐段前进”
- `PathFindTest.cs` 证明点击取格和画路径在 2D 里可以成立，但它当前只是“点两个格子高亮路径”的测试脚本，不是正式玩家点击移动闭包

### 对当前项目真正有用的地方

| 类型 | 结论 |
| --- | --- |
| `设计模式` | 路径计算、grid 宿主、world/grid 换算和路径点跟随可以拆开，而不是必须绑成 `NavMeshAgent` 一体化实现 |
| `软件工程` | 它证明“算法层”和“运行时宿主层”可以分离；当前项目若真吸收，也应继续落回现有 `Movable / PlayerController` 正式闭包，而不是整包搬 demo 宿主 |
| `易用` | `bool[,]` 与 `float[,]` 双入口说明它既能表达“能不能走”，也能表达“哪里更难走”，对后续地形代价或队伍移动有价值 |

### 当前可抽取的证据点

- `AStarPathfinding` 的 2D 网格 A* 算法入口形状
- `bool[,] walkableMap` / `float[,] costMap` 这两种输入模型
