# 框架最终裁决

> 用途：作为 `FantasyWord` 地基的默认引用入口。
> 如果只看一份文档，先看这份。

## 先说判法

这次不再问“哪个框架整体更强”，而是先问“这个系统到底属于哪一种职责”。

只按三项标准裁决：

- `设计模式`：职责是否清楚，系统边界是不是围绕真实问题切开，还是把多种问题堆进同一个 manager。
- `软件工程`：是否只有一个真相源，是否容易验证，是否能控制 Unity 序列化、Prefab 接线和回归面。
- `易用`：策划和开发能否直接靠 Inspector、Prefab、ScriptableObject 和少量代码稳定搭内容。

先识别职责，再选边：

| 职责类型 | 正确拥有者判断 |
| --- | --- |
| 长期世界状态 | 谁最擅长表达“世界现在是什么”，谁赢 |
| 瞬时角色执行与手感 | 谁最擅长表达“角色这一秒怎么动、怎么打、怎么受击”，谁赢 |
| 通用基础工具 | 谁最擅长减少重复工具代码，又不抢玩法语义，谁赢 |
| 开放世界长期模拟 | 如果三方都没有完整答案，就由 `FantasyWord` 自建 |

所以，比较的不是“总冠军”，而是：

- 谁适合当 `世界规则真相`
- 谁适合当 `动作执行真相`
- 谁适合当 `工具真相`
- 哪一层必须由项目自己建立

这里还要补一条，避免把“系统”和“业务”混成一类：

- `框架机制`：生命周期、输入根、存档文件层、对象池、事件/通知边界、UI 宿主、地图宿主。
- `领域框架模块`：背包、任务、对话、属性、能力、装备、制作这类可跨具体项目复用的系统闭包。
- `具体业务内容`：某把剑、某个药水、某个任务链、某个商店、某套菜单文案、某个 NPC 流程。

因此：

- `InventorySystem / JournalSystem / DialogueSystem / Stats / Ability` 这类“系统”本身可以属于框架的一部分。
- 但这些系统里绑定的具体菜单流程、具体内容资产、具体产品假设，不自动等于当前必须保留的地基。
- 当前要裁掉的重点不是“所有 system 都算业务”，而是“哪些 system 已经越过通用模块边界，开始夹带具体产品流程、具体 UI 栈和具体真相重复”。

补充边界：

- `uMMORPG Remastered - MMORPG Engine [2.41]` 不参与这张总裁决表。
- 它当前只作为 `2D 移动与场景组织` 的局部源码证据源使用。
- 它之所以容易被误读成“也许能当开放世界地基”，是因为源码里确实带有 `PartySystem / GuildSystem / SafeZone / Instance` 这类 MMO 组织脚本；但当前没有发现 `World / Cell / Faction / Economy / Base / Settlement / Region / Schedule` 这类开放世界模拟宿主闭包。进一步按 `2026-06-17` 复核，`SafeZone` 本体只是区域 trigger 标记，`UIRespawn` 也只是死亡后显示复活按钮的界面壳，玩家复活和怪物自复活仍分散在各自状态机里，没有统一 `Respawn` 或区域宿主。
- 因此它不能升格成第四个总框架候选，也不能被当成当前项目的开放世界基线。

### 三项标准怎么用

三项标准不是平均投票，也不是三列打分后简单求和。

正确顺序是：

1. 先看 `设计模式`
   先判断这个系统到底属于“长期世界状态”“瞬时角色执行”还是“通用工具”。
   如果系统分类都判错，后面分数再高也只是在错误赛道里比较。
2. 再看 `软件工程`
   判断它能不能成为该职责的正式真相源，特别是会不会顺带带入第二生命周期、第二输入根、第二 UI 栈或第二存档语义。
3. 最后看 `易用`
   在前两项成立的前提下，再决定谁更适合让策划和开发快速开始做游戏。

这套顺序直接推出一个结论：

- 本项目不应该存在“单一总冠军框架”。
- 因为 `长期世界状态`、`瞬时角色执行`、`通用工具` 本来就是三种不同问题。
- 试图让一个框架同时赢三种问题，最后通常得到的不是统一，而是错层接管。

以下都不是理由：

- `当前已经用了谁`
- `只是参考，不用正面对比`
- `都留着最稳`
- `先包一层以后再收`

## 直接回答

### 1. 现在有没有多余兼容层

结论：`没有，而且正式禁止继续造。`

理由不是“现在没搜到”，而是：

- `设计模式`：兼容层会把“正式入口是谁”重新搞模糊。读代码的人会看见项目层、插件层、兼容层三套入口，不知道哪套才是真相。
- `软件工程`：兼容层最容易把第二生命周期、第二输入根、第二 UI 栈、第二存档语义偷偷带进来。
- `易用`：表面上像“隔离风险”，实际上会把调用链拉长，阅读成本更高，调试更慢。

正式动作只有三种：

- `直接替换`
- `正式融合`
- `暂不动`

没有第四种“先包一层再说”。

### 2. `editor` 和 `core` 现在这样放合不合理

结论：`合理，而且现在不应该提前拆。`

#### 为什么 `Assets/Scripts/GameCore/Runtime` 合理

正确理由不是“它现在就在这里”，而是：

- `设计模式`：`GameCore` 当前承担的是“地基整合根”，不是“最终产品目录”。当世界规则、动作执行、工具吸收还在同一地基闭包里时，先拆成 `World/Characters/Combat/Presentation` 这类顶层目录，只会制造名字分层，不会得到真实分层。
- `软件工程`：迁移期最怕的是真相分叉。把运行时正式入口集中在 `GameCore/Runtime`，可以把序列化、Prefab 接线、场景宿主、系统入口和验证门禁压在同一个稳定根上，漏改面最小。
- `易用`：当前维护者只需要记住一句话: `正式运行时代码先看 GameCore/Runtime`。如果现在就拆顶层目录，读代码的人反而要先猜“这些目录里哪些已经是正式真相，哪些只是未来规划”。

一句话：`GameCore` 现在是整合根，不是美术化的产品目录。

#### 为什么 `Assets/Editor/GameCore` 合理

- `设计模式`：编辑器工具的职责是服务这套 runtime 闭包，不是玩法系统本身。
- `软件工程`：它天然服从 Unity `Editor` 编译边界，能直接阻断编辑器代码误进运行时程序集和玩家构建。
- `易用`：找 `EditorWindow`、`PropertyDrawer`、验证器和 AI 编辑器桥时，入口稳定清楚。

一句话：`Editor/GameCore` 是运行时地基的支撑边界，不是业务层。

#### 目录对照到参考源码时，正确读法是什么

| 参考目录 | 当前目录 | 为什么这样对照才对 |
| --- | --- | --- |
| `2DRPGEngine/Assets/Mythril2D/Core/Runtime/Scripts/Game`、`Database`、`Maps`、`Controllers`、`UI` | `Assets/Scripts/GameCore/Runtime/Game`、`Database`、`Maps`、`Controllers`、`UI` | 这批目录表达的是 `世界规则真相 + 正式运行时宿主`。它们在设计模式上本来就是同一运行时根，不该为了好看先拆成多个顶层产品目录。 |
| `2DRPGEngine/Assets/Mythril2D/Core/Editor/Scripts/Editors`、`PropertyDrawers`、`EditorWindows`、`Playtest` | `Assets/Editor/GameCore/Editors`、`PropertyDrawers`、`EditorWindows`、`Playtest` | 这批目录只服务 runtime 资产和验证入口。它们不表达玩法，所以应该跟着 `Editor` 编译边界走，而不是混回业务目录。 |
| `TopDownEngine/Common/Scripts/Characters`、`Weapons`、`Damage`、`MMFeedbacks` | `Assets/Scripts/GameCore/Runtime/Combat`、`Presentation`、`Animation` 内的正式吸收点 | 这批目录赢的是 `动作执行模式`，不是项目总目录。正确动作是把胜出的能力吸收到正式运行时闭包，而不是把 `TopDownEngine/Common` 整块当项目根。 |
| `TopDownEngine/Common/Scripts/Managers`、`GUI`、`ScriptsInputSystem`、`ScriptsCinemachine` | 不进入项目总根，只保留为第三方来源边界或局部参考源 | 这些目录把生命周期、输入、GUI、相机和关卡流程绑得太重。它们可以提供样板，但不该变成项目正式宿主目录。 |
| `Assets/Plugins/YokiFrame/Core/Runtime/PoolKit`、`Tools/SaveKit`、`InputKit`、`UIKit` | 项目运行时只保留调用点，不复制第二份工具实现 | 这批目录赢的是 `工具真相`。正确动作是直接用稳定工具入口，避免项目侧再造浅包装或并行工具层。 |

#### 为什么目录裁决不能照着 `TopDownEngine/Common` 走

- `设计模式`：`TopDownEngine/Common` 是一整套插件型动作生态，里面同时放了 `Characters`、`Managers`、`GUI`、`ScriptsInputSystem`、`ScriptsCinemachine`。这适合引擎插件分发，不适合当项目真相目录。
- `软件工程`：如果按它当项目总目录，`LevelManager/InputManager/GUIManager` 这类重量入口就会天然变成第二宿主，目录一开始就把错误生命周期合法化了。
- `易用`：它对“调动作样板”很顺手，但对“新人如何找到项目正式真相入口”并不顺手。项目代码阅读时，`GameCore/Runtime` 比 `Common/Scripts + 一堆 manager` 更直接。

### 3. 为什么不是某一边整体接管

结论：`因为三方赢的不是同一层。`

### 4. 为什么 `TopDownEngine` 必须进入正式裁决

结论：`因为它不是“可有可无的参考”，而是动作表现层的明确胜者。`

如果不把 `TopDownEngine` 拉进正式裁决，就会默认接受一个错误前提：

- 只要 `2DRPGEngine` 赢了世界规则层，它的动作层也可以顺便继续当正式实现。

这个前提不成立。

正确理由是：

- `设计模式`：`TopDownEngine` 在角色能力、移动、武器、命中、受击、反馈这一整段上，组件边界比 `2DRPGEngine` 更清楚，更像正式动作执行模型。
- `软件工程`：它把武器状态机、命中窗口、能力阻断、反馈触发点拆得更清楚，动作层回归面更容易限制。
- `易用`：它的 Inspector、Prefab 和反馈样板明显更适合快速把手感调到可玩。

也正因为如此：

- `TopDownEngine` 不能被降级成“灵感来源”。
- 它必须参加正式胜负。
- 它赢了就该替换薄动作实现，而不是只在文档里提一句“参考过它”。

#### 为什么不是 `2DRPGEngine` 整体接管

- `设计模式`：它擅长表达地图、任务、背包、角色数据、存档这些“长期世界状态”，但不擅长表达成熟的俯视角动作能力组合。
- `软件工程`：如果让它连动作层一起接管，世界真相虽然统一了，但动作执行会长期卡在偏薄的实现上。
- `易用`：做 RPG 数据很顺手，调武器、命中窗口、后摇、受击反馈不够顺手。

所以它应该赢 `世界规则层`，不该连 `动作表现层` 一起打包赢。

#### 为什么不是 `TopDownEngine` 整体接管

- `设计模式`：它擅长角色能力、移动、武器、命中、反馈，但它的 manager 体系把生命周期、输入、GUI、关卡流程绑得过重。
- `软件工程`：如果整体接管，就会把第二生命周期、第二输入根、第二 UI 根一起带进来，直接破坏单一真相源。
- `易用`：调动作和反馈非常顺手，但拿它承载 RPG 长期世界状态会变形。

所以它应该赢 `动作表现层`，不能顺带接管 `生命周期/输入/UI/世界规则`。

#### 为什么不是 `YokiFrame` 整体接管

- `设计模式`：它解决的是对象池、保存文件、输入重绑定、资源句柄、UI 缓存这类工具问题，不表达“世界是什么”。
- `软件工程`：它能让工具层更干净，但不能代替地图、任务、背包、角色成长、开放世界模拟的真相建模。
- `易用`：拿来做工具非常省事，拿来当玩法主框架会让所有玩法语义失焦。

所以它应该赢 `工具层`，不该升格成 `游戏主框架`。

## 正确框架

正确框架不是单边整体接管，而是四层分治：

| 层 | 正式拥有者 | 为什么它赢 |
| --- | --- | --- |
| RPG 世界规则层 | `2DRPGEngine` | 它最擅长表达地图、任务、背包、角色数据、存档这些长期世界状态 |
| 俯视角动作表现层 | `TopDownEngine` | 它最擅长表达角色能力、移动、武器、命中、受击和反馈这些瞬时执行问题 |
| 通用工具层 | `YokiFrame` | 它最擅长替换重复浅工具，又不抢玩法语义 |
| 开放世界模拟层 | `FantasyWord` | 三方都没有完整覆盖区域/Cell、队伍、派系、AI 日程、经济和局部模拟 |

一句话版本：

- `2DRPGEngine` 赢世界规则真相。
- `TopDownEngine` 赢动作表现真相。
- `YokiFrame` 赢工具真相。
- `FantasyWord` 自己补开放世界模拟真相。

## 系统级正式裁决

| 系统 | 正式拥有者 | 为什么选它 | 为什么不选另一边 |
| --- | --- | --- | --- |
| 启动与系统生命周期 | `2DRPGEngine GameManager + AGameSystem` | 生命周期必须围绕世界规则宿主建立单一入口 | `TopDownEngine` 会顺带带入多 manager 体系；`YokiFrame` 架构层不表达 RPG 世界宿主 |
| 地图、检查点、传送、场景恢复 | `2DRPGEngine MapSystem` 为真相，吸收 `TopDownEngine` 关卡样板 | 地图名、检查点栈、传送与地图恢复本质上是长期世界状态 | `TopDownEngine LevelManager` 强在样板，不适合接管地图真相；`YokiFrame` 不提供这套语义 |
| 玩家数据、成长、装备位、技能槽 | `2DRPGEngine Hero/CharacterSheet/Stats` | 玩家长期数据必须和任务、背包、存档共用同一真相 | `TopDownEngine` 动作角色不该另存一套长期数据；`YokiFrame` 不竞争这一层 |
| 移动、动作能力、武器执行、命中、受击 | `TopDownEngine`，但吸收到 `GameCore` | 这是典型的瞬时执行问题，TopDown 的组件拆分和状态机更成熟 | `2DRPGEngine` 能接规则但执行偏薄；`TopDownEngine` 不能整体搬入以免带入第二生命周期 |
| 物品、背包、装备、制作、任务、对话 | `2DRPGEngine` | 这是 RPG 内容真相，不是动作样板问题 | `TopDownEngine` 更适合拾取/机关表现，不适合作真相；`YokiFrame` 也不表达玩法语义 |
| 存档 | `2DRPGEngine SaveDataBlock` 保语义，`YokiFrame SaveKit` 保文件层 | 世界状态聚合和文件承载本来就是两种职责 | 只用 `2DRPGEngine` 文件层偏薄；只用 `YokiFrame` 又没有 RPG 世界语义 |
| 输入 | `GameCore InputSystem` 保真相，`YokiFrame InputKit` 补重绑定 | 输入语义是玩法真相，重绑定是工具问题 | `TopDownEngine InputManager` 会制造第二输入根；只靠 `2DRPGEngine` 又缺成熟重绑定工具 |
| UI 宿主、菜单语义与缓存工具 | 当前正式宿主已经是 `YokiFrame UIKit`，并吸收仍有价值的 `2DRPGEngine` 菜单语义 | 大量 UI 需要统一面板生命周期、资源链、层级、焦点和缓存；UIKit 在工具深度上更适合做宿主，且宿主替换已落到正式运行时代码 | `TopDownEngine GUIManager` 不适合承载 RPG 菜单真相；`AUIMenu` 不能和 `UIPanel` 双栈并行 |
| 对象池、资源句柄、UI 缓存等通用工具 | `YokiFrame` | 这是纯工具层问题，YokiFrame 明显更深更完整 | `2DRPGEngine` 和 `TopDownEngine` 在这层都没有足够优势 |
| 开放世界模拟 | `FantasyWord` 自建 | 这是项目目标能力，不是现成三方里谁略像一点就能接管 | 三方都没有完整答案，硬选只会得到伪架构 |

## 当前地基真正要解决的问题

当前阶段的重点不是“看到 Inventory / Quest / Dialogue 就先删”，而是先解决下面这些框架问题：

1. 生命周期层级是否合理
   现在 `AGameSystem` 全挂在 `GameManager` 下，而且 `GameManager` 暴露了大量静态快捷入口。这种形状比 TopDown 的多 manager 要轻，但仍偏“全局系统容器”，不够像分层清楚的 UE 风格宿主。
2. 真相所有权是否唯一
   现在最危险的不是有背包系统，而是同一职责未来可能出现双真相，例如 `Stats` vs `GAS AttributeSet`、`InputSystem` vs `TopDown InputManager`、`AUIMenu` vs `UIKit`、`MapSystem` vs `LevelManager`。
3. 系统层和实体层有没有分清
   例如背包、任务、属性到底应该是“全局宿主管理”、还是“角色持有数据、系统只协调流程”，这比先删不删某个系统更重要。
4. 静态访问是否过重
   当前 `GameManager.InventorySystem / JournalSystem / DialogueSystem / SaveSystem / PlayerSystem` 这种到处直取的方式，虽然比 TopDown 多 manager 好控，但仍然容易让依赖方向变平、测试边界变弱、模块耦合变宽。
5. UI 和玩法是否分层
   当前要防的是“系统真相和具体菜单流程绑死”，而不是误判成“只要有菜单就是业务，所以整个系统都不算框架”。

所以这轮地基搭建真正该问的是：

- 哪些系统保留为正式框架模块
- 哪些具体产品流程从这些模块里解绑
- 哪些静态快捷入口要收缩
- 哪些真相重复必须被禁止

## 模块动作

### 直接替换

| 模块 | 胜者 | 正式动作 |
| --- | --- | --- |
| 对象池 | `YokiFrame` | 项目侧浅池退场，统一切到 `GameObjectPoolService` |
| 武器执行层 | `TopDownEngine` | `2DRPG` 薄执行退场，改用 TopDown 风格武器状态机与命中窗口闭包 |
| 动作阻断模型 | `TopDownEngine` | 分散判断退场，统一收成能力权限合同 |
| 旧自造地基 | 无保留价值 | `Bootstrapper/RuntimeContext/ModuleInstaller/EventBus` 彻底退出正式口径 |

### 正式融合

| 模块 | 真相源 | 吸收来源 | 正式动作 |
| --- | --- | --- | --- |
| 地图、检查点、传送、重生 | `2DRPGEngine MapSystem` | `TopDownEngine` 边界、出生点、重生延迟、相机样板 | 保留地图真相，吸收关卡表现配置 |
| 生命数值与受击表现 | `RPG Stats` | `TopDownEngine` 击退、无敌帧、反馈 | 数值留 RPG，受击执行与反馈按 TopDown 模式吸收 |
| 存档 | `2DRPG SaveDataBlock` | `YokiFrame SaveKit` | `SaveDataBlock` 保世界语义，文件层改用 `SaveKit` |
| 输入 | `GameCore InputSystem` | `YokiFrame InputKit` | 保留玩法输入入口，`InputKit` 只做重绑定/保存/冲突查询 |
| 背包真相与角色操作目标 | 全局 `InventorySystem.items/money` | 当前控制角色边界 | 保留全局背包真相，装备/使用目标跟随正式当前控制对象 |
| 前台角色回退规则 | `PlayerSystem` | 各 UI / 表现 / 拾取调用点 | 把回退规则统一收回 `PlayerSystem` |
| UI 宿主、菜单语义与缓存工具 | `YokiFrame UIKit` 宿主能力 | `2DRPGEngine` 菜单语义 | 宿主替换已落到正式运行时代码，当前继续用非业务化面板 smoke、静态门禁和正式 prefab 证据守住唯一菜单 seam；旧菜单语义只保留已吸收到 `UIKitMenuPanelBase` 的部分 |

### 暂不动

| 模块 | 当前结论 | 原因 |
| --- | --- | --- |
| `TopDownEngine` manager、输入、GUI、Level 生命周期 | 永不升格为正式入口 | 会制造第二生命周期、第二输入根、第二 UI 根 |
| `YokiFrame` 架构层 | 不接管生命周期 | 工具框架不等于玩法框架 |
| UI 业务菜单全量迁 `UIKit` | 当前不再新增业务竖切样板，但正式宿主切换已完成 | 当前不能再拿背包、商店、死亡界面等具体业务流程做“再次证明 UIKit 可用”的迁移样板；后续工作集中在共享构件、旧资源与遗留口径清理 |
| 完整点击移动 / 自动靠近 / 控制组穿越 / 实例入口 | 暂不硬做 | 当前只保留第一阶段基础点击移动链路；完整能力仍缺正式一级参考，不允许靠临时实现推进 |
| 开放世界模拟空壳 | 暂不先写 | 没有明确拥有者、保存语义和验收场景时，空架构只会制造伪分层 |

## 不可退让项

- 禁止再用“当前已经用了谁”当理由。
- 禁止新增 `Compatibility`、`Adapter`、`Wrapper`、`Facade`、`FoundationSupport` 这类双轨层。
- 禁止让 `TopDownEngine` manager 接管正式生命周期、输入或 UI。
- 禁止让 `YokiFrame` 架构层接管正式游戏生命周期。
- 禁止把 `UIKit`、`GAS` 这种框架级替换写成“候选冻结”；不做具体业务迁移，不等于不做宿主和规则层替换。
- 禁止为了“看起来像最终产品目录”提前拆散 `GameCore`。
- 禁止在一级缺口没补齐前，硬做点击移动、自动靠近、实例入口或控制组穿越。

## 正式判词

这次裁决的正式判词可以压成四句：

- `2DRPGEngine` 不是总框架，它只是世界规则层胜者。
- `TopDownEngine` 不是样板附庸，它是动作表现层胜者。
- `YokiFrame` 不是可选点缀，它是工具层胜者。
- `FantasyWord` 不能继续假装三方里有人天然覆盖开放世界模拟层，这一层必须自己建立。
