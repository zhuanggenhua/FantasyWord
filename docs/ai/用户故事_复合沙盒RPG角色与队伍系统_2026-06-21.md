# 用户故事_复合沙盒RPG角色与队伍系统

## 适用范围

- 场景：开放世界探索、队伍控制、战斗、拾取、装备、变形、感染、奇特状态效果、区域模拟和确定会做的有限联机合作。
- 对象：玩家队伍角色、可招募角色、NPC、怪物、容器、地面物品、商店、制作站、未来访客可控制角色。
- 系统：角色闭包、能力/状态、背包/装备/快捷栏、控制权、命令链、存档、Mod 扩展和联机裁决边界。

## 最新用户结论

- 最后确认日期：2026-06-22
- 来源：用户进一步确认本游戏是单人主控、可有队友的俯视角开放世界 RPG；战斗目标接近《开拓者：正义之怒》的可暂停即时制，指挥模式接近《龙腾世纪》的战术模式，角色构筑以职业和技能树为核心并参考 ToME4 的视野、侦查、复杂状态和职业构筑；世界交互要有类似《塞尔达》式的涌现交互，开放世界 AI 和模拟参考 Kenshi，并需要 GOAP 或等价目标规划能力。用户补充确认地形是类似《红警》地图那种 2D 表现但存在地形抬高、坡道和高台差的系统，不是以多楼层室内空间为主的模型；这一系统缺少直接参考，必须专门找参考游戏思考实现方案。用户进一步纠正：第一阶段要做的是地基上的自然实现案例，而不是最小原型；如果某系统进入实现，就必须连带对应插件/框架一起进入，不能先做项目侧最小替身。没有行为树或正式等价 AI 框架时，绝对不做敌人 AI。
- 当前状态：已确认

## 玩家目标

- 玩家可以经营和控制一支由多个角色组成的队伍，而不是只扮演一个固定主角。
- 玩家可以像 CRPG 一样管理每个角色的装备、技能、背包、快捷栏、状态和成长。
- 玩家可以像 RTS 一样框选或多选角色，下达移动、攻击、拾取、交互、搬运、工作和战术命令。
- 玩家可以在 Roguelike 式奇特效果中获得、失去、保留或替换能力，例如变形、感染、丧尸化、诅咒、临时器官变化、阵营污染、技能突变和装备赋予能力。
- 玩家可以在失败后继续推进世界状态，而不是所有失败都回到读档或强制结束。
- 玩家主要扮演一个人，但可以招募或同行队友；平时可以单人探索，必要时进入指挥模式统一操作队友。
- 玩家可以在可暂停即时战斗中暂停、观察战况、下达命令、恢复时间流动，而不是固定回合制或纯即时动作。
- 玩家在第一阶段就需要面对最基本的敌人原型，而不是只有角色面板和技能资产；敌人应能移动、索敌、攻击、受击和死亡。
- 玩家可以与世界物件发生强规则交互，例如打开牢笼、搬运石头或尸体、力量足够时举起更重物体，长期目标允许树木、建筑或大型物件参与规则互动。
- 玩家可以通过职业和技能树形成构筑；职业提供稳定身份，技能树、装备、状态、突变和临时效果提供变化。
- 玩家可以使用视野、侦查、潜行或感知类能力提前发现危险、陷阱、资源、隐藏目标或敌对意图。
- 玩家在 2D 地形上仍能感受到类似 RTS 地图的高低差：坡道、高台、悬崖边、抬高地形和地形断层会影响移动、视野、射击、法术、交互、AI 和任务路径。

## 入口条件

- 玩家至少拥有一个可控角色。
- 队伍中可以存在多个角色，每个角色都应有独立身份、属性、装备、能力、状态和库存归属。
- 世界中可以存在非队伍 NPC、敌对单位、中立单位、容器、掉落物和可交互对象。
- 单机是默认入口；有限联机是确定目标，当前不要求网络框架存在。

## 主流程

1. 玩家选择一个角色或一组角色。
2. 玩家下达移动、攻击、拾取、交互、装备、使用物品、搬运、工作或施法命令。
3. 系统把玩家输入转成正式命令，再由对应角色按自身状态、能力、背包、装备、阵营和当前位置裁决能否执行。
4. 执行成功后，世界状态、角色状态、物品归属、任务进度、派系关系和表现反馈更新。
5. 执行失败时，玩家应看到明确反馈，例如距离不足、角色不能行动、背包已满、缺少能力、目标无效、状态被禁止或命令被覆盖。
6. 角色发生变形、感染、死亡、昏迷、控制权变化或奇特状态效果时，系统按规则保留一部分能力和物品，并替换、禁用或移除另一部分能力。
7. 保存游戏时，每个角色的长期身份、位置、背包、装备、快捷栏、能力来源、状态效果和关键 runtime 状态都应能被恢复。
8. 进入战斗后，玩家可以让时间继续流动，也可以暂停或切入指挥模式，为自己和队友下达移动、攻击、施法、使用物品、交互或撤退命令。
9. 世界 NPC 根据性格、背景、派系、需求、任务、危险和环境机会选择行动；普通日程可简单执行，复杂决策可升级为 GOAP 或 Utility AI。
10. 任务可以来自预设内容，也可以根据角色、地点、派系、世界状态和需求自动生成；自动生成任务必须仍能被存档、审计和回滚。

## 关键分支与失败路径

- 多角色背包：拾取物默认进入执行拾取的角色背包；玩家可以在角色之间转移物品；队伍资金可以是共享钱包，但不等于全队共享物品背包。
- 容器与尸体：箱子、尸体、地面物品堆和商店库存都是库存 owner，不能被混进玩家全局背包真相。
- 装备与能力：装备可以授予能力、修改属性、改变外观或限制行动；卸下装备后，对应能力和状态必须按规则撤回。
- 变形与感染：角色形态变化时，系统必须能表达“保留部分能力、替换部分能力、禁用部分装备、保留背包或转移背包”的不同规则。
- 队伍命令：多选角色时，命令可以批量下发，但每个角色独立裁决负重、距离、行动状态、能力权限和目标合法性。
- 可暂停即时战斗：暂停只冻结战斗时间和命令推进，不应破坏 UI、提示、音频淡入淡出、保存状态或对话/菜单宿主。
- 指挥模式：指挥模式可以扩大玩家对队友的操作权，但仍必须通过正式控制组和订单链，不允许 UI 直接改角色状态。
- 视野与侦查：看不见、没侦查到或被隐藏的对象不应被普通命令当成已知真相；侦查结果需要有可保存或可重新计算的边界。
- 2D 高低差：地形高度不是单纯渲染层级；它必须进入移动合法性、坡道连接、悬崖阻挡、视线遮挡、远程命中、范围效果、物体搬运和 NPC 寻路裁决。
- 涌现式交互：物体能否被举起、搬运、投掷、破坏或作为任务目标，取决于物体标签、重量、体积、状态、角色力量、工具和环境，而不是硬写到单个对象脚本。
- 元素反应：元素状态、地面、天气、物品材质和技能效果之间可以互相触发；该系统必须有正式规则层，不能散落在技能脚本里互相调用。
- 世界 AI：NPC 的性格和背景会影响目标选择，但具体内容、数值和叙事结果不得提前硬编码成固定剧情。
- 建筑损坏、火车轨道和建造系统：当前登记为实验项，先做可行性验证和系统边界，不提前承诺完整生产级实现。
- 敌人 AI：没有行为树或正式等价 AI 框架时，不进入实现；不能先写最小敌人脑补逻辑占位。
- AI 接管：角色失去玩家控制、访客掉线或被强制控制时，角色必须能回到 AI、等待、跟随或由房主/本地玩家接管。
- 失败继续：角色死亡、被俘、感染、重伤、丢失装备或队伍分散，不应默认等于游戏结束；是否结束取决于具体模式和存档规则。

## 玩家可见反馈

- 当前选中角色或控制组必须清楚可见。
- 背包、装备、快捷栏和角色面板必须显示当前查看的角色或容器，而不是默认读全局玩家背包。
- 多选时，UI 应显示队伍层面的命令入口和每个角色的关键阻断状态。
- 能力变化必须有可读反馈：新增、失去、被禁用、冷却、资源不足、状态阻断和形态限制。
- 物品转移、装备变化、拾取失败、容器打开、商店交易和制作消耗必须明确显示归属变化。
- 战斗暂停、恢复、慢速或指挥模式切换必须有明确反馈，玩家能看出当前时间状态和待执行命令。
- 视野、侦查、隐藏目标、地形高低差、可交互物体、元素状态和物体重量/可搬运性都需要在合适 UI 或世界提示中可读，但不能把大段规则说明常驻在主 HUD。
- NPC 的表情气泡、头顶对话、剧情式立绘对话和沉浸式短对白都属于正式表现目标；不同表现形式应消费同一套对话/事件/状态事实。

## 本轮重构口径

- 本轮重构应带上联机边界，但不接入联机实现。
- 必须带上的联机边界：命令入口、角色控制权、对象归属、物品归属、装备/使用物品裁决、伤害/状态裁决、存档写入边界、输入来源区分。
- 不带上的联机实现：不接入 FishNet 包，不创建网络目录，不写 RPC、同步字段、网络对象、网络权限空壳或网络 SDK 抽象。
- 正式口径：未来联机只是把远程输入送到房主裁决；房主仍调用同一套单机规则入口。

## 参考使用方式

- Kenshi：参考队伍沙盒、无固定主角、失败继续、派系、基地/生产、局部模拟和复杂世界状态；不照搬 3D 技术栈、UI 或具体系统数据。
- 博德之门：参考多角色 CRPG、角色背包、装备、技能、战术控制、互动选择和状态组合；不照搬 DnD 规则文本或具体 IP 内容。
- 开拓者：正义之怒：参考可暂停即时制战斗、队友命令、职业构筑、Buff/Debuff 层叠和战前战中策略；不照搬 Pathfinder 或 DnD 的具体授权规则文本、职业名、法术名或数值表。
- 龙腾世纪：参考战术模式、队友命令、战斗暂停下的目标选择和条件化队友行为；不照搬具体剧情、技能或 UI。
- ToME4：参考 Roguelike 式复杂能力、状态、突变、奇特效果、构筑和长期可扩展内容；不照搬具体职业、技能树、数值或内容文本。
- 塞尔达旷野/王国类开放交互：参考物理感强的物件互动、搬运、投掷、材质和环境组合；不把它理解为必须重做同等规模物理引擎。
- Red Alert / RTS 地图：参考抬高地形、高台、坡道、悬崖边、地形优势和 2D 地图上可读的高度差；不照搬纯 RTS 基地经营或兵种克制结构。
- Final Fantasy Tactics / Tactics Ogre：只参考局部战斗地图里的高度判定、高台优势和远程攻击差异；不等于项目必须改成回合制格子战斗。
- 用户提到的“奈斯启示录”：暂记录为种植、钓鱼和开放世界生活循环参考，具体作品名和系统细节待后续确认。
- RTS Starter Kit：参考选择、订单、群组、阵型和批量命令链；不作为角色能力、背包、存档或联机真相源。
- TopDownEngine：参考控制器、角色、能力组件、武器、受击、反馈、角色切换和角色库存模式；不接管 manager、输入根、GUI 或长期玩家数据。
- 2DRPGEngine / GameCore：保留世界规则、数据库、地图、任务、对话、存档和 RPG 数据语义；但全局背包口径需要按本用户故事重新评估。
- EX-GAS：作为能力规则、标签、冷却、消耗、状态效果和能力授予/移除的规则真相候选；动作执行仍应留在 GameCore 吸收后的角色执行闭包。
- GOAP / Utility AI：作为开放世界 NPC 目标选择、工作分配和复杂行为规划候选；不能在没有世界状态、行为代价和存档边界前直接接入成第二套 AI 宿主。

## 非目标 / 禁止猜测

- 不因为有 RTS 要素就立刻切 ECS。
- 不因为未来联机就提前接 FishNet、Mirror、NGO 或网络目录。
- 不把开放世界合作误解成 MMO、专用服务器持久世界、账号服或全地图多人 RTS 同步。
- 不把 TopDown 的 `InputManager`、`GUIManager`、`LevelManager` 或 `InventoryEngine` 整体接管为正式入口。
- 不把 2DRPG 的全局背包旧实现继续当作本产品目标的最终答案。
- 不把 Roguelike 奇特效果写成一次性硬编码特例；新增效果必须能通过规则层、稳定 ID、存档和 Mod 扩展边界表达。
- 不把可暂停即时战斗误解为纯回合制，也不把战术模式误解为另一个独立游戏模式；它们必须消费同一套时间、命令、AI 和能力规则。
- 不为“先跑起来”而先造最小敌人 AI、最小世界 AI 或最小交互替身；进入实现的系统必须带着对应正式框架/插件一起落地。
- 不因为要做涌现式交互就把所有物体都做成昂贵物理模拟；先建立物体能力标签、重量/体积/材质和交互规则合同。
- 不把 2D 高低差伪装成纯渲染排序；如果高度影响玩法，就必须进入正式地形数据、寻路、视野和交互规则。
- 不因为需要高低差就把整个游戏切成 3D NavMesh 或室内多楼层系统；先评估离散 elevation、坡道连接、悬崖阻挡和局部导航 provider。
- 不把建筑损坏、火车轨道或建造系统提前写进核心必做闭包；它们先按实验项走可行性阶段。

## 验证点

- 能创建至少两个角色，每个角色有独立背包、装备、快捷栏和能力来源。
- 拾取同一物品时，物品进入执行拾取角色的背包。
- 玩家能把物品从一个角色转移给另一个角色或容器。
- 角色变形或感染后，系统能演示保留部分能力、替换部分能力和禁用部分装备。
- 多选两个以上角色后，移动或交互命令能批量下发，并由每个角色独立裁决。
- UI 能在当前查看角色、控制组和容器之间切换显示库存与状态。
- 所有会改变世界的动作都有正式规则入口，未来可由本地输入、AI 或远程访客输入共同调用。
- 不存在为了联机预留而新增的网络包、网络目录、RPC 空壳或网络同步字段。
- 能暂停战斗、给队友下命令并恢复执行，命令仍走正式订单链。
- 至少一个可交互物体能按力量或状态裁决举起/搬运/放下/失败反馈。
- 至少一个视野或侦查场景能证明未知目标不会被普通命令当作已知事实。
- 至少一个 2D 高低差原型能证明高台、悬崖边和坡道会影响移动、视线和远程目标裁决。
- 至少一个 NPC 能按目标/需求/背景差异选择不同行为，并能保存关键状态。
- 至少一个元素反应样例能证明规则来自统一元素系统，而不是两个技能脚本互相硬调。
