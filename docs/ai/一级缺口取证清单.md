# 一级缺口取证清单

> 用途：把 `S3` 里的 4 个一级缺口从“知道缺什么”推进到“下一轮该带什么证据回来”。
> 本文只服务取证，不服务实现。
> 边界：本文只覆盖 `2D 移动与场景组织` 的 4 个一级缺口，不覆盖开放世界模拟层本身。

## 总规则

- 每个缺口都必须先补**直接源码证据**，再谈是否能吸收。
- 证据必须回答：`设计模式为什么成立`、`软件工程为什么不打穿真相源`、`易用为什么不是只对 demo 有效`。
- 如果候选源只解决其中一小段，但不能形成正式闭包，只能登记，不得提前开写。

## 缺口 1：单机/本地 2D 导航 Provider

### 这条缺口为什么存在

- `设计模式`：当前还没有一条正式闭包统一回答“角色是否能导航、是否在导航、如何取消导航、如何修正落点”。
- `软件工程`：如果先在 `PlayerController`、技能、交互、NPC 行为里各写一套导航入口，后面一定会出现多套移动真相。
- `易用`：策划和开发后续需要玩家/NPC/队伍都能复用同一导航能力，而不是每个控制器自己带一套寻路胶水。

### 新参考必须回答的问题

1. 角色当前是否具备导航能力，入口挂在哪
2. 当前是否在导航，状态如何暴露
3. 目标点不合法时，如何修正到最近合法点
4. 停止半径如何定义和复用
5. 手动输入、新导航请求、受击或技能如何取消旧导航
6. 玩家和 NPC 是否共用同一导航真相

### 直接判不合格的信号

- 强绑 `Mirror`
- 强绑 `NavMeshAgent` / `CharacterController`
- 只有接口，没有运行时代码
- 只对玩家成立，对 NPC 不成立
- 只解决“能走”，不解决取消、落点修正和停止半径

当前已确认的本机例子：

- `uMMORPG PlayerCharacterControllerMovement.cs + CharacterController2k.cs`
  - 强绑 `NetworkTransformBase`
  - 强绑 `CapsuleCollider + Rigidbody`
  - `CanNavigate()` 返回 `false`
  - 这条线应直接判退，不再当 2D 导航候选

### 当前候选源

| 候选源 | 当前价值 | 当前不足 |
| --- | --- | --- |
| `uMMORPG Movement.cs` | 已证明导航/传送/落点合法性应拆开 | 仍不是单机/本地 2D 正式导航闭包 |
| `Assets/Plugins/AStar 2D Grid Pathfinding` | 已提供本地 2D 网格 A* 算法、demo 级 world/grid 映射、点击取格与示例跟随，证明单机/本地 2D 求路可以脱离 `NavMeshAgent` 成立；`bool[,]` 与 `float[,]` 双入口还说明它支持可走图与 cost map 两种输入 | 当前还缺正式导航状态、取消、停止半径、UI 遮挡和 `Movable / PlayerController` 共用运行时；现有 grid 宿主仍是 demo 单例，点击链仍是旧 `Input` 测试脚本，暂时还不能直接映射到 `GameCore` |
| `Unity 2D/Tilemap 导航方案` | 可能补 2D 合法落点与路径能力 | 当前还只是类别，不是具体可搬闭包 |

### 下一轮最小取证包

1. 直接命中的源码文件路径
2. 导航状态读取方法
3. 导航取消方法
4. 合法落点修正方法
5. 停止半径处理点
6. 玩家/NPC 复用关系

### 什么时候才算“够直接吸收”

只有同时满足下面 4 条，才允许从“只登记”升级到“直接吸收”：

1. 已找到真实运行时代码，而不是接口、样板图或文档描述
2. 同一闭包里能同时回答：导航状态、导航取消、合法落点修正、停止半径
3. 玩家和 NPC 至少在设计上能共用同一导航真相，而不是只服务单个玩家控制器
4. 不需要为它新增 `NavigationProvider` 空壳或第二套移动宿主

## 缺口 2：2D 点击移动执行闭包

### 这条缺口为什么存在

- `设计模式`：点击移动不是“鼠标点一下就 MoveTowards”，它至少应是地面命中、UI 拒绝、落点修正、路径下发、到达判定和路径取消的一条正式链。
- `软件工程`：如果这条链先散进输入脚本、控制器、相机脚本和交互脚本，后面无法统一接“自动靠近后续接动作”。
- `易用`：只有形成完整点击移动闭包，策划才知道“点哪里能走、点 UI 为什么不走、什么时候算到达”。

### 新参考必须回答的问题

1. 地面命中怎么做
2. 点到 UI 如何拒绝
3. 目标点如何修正到最近合法落点
4. 新点击、WASD、摇杆如何取消旧路径
5. 到达判定是否支持停止半径
6. 目标指示器属于正式链还是纯表现

### 直接判不合格的信号

- 只有 3D 射线，不是 2D 闭包
- 只有鼠标点地逻辑，没有路径取消
- 只有 `MoveTowards/Lerp`
- 强绑单个玩家控制器，NPC 或自动靠近无法复用

当前已确认的本机例子：

- `uMMORPG PlayerCharacterControllerMovement.cs + CharacterController2k.cs`
  - 本体是 Mirror 本地玩家 + 3D CharacterController 运动体系
  - `Navigate(...)` 空实现
  - `NearestValidDestination(...)` 直接回原目标
  - 这条线应直接判退，不再当 2D 点击移动候选

### 当前候选源

| 候选源 | 当前价值 | 当前不足 |
| --- | --- | --- |
| `uMMORPG PlayerNavMeshMovement.cs` | 已证明“最近合法落点 + 手动输入取消旧路径”是成熟规则 | 仍强绑 `NavMeshAgent`、3D 射线和 Mirror 玩家流 |
| `TopDown MouseDrivenPathfinderAI3D.cs + CharacterPathfinder3D.cs` | 已证明点击路径职责应该集中到正式路径层 | 当前只有 3D 样板，没有 2D 点击寻路正式闭包 |

### 下一轮最小取证包

1. 地面命中源码
2. UI 遮挡判定源码
3. 合法落点修正源码
4. 路径取消源码
5. 停止半径到达源码
6. 正式落点建议：`Movable` / `PlayerController` / 独立正式闭包中的哪一个

### 什么时候才算“够直接吸收”

只有同时满足下面 4 条，才允许从“只登记”升级到“直接吸收”：

1. 已看到完整点击链，而不是只有鼠标点地或只有移动插值
2. 同一闭包里能同时回答：点地、挡 UI、目标修正、路径取消、停止距离
3. 这条链不强绑 3D 射线、`NavMeshAgent`、Mirror 玩家状态或单一 demo manager
4. 吸收后能落到现有正式闭包，不需要先造 `ClickMoveController` 或并行测试控制器

## 缺口 3：单机/本地场景实例宿主参考

### 这条缺口为什么存在

- `设计模式`：实例入口、归属、边界、实例内出生点和清理策略必须由正式宿主统一持有，不能散在传送门或地图脚本上。
- `软件工程`：如果没有宿主，后面实例定位、进入、离场清理和状态恢复一定会分叉。
- `易用`：策划需要知道“这个入口进入的是哪个实例、实例何时销毁、回到哪里”。

### 新参考必须回答的问题

1. 实例模板放哪
2. 实例归属由谁定义
3. 实例边界和实例内出生点挂在哪
4. 运行时如何稳定定位或重建实例
5. 离场清理和空实例清理归谁
6. 单机下也是否成立

### 直接判不合格的信号

- 只有传送门，没有实例宿主
- 强绑 `Mirror` 队伍副本 / Interest 管理 / 网络实体清理
- 强绑 3D 场景边界或 NavMesh 体系
- 只证明“能传进去”，不证明实例如何持续存在

### 当前候选源

| 候选源 | 当前价值 | 当前不足 |
| --- | --- | --- |
| `uMMORPG Instance.cs` | 已证明实例宿主至少要显式承载入口、归属、边界、出生点和清理策略 | 仍强绑 Mirror 副本、网络实体清理和 3D 边界 |
| `uMMORPG PortalToInstance.cs` | 已证明入口脚本最多只该串“查找/创建实例 -> 传送到实例入口” | 它不是实例宿主本身 |

当前已确认的本机补充负证据：

- `uMMORPG SafeZone.cs`
  - 只是 `BoxCollider` gizmo 与区域标记脚本
  - 真正进入运行时的是 `Entity.inSafeZone`
  - 只能证明“局部区域规则可用 trigger 给实体打标记”，不能补实例宿主
- `uMMORPG UIRespawn.cs`
  - 只是死亡后显示按钮并发 `CmdRespawn()`
  - 不是实例入口、实例离场或场景宿主

### 下一轮最小取证包

1. 宿主类源码
2. 入口与归属字段
3. 实例边界/出生点字段
4. 实例生命周期与清理方法
5. 单机可成立的证据
6. 若不能单机成立，明确为何只能登记

### 什么时候才算“够直接吸收”

只有同时满足下面 4 条，才允许从“只登记”升级到“直接吸收”：

1. 已看到显式实例宿主，而不是只有副本入口脚本
2. 宿主能同时承载：入口、归属、边界、实例内出生点、清理策略
3. 运行时实例定位或重建规则是宿主统一负责，不散在传送脚本里
4. 这套闭包在单机下也成立，不依赖 Mirror 队伍副本与网络实体清理

## 缺口 4：单机/本地出生点分流宿主参考

### 这条缺口为什么存在

- `设计模式`：出生点分流必须有正式宿主，不能散在 `Teleporter`、`MapInfo` 或 `PlayerSystem` 的 if/else 里。
- `软件工程`：如果没有宿主，地图入口、角色模板入口、控制组入口会各自维护一套分流规则。
- `易用`：策划需要明确知道“按什么条件走哪个出生点，找不到专用点时回退到哪”。

### 新参考必须回答的问题

1. 分流规则挂在哪个正式宿主
2. 专用出生点与默认出生点如何共存
3. 找不到专用出生点时如何正式回退
4. 失败时如何处理
5. 地图入口、角色模板入口、条件入口是否同宿主
6. 是否能脱离角色创建流程单独成立

### 直接判不合格的信号

- 强绑 `Mirror` 角色创建流
- 把分流写在传送门脚本里
- 把分流写在角色 Prefab 初始化里
- 只有出生点数组，没有正式宿主

### 当前候选源

| 候选源 | 当前价值 | 当前不足 |
| --- | --- | --- |
| `uMMORPG GetStartPositionFor(...) + NetworkStartPositionForClass.cs` | 已证明“出生点分流应归正式宿主，且专用点缺失时应回退默认入口” | 仍强绑 Mirror 出生点和角色创建流程 |
| `TopDown GoToLevelEntryPoint.cs + GameManager.StorePointsOfEntry(...)` | 已证明“跨场景入口索引”应先存正式宿主再解析 | 仍不是通用出生点分流宿主，只是场景入口样板 |

当前已确认的本机补充负证据：

- `uMMORPG UIRespawn.cs + Player.UpdateServer_DEAD()`
  - 玩家真正复活是 `GetNearestStartPosition(...) + movement.Warp(...) + Revive(0.5f)`
  - 这证明“最近出生点复活”是局部规则，但没有形成统一出生点分流宿主
- `uMMORPG Monster.cs`
  - 怪物自复活依赖 `startPosition + respawnTime`
  - 这是实体自持的局部行为，不是地图入口/角色模板入口/条件入口的统一分流方案

### 下一轮最小取证包

1. 分流宿主源码
2. 分流规则数据结构
3. 默认回退逻辑源码
4. 失败处理源码
5. 与地图/角色/队伍入口的关系
6. 正式落点是否能映射到现有 `GameCore` 闭包

### 什么时候才算“够直接吸收”

只有同时满足下面 4 条，才允许从“只登记”升级到“直接吸收”：

1. 已看到正式分流宿主，而不是把 if/else 散在地图、传送门或角色初始化里
2. 同一闭包里能同时回答：分流规则、默认回退、失败处理、入口标识
3. 这套规则能脱离 Mirror 角色创建流单独成立
4. 吸收后能映射到现有 `MapSystem / MapInfo / Teleporter / PlayerSystem` 正式边界，而不是先造新宿主占位

## 当前统一结论

- 这 4 个缺口当前都还没到“可直接吸收”
- 下一轮最值钱的进展不是写代码，而是把任一缺口的“最小取证包”补齐
- 在最小取证包补齐前，点击移动、自动靠近、实例入口、出生点分流都继续停在登记态
- 若本机现有参考池已经扫到边界，尤其前两个一级缺口没有新源码时，后续直接按 `2D移动与场景组织外部参考搜索指引.md` 去找外部新参考，不再回头重复翻本机旧参考。
