# 项目定位与迁移边界

## 当前定位

- 游戏类型：单机优先的俯视角开放世界像素复合 RPG，长期融合队伍制 CRPG、局部 RTS 指挥和 Roguelike 奇特状态/能力效果。
- 核心体验：高自由度探索、交互、采集/制作、队伍经营、角色成长、战斗、物品与世界状态积累。
- 产品参考：长期目标受 Kenshi、博德之门和 ToME4 影响。Kenshi 参考队伍沙盒、失败继续、派系、基地/生产和局部模拟；博德之门参考多角色 CRPG、独立背包/装备/快捷栏、战术控制和复杂互动选择；ToME4 参考 Roguelike 式复杂能力、状态、突变、构筑和奇特效果。三者只作为产品目标和系统设计参考，不作为代码或具体内容来源。
- Mod 方向：长期必须支持 Mod / UGC / 外部内容包；当前阶段先保证内容数据、资源引用、存档和扩展边界不被写死，具体 Mod 加载器、打包格式、创意工坊或脚本沙箱后续专项立项。
- 联机方向：确定要做 FishNet 优先评估的主机权威有限人数合作；当前阶段不接入网络框架、不创建网络目录或网络占位层。本项目不以 MMORPG、专用服务器持久世界或多人 RTS 同步为目标。
- 当前阶段目标：先完成工程地基、AI 规范、工具链迁移和目录重整，再决定玩法系统迁移顺序。
- 当前阶段不以“顺手做一个具体系统/具体菜单样板”来验证地基；框架仍在改时，新增具体业务只会放大后续重构负担。但本轮角色/背包/能力/命令重构必须服从新用户故事：多角色队伍、角色私有背包、复杂能力变化、RTS 命令链和未来主机权威联机裁决边界。
- 美术基线：MiniFantasy 是当前正式像素素材方向。换装、角色、怪物、道具和地图表现默认围绕 MiniFantasy 建立；参考工程素材只能辅助理解结构和接线，不进入正式美术口径。

## 不继承的旧目标

- 不继承旧 `FantasyWorld` 恢复任务的用户故事、单场景换装验收、旧主线剧情或旧任务阶段。
- 不继承 `dark-corridor` 的横版平台动作定位、横版玩家控制器、横版相机和横版测试场景。
- 不把旧 `task_plan.md`、`findings.md`、`progress.md` 中的阶段状态当成当前任务目标。

## 可以复用的内容

- `dark-corridor` 的 AI 规范分层、AIBridge 接入方式、工程门禁、参考矩阵方法、目录治理方法。
- 旧 `FantasyWord` 工程中仍适合俯视角开放世界的资产、MiniFantasy 像素素材、装备/换装实验、数据结构线索。
- 旧恢复文档中的事实线索，例如哪些旧资源损坏、哪些插件曾被依赖、哪些路径曾被验证过。

## 迁移原则

- 先迁工程地基和规范，再迁插件，再迁代码目录，再迁场景和资源。
- 先锁框架边界，再做具体业务；不得把 UIKit、相机、交互或其它框架调整包装成某个具体玩法菜单/流程的顺手落地。
- 可直接复制的规范和工具链优先复制，但必须改成 `FantasyWord` 的产品口径。
- 旧代码只在职责仍成立、文本健康、依赖明确、不会把旧用户故事带回来时才进入当前正式链路。
- 旧插件按“依赖核验”处理；只有插件行为要决定正式功能设计时，才升级为参考矩阵。
- 不做联机架构占位，不引入网络框架、同步方案、网络目录或网络 SDK 抽象。核心规则仍要保持单一真相源和清晰边界，这是单机可维护性、Mod 兼容和确定联机目标共同要求；本轮重构只带上命令入口、角色控制权、对象归属、物品归属、装备/使用物品裁决、伤害/状态裁决、存档写入边界和输入来源区分这些联机兼容边界。只有当联机专项正式立项时，才允许按 `docs/ai/联机与Mod边界.md` 接入 FishNet。
- Mod 支持是正式产品边界：新增数据结构、资源引用、存档字段、场景入口和规则扩展点时，默认考虑稳定 ID、版本迁移、来源归属、覆盖/合并策略和可审计配置；不得把官方内容路径、枚举分支或资源实例硬编码成未来无法被外部内容扩展的形状。

## 当前迁移顺序建议

1. 建立 `AGENTS.md` 和 `docs/ai/`。
2. 替换旧 UnityMCP 为当前 AIBridge。
3. 归档旧恢复文档和旧自动化脚本。
4. 重整 `Assets` 顶层目录，区分正式资源、第三方资源、实验资源和历史恢复残留。
5. 重新定义俯视角玩家、相机、地图、交互和数据系统的参考面。
