# 框架正式动作清单

> 用途：把三方裁决直接落成动作。
> 本清单不接受“先包一层以后再收”的第四种答案。

## 动作定义

- `直接替换`：一方在该职责上已经明显胜出，现有薄实现应退场。
- `正式融合`：一方拥有真相，另一方拥有执行或工具能力；融合后公开入口只能留一套。
- `暂不动`：现在动它只会制造第二真相、第二生命周期、第二 UI 栈，或者仍缺一级参考。

## 先分清什么该保留、什么该剔除

- `保留`：可复用的框架机制和领域框架模块，例如 `MapSystem`、`SaveSystem`、`InventorySystem`、`JournalSystem`、`DialogueSystem`、`Stats`、`Ability` 这种“系统壳 + 数据真相 + 通用流程合同”。
- `剔除`：同职责第二真相、第二生命周期、第二输入根、第二 UI 栈、第二属性真相，以及为了临时兼容而加的包装层。
- `解绑`：系统里夹带的具体产品流程、具体菜单跳转、具体内容假设、具体商店/制作/死亡界面样板；它们不一定当场删除，但不能继续拿来定义当前地基。

换句话说：

- `系统` 本身不是问题，系统本来就是框架的一部分。
- 真正的问题是 `系统是否过度全局化`、`是否静态入口过多`、`是否把实体真相和流程真相都吸到全局 system`、`是否和别的参考重复表达同一职责`。

## 直接替换

| 模块 | 胜者 | 为什么直接替换 | 正式动作 |
| --- | --- | --- | --- |
| 对象池 | `YokiFrame` | 这是纯工具职责，`GameObjectPoolService` 在容量、预热、资源句柄释放和诊断上明显更深 | 项目侧浅池退场，统一切到 `GameObjectPoolService` |
| 事件派发机制 | `YokiFrame EventKit.Type` | Yoki 已有强类型事件、注销 token、编辑器监控和安全派发；旧 `NotificationSystem` 是巨大 `UnityEvent` 字段表，职责过宽，现已退场 | 正式事件统一进入 GameCore 事件结构 + `EventKit.Type`；不得恢复旧通知中心 |
| 武器执行层 | `TopDownEngine` | 这是瞬时执行职责，TopDown 的武器状态机、命中窗口、连发、后摇、换弹和反馈触发点明显更成熟 | `2DRPG` 薄攻击执行退场，改用 TopDown 风格武器执行闭包 |
| 动作阻断模型 | `TopDownEngine` | 行动许可、受击中断、武器阻断和动画触点应该收成统一能力合同，不应散落在控制器和能力子类里 | 分散判断退场，统一改权限合同 |
| 旧自造地基 | 无保留价值 | 既不赢世界规则，也不赢动作执行，也不赢工具层，继续保留只会形成第二地基 | `Bootstrapper/RuntimeContext/ModuleInstaller/EventBus` 彻底退出正式口径 |

## 正式融合

| 模块 | 真相源 | 吸收来源 | 为什么要融合 | 正式动作 |
| --- | --- | --- | --- | --- |
| 地图、检查点、传送、重生 | `2DRPGEngine MapSystem` | `TopDownEngine` 关卡边界、默认出生点、检查点顺序、重生延迟、相机样板 | 地图名、检查点栈和地图存档必须是一套真相；但关卡表现样板明显是 TopDown 更成熟 | 保留 `MapSystem` 真相，吸收 TopDown 场景表现配置 |
| 生命数值与受击表现 | `RPG Stats` | `TopDownEngine` 击退、无敌帧、受击反馈 | 数值真相必须留在 RPG 数据里；受击表现显然不该停留在薄实现 | 数值留 RPG，受击执行和表现按 TopDown 模式吸收 |
| 存档 | `2DRPG SaveDataBlock` | `YokiFrame SaveKit` | 世界状态聚合和文件承载本来就是两种职责 | `SaveDataBlock` 保世界语义，文件层改用 `SaveKit` |
| 输入 | `GameCore InputSystem` | `YokiFrame InputKit` | 输入语义属于玩法真相，重绑定属于工具层 | 保留 `InputSystem` 入口，`InputKit` 只做重绑定/保存/冲突查询 |
| 背包真相与角色操作目标 | 全局 `InventorySystem.items/money` | 当前控制角色边界 | 背包和货币应保持一套世界真相；但“对谁装备/给谁使用”不能继续绑死唯一主角 | 保留全局背包真相，装备/使用目标跟随正式当前控制对象 |
| 前台角色回退规则 | `PlayerSystem` | 各 UI / 表现 / 拾取调用点 | 当前控制对象一旦允许切换，回退规则就必须收回唯一正式入口 | 把回退规则统一回收进 `PlayerSystem` |
| UI 宿主、菜单语义与缓存工具 | `YokiFrame UIKit` 宿主能力 | `2DRPGEngine` 菜单语义 | 宿主生命周期、层级、焦点、缓存和资源链是框架问题，UIKit 在这层更深；旧菜单语义可被吸收，但不能继续和 `UIPanel` 双栈并行 | 宿主替换已完成，当前继续用非业务化面板 smoke、静态门禁和正式 prefab 证据锁定打开/关闭/焦点/缓存/资源链，并清理旧资源与共享构件残留 |
| 属性、能力和效果规则 | EX-GAS 2.0 | 项目侧运行配置、Cue 桥、2D TargetCatcher 扩展、旧资产升级线索 | 复杂开放世界需要可扩展属性集、标签、叠层、冷却和状态效果；已迁移技能的身份、输入、时间轴、命中、伤害和表现触发必须只剩 EX-GAS 一套正式 owner，项目侧只能补资源解析、2D 捕获和旧数据升级 | 当前继续把旧 `Stats/IEffect` 规则残留直接替到 EX-GAS；已迁移技能不得再沿 `AbilitySheet / AbilityExecutionAsset` 形成正式闭包，旧 `AbilitySheet` 只服务旧存档和存量资产反序列化；旧执行资产类型已删除 |

## 暂不动

| 模块 | 为什么暂不动 | 禁止动作 | 解锁条件 |
| --- | --- | --- | --- |
| `TopDownEngine` manager、输入、GUI、Level 生命周期 | 它们会顺带引入第二生命周期、第二输入根、第二 UI 根 | 禁止把 `GameManager/LevelManager/InputManager/GUIManager` 升成正式入口 | 不解锁，只允许吸收局部模式 |
| `YokiFrame` 架构层 | 工具框架不等于玩法框架；但 `EventKit` 的事件派发机制已经胜出 | 禁止让 `Architecture/SingletonKit` 接管正式游戏生命周期；禁止把项目领域事件定义写进 Yoki 插件本体 | `EventKit.Type` 可作为正式事件派发工具使用 |
| 具体业务 UI 全量迁 `UIKit` | 当前阶段不做新的业务竖切样板，不能拿具体背包、商店、死亡界面或 HUD 当“再次证明 UIKit 可用”的迁移样板 | 禁止新增 Adapter/Wrapper 把两套菜单栈强绑在一起；禁止借业务菜单回退第二宿主 | 正式宿主已切到 `UIKit`；后续继续用非业务化面板 smoke 验证宿主、资源链、生命周期和加载模型，同时清理旧资源残留 |
| 具体业务竖切样板 | 当前阶段目标仍是框架地基，不是玩法落地 | 禁止借“验证框架可行性”为由，提前迁具体商店、背包、死亡界面、角色面板、任务面板或其它业务 UI/流程 | 只有当框架边界稳定且用户明确切到业务实现阶段时才解锁 |
| 完整点击移动 / 自动靠近 / 控制组穿越 / 实例入口 | 当前只允许保留已落地的第一阶段基础点击移动链路；完整能力仍缺一级正式参考，不能靠项目侧临时实现先做出来 | 禁止先写 `ClickMoveController`、项目侧实例入口或控制组穿越实现 | 补齐一级缺口正式参考 |
| 开放世界模拟空壳 | 没有明确拥有者、保存语义和验收场景时，空 `WorldSystem/WorldContext` 只会制造伪架构 | 禁止先建空目录、空类、空模块 | 进入具体功能规格后逐项建立 |
| `Stats` 与 `GAS` 并行接管属性 | 当前 `GameCore` 已正式接入 `AbilitySystemComponent`，继续保留旧 `Stats` 规则只会形成双真相 | 禁止让生命、法力、攻击、防御等同时从旧 `Stats` 规则与 `AttributeSet` 结算或显示 | 下一阶段继续清掉旧属性/效果残留；当前项目起步期允许直接替换正式链 |
| 游戏内卡牌自走棋模式状态 | 它是本游戏的一部分，但和开放世界有不同输入、UI、棋盘、自动战斗回合和胜负结算 | 禁止把牌局状态挂到 `GameManager` 静态快捷入口，禁止复用开放世界当前控制角色作为牌局真相 | 建立模式宿主裁决后，按 `ModeRuntime` 或同级边界进入；可依赖玩家长期数据和项目级服务 |
| TopDown manager 链 | TopDown 的总 manager 会带入第二生命周期、第二输入根、第二 UI 根和动作关卡假设 | 禁止 `GameCore` 直接依赖 `TopDownEngine.GameManager/LevelManager/InputManager/GUIManager`，也禁止用 TopDown `InventoryEngine` 替换 RPG 背包真相 | 只吸收武器执行、受击反馈、出生/重生样板等局部成熟模式 |

## 目录动作

| 目录 | 动作 | 理由 |
| --- | --- | --- |
| `Assets/Scripts/GameCore/Runtime` | 保留为当前正式 runtime 总根 | 它是当前地基整合根；在项目自有独立真相源形成前，不提前拆散 |
| `Assets/Editor/GameCore` | 保留为项目侧编辑器根 | 它服务同一套 runtime 闭包，并受 Unity `Editor` 编译边界保护 |
| `Assets/Plugins/TopDownEngine` | 保留第三方来源边界 | `TopDownEngine` 赢的是动作模式，不是项目生命周期 |
| `Assets/Plugins/YokiFrame` | 保留第三方工具来源边界 | `YokiFrame` 赢的是工具层，不是玩法层 |
| `Assets/Scripts/World/Characters/Items/Combat/Presentation` | 暂不晋升为顶层正式目录 | 只有对应系统形成 `FantasyWord` 自己的独立真相源时，才值得从 `GameCore` 正式晋升 |

当前证据不要混读成理由，但必须能落到仓库现态：

- `Assets/Scripts/GameCore/Runtime` 当前真实承载 `Game`、`Database`、`Maps`、`Controllers`、`Combat`、`UI`、`Presentation`、`Persistence` 等正式运行时闭包，对应 `2DRPGEngine Core/Runtime/Scripts` 的世界规则与宿主结构。
- `Assets/Editor/GameCore` 当前真实承载 `Editors`、`EditorWindows`、`PropertyDrawers`、`Playtest`、`Bridge`、`Persistence`、`Utils` 等编辑器支撑闭包，对应 `2DRPGEngine Core/Editor/Scripts` 的检查器和验证入口结构。
- `Assets/Plugins/TopDownEngine` 当前是真正导入工程的候选子集，含 `Common/Scripts`、`ScriptsInputSystem`、`ThirdParty/MoreMountains/*` 和 `Demos/Koala2D`；`ReferenceSources/TopDownEngine` 仍保留原始参考镜像，服务源码对照与裁决取证。
- `Assets/Plugins/YokiFrame` 当前是真正导入工程的工具层本体，含 `Core/Runtime/PoolKit`、`Core/Runtime/ResKit`、`Tools/SaveKit`、`InputKit`、`UIKit` 等；项目侧正式代码只应保留调用点，不应再复制第二份同职责工具实现。

## 一句话总裁决

- `2DRPGEngine` 赢世界规则真相，所以世界状态这层不再摇摆。
- `TopDownEngine` 赢动作表现，所以动作薄实现该退场就退场。
- `YokiFrame` 赢工具层，所以项目侧重复薄工具不再保留。
- `FantasyWord` 自己补开放世界模拟层，三方都不能整体代替它。
