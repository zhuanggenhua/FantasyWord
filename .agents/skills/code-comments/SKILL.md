# Code Comments 中文注释版

## 目标

写和代码放在一起、会长期有用的中文注释。注释解释职责、约束、契约、边界和“为什么这样做”，不要复述代码已经表达清楚的“做了什么”。

本 skill 默认使用中文注释；代码标识符仍按项目语言和仓库风格保持英文、可搜索、可重构。

## 何时使用

- 用户要求补注释、改注释、审注释质量、让代码更容易交接。
- 新增或修改公开 API、接口、抽象基类、ScriptableObject、配置类型、序列化字段、编辑器工具、验证入口。
- 代码涉及生命周期、协程、事件订阅、物理时序、异步加载、存档兼容、资源释放、状态机、条件编译、平台差异或第三方插件边界。
- Unity Inspector 中暴露字段需要中文名称、中文提示或中文分组。

## 核心原则

1. 中文优先：项目侧注释、XML 文档注释、Inspector 提示文本默认写中文。
2. 解释原因：优先说明职责、调用契约、不变量、边界条件、维护风险和取舍。
3. 少写废话：不要写“设置值”“遍历列表”“返回结果”这类复述代码的注释。
4. 就近维护：注释放在对应类型、字段、方法或关键分支附近，避免只写到外部文档里。
5. 谨慎推断：如果只能从实现推断意图，注释要保守表达，不把猜测写成事实。
6. 及时清旧：发现过期注释、注释与代码不一致、注释掉的旧代码，优先修正或删除。

## Unity/C# 硬规则

### 文件和类型

- 有明确模块边界、系统入口或编辑器工具职责的文件，应在文件顶部或主类型上写简短中文说明。
- `public`、`protected`、`internal` 类型、接口、抽象基类、ScriptableObject 配置类型必须说明职责和使用边界。
- 不要给普通 POCO、枚举或一眼能懂的小类型写空泛注释；字段语义不明显时才补。

### 字段和 Inspector

- `public` 字段或 `[SerializeField] private` 字段只要暴露到 Inspector，必须有中文显示名。
- Unity 项目优先使用 NaughtyAttributes：
  - `[Label("中文名")]`：字段中文名。
  - `[BoxGroup("中文分组")]` / `[Foldout("中文分组")]`：组织复杂配置。
  - `[InfoBox("中文说明")]`：给编辑器用户解释约束、风险或使用方式。
  - `[ShowIf]` / `[HideIf]`：条件显示，必要时给条件字段补中文说明。
  - `[ReadOnly]` / `[Required]`：表达只读、必填等编辑语义。
- 可配合 Unity 内置 `[Tooltip("中文说明")]`、`[Header("中文分组")]`、`[Range]`。
- 字段注释或 Tooltip 要说明“这个值影响什么、谁来配置、错误配置会怎样”，不要只翻译字段名。

### 方法和契约

- 对外可调用的方法要说明调用者能依赖什么、输入限制、返回值语义、失败方式和副作用。
- 私有方法只有在隐藏了重要规则、时序或不变量时才写注释。
- 不要逐行讲实现；如果注释像是在把代码翻译成中文，删掉或重写。

### 生命周期和复杂逻辑

以下场景必须写中文注释说明原因或边界：

- `Awake` / `OnEnable` / `Start` / `OnDisable` / `OnDestroy` 之间有顺序依赖。
- 协程、异步任务、取消 token、场景切换或对象池复用会影响状态。
- `Update` / `FixedUpdate` / `LateUpdate` 中的时序选择有 gameplay 或物理原因。
- 事件订阅、反订阅、跨系统回调、Timeline Signal、动画事件会影响业务状态。
- 存档字段兼容、`FormerlySerializedAs`、资源路径迁移、旧数据读取兜底。
- 第三方插件接入边界、项目侧门面和不能直接调用插件 API 的理由。

## TODO / FIXME / HACK

临时注释必须可追踪、可处理：

```csharp
// TODO: 技能系统稳定后，把这里改成从 Ability 配置读取音效 Key。
// 当前先保留硬编码入口，是为了让玩家控制器竖切能独立验证。

// FIXME: 快速切场景时可能重复订阅。修复前不要把此组件放入对象池。

// HACK: Bro_Audio 初始化晚于测试场景构建器，所以这里延迟一帧绑定。
// 若后续改成显式启动流程，应删除这个兜底。
```

不要留下没有上下文的 `TODO`、作者名、日期、废弃代码块或“以后再说”。

## 审查清单

检查注释时按下面顺序判断：

1. 是否必须中文。
2. 是否解释了职责、契约、约束或为什么这样做。
3. 是否有明显的复述代码、废话注释或过期注释。
4. Inspector 暴露字段是否有中文 `Label` / `Tooltip` / `InfoBox`。
5. 注释是否与当前实现一致。
6. 是否有注释掉的旧代码、无上下文 TODO、无依据的猜测。
7. 是否把应该由类型名、字段名或结构表达的信息塞进注释里。

## 输出要求

- 用户要求改代码时，直接编辑相关文件，保持 diff 聚焦在注释和必要的 Inspector 特性。
- 汇报时说明：改了哪些文件、补了哪些类型/字段/方法注释、哪些地方故意不补注释、仍然不确定的代码意图。
- 如果项目有更具体规则，优先服从项目 `AGENTS.md`、`docs/ai/`、`.codex/skills/` 或用户当轮指令。
