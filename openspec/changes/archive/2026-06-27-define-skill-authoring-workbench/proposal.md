# Proposal: define-skill-authoring-workbench

## Why

`plan-core-framework-roadmap` 已经把下一阶段入口锁定为“基础角色自然实现案例 + 技能编辑 + 角色构筑”，但当前还没有把“哪些问题必须先问用户、哪些框架可以先做、哪些实现必须等拍板”写成正式 change。

技能编辑和角色构筑会直接影响：

- 角色长期构筑数据怎么存。
- 技能定义资产怎么分层。
- 技能树、职业、快捷栏、资源、冷却和授予来源怎么建模。
- 编辑器、运行时、存档和验证链路的结构边界。

这些都属于会改变代码结构和资产模型的前提。如果现在直接实现默认职业、默认技能树、默认技能栏或默认技能内容，就会违反“前提未锁定不得实施”和“不新造第二套真相”的项目规则。

因此，本 change 的目标不是实现具体技能内容，而是先把技能编辑与角色构筑的正式提案、用户待确认问题、可先做边界、首批安全实现范围，以及最终对策划暴露的正常技能制作流程定义清楚。

## What Changes

- 新建 `define-skill-authoring-workbench` OpenSpec change。
- 锁定当前实现子阶段为：先完成 `基础攻击 + 动画驱动 + 碰撞盒命中 + 最小属性判定`，但不再把该样例的修补/接线/诊断入口暴露成人类作者流程。
- 蓄力攻击、背刺和复杂技能都不在本轮直接实现范围内，后续按阶段继续进入。
- 锁定下一小阶段候选为：`蓄力攻击、背刺`，再之后才进入 `火球术、陨石雨、闪电链、追踪剑、吸血、抽魂` 这类更复杂技能。
- 锁定技能运行时路线为：优先充分使用 GAS，并把 EX-GAS 推荐闭包作为必须对照的基线；推荐用法不是禁止混合的红线，混合也不是违规形态。如果动作执行 + GAS 规则的融合方案被证明比纯推荐用法更适合当前项目，可以作为正式方案，但必须保留单一入口、单一目标快照和单一结算结果。
- 锁定主流参考方向为配置型规则模型，而不是先做大型技能编辑器。参考 WoW/AzerothCore/SimulationCraft 的 spell data + effect data + power/proc 数据拆分，以及 Pathfinder/D20 的施法时间、目标、豁免、法抗、动作和专长/职业规则结构。
- 锁定第一版验收方向为“先按参考源码和成熟职责边界收口出项目自己的正式技能实现流程”。当前不得把项目侧自造窗口、修补菜单、样例维护脚本或测试场景按钮当成正式方向或默认优于参考。
- 锁定当前现态口径：基础攻击当前只证明“开发 smoke 可跑 + 正式骨架部分落地”，不证明“策划正式作者流程已成立”。
- 在不引入未确认职业、技能树和正式技能内容的前提下，第一版作者流还必须至少能对齐并复现 `2DRPGEngine` 当前真实存在的技能族：`Melee / Projectile / Dash / SelfCast / Summoning / ContactDamage / Ticking`。其中动作和角色素材优先使用项目内现有资源，不直接照搬参考工程素材；只有投射物允许使用参考或外部现成投射物资源作为过渡样例。
- 将前一轮过窄的 `ProjectileDefinition / ImpactReaction` 从顶层架构降级为 `EffectDefinition` 或执行/表现子类型；顶层改为 `AbilityDefinition / CastDefinition / CostDefinition / TargetDefinition / EffectDefinition / TriggerDefinition / ProcDefinition / ResolutionDefinition`。表现只作为规则结果的引用集合，不作为规则顶层真相。
- 明确 GameCore `GameplayFeedbackSet` 是当前项目侧表现反馈真相源；EX-GAS `GameplayCue` 只作为 GAS 侧表现触发入口，不得承担伤害、治疗、资源、状态、位移等规则结算。基础攻击当前已收口到 `GameplayEffect.Executions -> FormalInstantDamageExecution`，后续技能同样不得回退到 Cue 扣血模式。
- 新增玩家“炼金式法术配置”方向：玩家可以通过受限配方配置能力的触发与反应逻辑，不只是改变数值属性。该系统应编译或解释为同一套 Ability / Effect / Trigger / Cost 配置；第一版 UI 可以是槽位式或链式配方，不把自由节点图作为当前规则地基。
- 明确节点图裁决：节点图不是当前规则系统的主方案；只有当玩家/Mod 配方需要大量条件分支、触发链、数据流和可视化编排时，才作为高级编辑 UI 候选进入后续裁决。不得因为未来可能需要节点，就提前新造第二套技能运行真相。
- 明确技能编辑/角色构筑实现前，必须先由用户确认的最小数据模型问题。
- 明确在这些问题未确认前，允许先做的内容无关框架。
- 明确必须等待用户拍板的实现面，禁止擅自补默认职业、技能树、技能内容或流派。
- 允许本阶段使用“测试技能资产”验证实际动画、碰撞盒和属性链路，但不得把这些测试资产误报成正式内容，也不得把它们长期挂进正式角色默认能力或正式数据库登记中。
- 明确正式技能系统最终应交付“如何做技能”的单一使用流程：策划从统一技能入口新增技能、选择执行形式、配置规则与表现、绑定通用运行时壳并直接测试，而不是先修场景、补接线或点内部准备按钮。
- 明确当前执行资产层只是“单资产入口收口 + 迁移期静态预览”。尤其近战命中框当前只有静态预览，不是按动画帧可视化编辑的正式作者面。

## Scope

本 change 覆盖：

- 技能编辑提案与参考对比边界。
- 正式技能制作流的目标形态与用户可见流程边界。
- 角色构筑最小待确认问题清单。
- 内容无关的编辑框架、数据合同、校验框架、运行时挂接点的安全范围。
- 第一批安全实现范围和阻塞项边界。

本 change 不覆盖：

- 正式职业设计。
- 正式技能树结构。
- 第二小阶段之后的正式复杂技能内容、数值、特效和动画。
- 敌人 AI、行为树或其它正式等价 AI 框架。
- 为了兼容未决问题而额外新造的并行真相层。

## Acceptance Direction

- 提案必须明确：未确认的职业/技能树/技能内容不得直接实现。
- 提案必须列出会改变代码结构和资产模型的最小必要问题，而不是泛泛收集世界观想法。
- 提案必须区分“可先做的内容无关框架”和“必须等用户拍板的内容相关实现”。
- 提案必须明确：当前阶段允许用测试技能资产验证链路，但这些资产不是正式技能设计。
- 提案必须明确：当前基础攻击仍有规则残留未收干净，例如基础 `effects` 仍在 `AbilitySheet`、背刺额外效果仍在执行资产；因此不能把当前实现汇报成“规则层已完全收口”。
- 提案必须明确：旧的“工作台 / 准备链路 / 修复接线 / 样例维护菜单”不属于正式技能系统，应删除而不是转地下保留。
- 提案必须明确：当前实现子阶段只先做基础攻击和命中判定，蓄力攻击、背刺和复杂技能都进入后续阶段。
- 提案必须明确：GAS 是正式规则系统和推荐用法评估基线；动作执行、碰撞盒和表现反馈是否由 GAS 原生闭包接管，必须经过证据裁决，不能因为“推荐用法”或“当前已经混合”自动拍板。
- 提案必须明确：当前优先建立配置型规则模型，编辑器后置；所有正式架构层级必须有主流参考或本地成熟参考支撑，没有参考只能登记为候选，不能写成正式方案。
- 提案必须明确：`2DRPGEngine` 在本 change 中只承担源码级技能族与职责边界参考，不再承担“真实截图对比”或“流程 UI 对齐”验收职责；在没有新的正式参考依据前，不得把项目侧自造作者窗口、内部迁移脚本或修补逻辑写成正式方向。
- 提案必须明确：表现反馈不得形成第二套真相。项目侧表现反馈默认收口到 `GameplayFeedbackSet`；EX-GAS `GameplayCue` 只能触发表现，不能替代规则层或反馈闭包。
- 提案必须明确：执行真相当前仍未裁死单一赢家；现阶段只能接受“项目执行壳 + GAS 规则层”的收口方向，不能把某个整体框架写成已经最终胜出。
