# GameManager 静态访问策略

> 本文件属于 `define-fantasyword-foundation-framework` 的实施文档。
> 它回答“任何代码都能通过 `GameManager` 拿系统到底有什么问题，以及本项目是否继续这么做”。

## 结论

`GameManager.XxxSystem` 不是天然错误，也不是当前必须拆掉的技术债。它现在保留，因为它来自 2DRPG 地基，能让基础 RPG 系统快速组装、快速阅读和快速验证。

真正的问题不是“快”，而是“任何代码都能绕过所有权直接改同一套状态”。当系统继续扩张到开放世界、卡牌自走棋、UI 菜单运行时、属性/GAS 或第三方 manager 时，全局静态入口会让调用者看不出它正在改的是项目级状态、世界状态、模式状态还是实体状态。

因此当前策略是：

- 现有 13 个 2DRPG `GameManager.XxxSystem` 快捷入口保留。
- 禁止新增开放世界、卡牌模式、GAS、UIKit、TopDown manager 或其它同职责第二真相的静态快捷入口。
- 允许 `GameManager.GetSystem<T>()` 作为场景宿主查找方式，但新增领域系统必须先证明自己是项目级唯一系统。
- 后续不是一次性大拆，而是在具体模块进入时把所有权收回到 `Project / World / Mode / Entity` 对应层级。

## 为什么全局访问会出问题

| 问题 | 现实含义 | 在本项目里的风险 |
| --- | --- | --- |
| 隐式依赖 | 代码表面只调用一个静态入口，看不出它依赖了哪个系统、需要什么初始化顺序 | 改一个系统时不知道哪些调用点会被影响，只能全仓库搜索 |
| 生命周期混乱 | 调用者不知道目标系统是否已经初始化、是否随地图切换、是否随模式切换 | 卡牌自走棋、开放世界地图切换、读档后可能碰到旧状态 |
| 所有权模糊 | 项目级、世界级、模式级、实体级状态都被伪装成同一个全局入口 | 背包、牌局、派系、区域模拟、UI 栈容易互相污染 |
| 第二真相存活 | 为了少改调用点，旧系统和新系统都能被访问 | `Stats/GAS`、开放世界运行时/模式运行时误挂到 `GameManager.*`、或 TopDown manager 回潮都会重新制造第二真相；`AUIMenu/UIKit` 这条已在当前仓库收口，不应再被恢复 |
| 验证面过大 | 一个调用点可以跨过正式所有者直接改状态 | smoke 和静态门禁很难判断哪条链才是正式链 |
| Mod 边界不清 | 外部内容需要稳定数据和资源入口，而不是随便碰场景单例 | 长期 Mod 支持会被硬编码全局调用拖住 |

## 什么时候可以用 GameManager

| 场景 | 裁决 | 说明 |
| --- | --- | --- |
| 启动时收集并驱动 `AGameSystem` 生命周期 | 允许 | 这是当前 2DRPG 地基的核心价值 |
| 访问现有 RPG 基线系统 | 暂时允许 | 例如地图、背包、任务、存档、输入、UI 等既有系统入口 |
| 系统内部查同场景唯一系统 | 谨慎允许 | 应优先只读或通过正式方法调用，不绕过拥有者直接改内部状态 |
| 新增开放世界区域/Cell/派系/经济/日程 | 禁止挂静态快捷入口 | 这些是世界状态，不是项目全局服务 |
| 新增卡牌自走棋单局棋盘/回合/单位状态 | 禁止挂静态快捷入口 | 这些是模式状态，不是开放世界状态，也不是项目全局状态 |
| 新增 GAS 属性真相或 UIKit 菜单运行时 | 禁止挂静态快捷入口 | 必须先裁决替换哪一边，不能并行 |
| 接入 TopDown `LevelManager/InputManager/GUIManager` | 禁止 | 它们会制造第二生命周期、第二输入根和第二 UI 根 |

## 更符合软件工程的方案

本项目不采用“所有系统都从 `GameManager` 静态拿”的长期方案，也不回到旧自造 `RuntimeContext/ServiceRegistry/EventBus`。

正式方向是四层所有权：

| 层级 | 职责 | 入口形态 |
| --- | --- | --- |
| `Project` | 项目级配置、包、资源、音频后端、存档文件层、工具 | 现有 `GameManager + AGameSystem` 或后续明确项目根 |
| `World` | 当前开放世界存档、地图、区域、派系、AI 日程、经济、局部模拟 | 后续 `WorldRuntime` 或等价世界宿主 |
| `Mode` | 当前玩法模式，例如开放世界探索、卡牌自走棋、剧情演出 | 后续 `ModeRuntime` 或等价模式宿主 |
| `Entity` | 角色、物品、卡牌单位、棋盘格、场景对象 | 实体组件和领域对象自己持有局部状态 |

调用规则：

- 跨层读写必须经过拥有者的正式方法、命令或强类型事件。
- 表现层只订阅状态和事件，不直接修改领域状态。
- 工具层可以是全局的，但不能拥有玩法真相。
- 如果一个新系统不知道该挂哪一层，先写所有权矩阵，不先写代码。

## 当前实施动作

当前已经落地或登记的动作：

- `scripts/Invoke-FoundationStaticGate.ps1` 统计并限制 `GameManager` 静态 system 快捷入口，当前白名单为 13 个。
- `truth-ownership-implementation-matrix.md` 登记 `GameManager`、事件、UI、属性/GAS、输入、存档、地图/世界、背包/目标、卡牌模式、TopDown manager 和 Yoki 工具层冲突。
- 旧 `NotificationSystem` 已被彻底移除；正式事件必须进入 GameCore 强类型事件结构，并通过 Yoki `EventKit.Type` 派发。
- UI、GAS、存档、卡牌模式已建专项矩阵；未满足条件前不迁具体业务菜单、不接 GAS 属性、不建空模式系统。

后续执行顺序：

1. UI 菜单运行时只先做非业务 smoke 和资源链裁决，不迁具体菜单。
2. GAS 只有在专项矩阵证明胜出时替换 `Stats/currentStats` 同职责。
3. 开放世界和卡牌自走棋进入实现前，先建立对应 `World/Mode` 所有权规格，不挂新的 `GameManager.XxxSystem`。
